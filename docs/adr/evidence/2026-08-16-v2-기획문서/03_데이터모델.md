## 1. 위키 노드

위키의 기본 단위다. 데모에 21개 있다.

```
Node {
  id      : string      고유 키
  type    : 'core' | 'content' | 'entity' | 'source'
  title   : string      노드 이름
  meta    : {
    종류  : string      type의 한글 이름
    상태  : '확정' | '초안' | '낡음' | '충돌' | '비어 있음' | '읽음'
    갱신  : 'YYYY-MM-DD' | '—'
    출처  : string      원본 파일명과 쪽수. 없으면 '—'
  }
  body    : string[]    문단 배열. 빈 배열이면 미작성 노드
  flag?   : {           정리가 필요할 때만
    kind  : '오래됨' | '모순' | '끊김' | '빈 곳'
    note  : string      무엇을 어떻게 해야 하는지
  }
}
```

### 1.1 노드 종류 넷

| type | 한글 | 개수 | 쓰임 | 궤도 반지름 |
|------|------|------|------|-------------|
| `core` | 정체성 | 1 | 사업 한 줄 정의. 그래프 중심 | 0 |
| `entity` | 사업체 정보 | 5 | **자격 판별의 입력.** 정형 | 0.19 |
| `content` | 사업 내용 | 9 | **적합도 판정과 문서 생성의 입력.** 서술 | 0.33 |
| `source` | 원본 파일 | 6 | 올린 파일 자체 | 0.485 |

반지름은 캔버스 짧은 변에 대한 비율이다.

### 1.2 사업체 정보 다섯 [입력]

자격 판별에 그대로 쓰인다. 정형이라 룰엔진이 대조할 수 있다.

| id | 노드 | 값 예시 | 판별 용도 |
|----|------|---------|-----------|
| `biz` | 사업자 정보 | 개인사업자 · 2025-04-02 개업 | 업력, 사업자 형태 |
| `region` | 소재지 | 경기도 성남시 | 지역 요건 |
| `sector` | 업종 | 소프트웨어 개발 및 공급업 (58221) | 제한 업종 판정 |
| `owner` | 대표자 | 만 28세 | 청년 요건 |
| `grants` | 수령 이력 | 초기창업패키지 2025년 | 중복 수령 제한 |

> **업력과 만 나이를 계산값으로 둔 이유.** 공고마다 기준일이 다르다. 어떤 공고는 공고일 기준, 어떤 공고는 신청일 기준이다. "업력 1년 4개월"을 저장해 두면 어느 시점 기준인지 알 수 없어 판정이 틀릴 수 있다. 그래서 데모는 사업자등록일과 생년월일만 두고 화면에서 계산한다.
> 캐시가 필요하면 기준일과 함께 저장하는 식으로 가면 될 것 같다.

### 1.3 사업 내용 아홉 [추출]

적합도 판정과 문서 생성의 재료다.

`problem` 문제 인식 · `solution` 솔루션과 기술 · `customer` 목표 고객 · `market` 시장과 경쟁 · `local` 지역 연계 · `traction` 매출과 성과 · `team` 팀 구성 · `roadmap` 로드맵 · `finance` 자금 현황

`core` 정체성은 여기 안 들어간다. `type:'core'`로 따로 있고 그래프 중심이다. 1.1 표를 보라.

`local`(지역 연계)이 데모의 첫 추천을 만드는 근거다. 공고 취지가 지역상생이라 여기에 걸린다.

## 2. 연결

```
Link = [fromId, toId]      무방향. 데모에 37개
```

### 2.1 종류는 저장하지 않고 파생한다

```js
function linkType(a, b) {
  if (a === 'core' || b === 'core')                    return 'sub';   // 하위
  if (node(a).type === 'source' || node(b).type === 'source') return 'src';   // 출처
  return 'rel';                                                        // 관련
}
```

| 종류 | 무엇 | 화면 |
|------|------|------|
| `sub` 하위 | 정체성에서 각 항목으로 | 실선 |
| `rel` 관련 | 사업 내용끼리 | 점선 |
| `src` 출처 | 원본 파일에서 노드로 | **기본 숨김** |

근거는 `05_그래프설계근거.md` 4.3이다.

## 3. 궤도 구획

각도가 의미를 갖게 한다. **노드를 어느 구획에 넣을지는 스키마로 정해져 있다.**

```
GROUPS {
  content : [ 문제와 해결   [problem, solution]
              시장과 고객   [customer, market, local]
              성과와 자금   [traction, finance]
              팀과 계획     [team, roadmap] ]
  entity  : [ 등록 정보     [biz, region, sector]
              대표와 이력   [owner, grants] ]
  source  : [ 원본 파일     [f1..f6] ]
}
```

배치는 구획마다 각도 범위를 나눠 갖고 그 안에 균등 배치한다. 구획 사이에 `GAP = 0.30` 라디안 여백을 둔다.

## 4. 공고

```
Program {
  id       : string
  name     : string                       [추출]
  org      : string                       [추출] 주관기관
  src      : '중앙부처' | '지자체'          [추출]
  kind     : '현금' | '바우처' | '공간' | '멘토링'   [추출] 무엇을 주는가
  amount   : string                       [추출] 표시용 문자열
  dday     : number                       [계산]
  deadline : 'YYYY-MM-DD'                 [추출]
  fit      : number 0~1                   [계산] 적합도. 순위용
  fitL     : '매우 높음'|'높음'|'보통'      [계산] 표시용
  purpose  : string                       [추출] 공고 취지 한 줄. 적합도의 절반
  why      : string                       [계산] 왜 맞는지. 이유 없으면 내보내지 않는다
  nodes    : string[]                     [계산] 근거가 된 위키 노드 id
}
```

`purpose`와 `nodes`가 적합도의 양쪽이다. 화면은 이 둘을 좌우로 놓고 잇는다.

### 4.1 제외된 공고

```
Excluded { name, org, reason }      [계산] reason은 자격 미달인지 취지가 먼지
```

### 4.2 공고 상세

```
Detail {
  period : string          접수 기간
  type   : string          지원 유형
  amount : string          지원 내용과 자부담
  method : string          접수 방법
  intro  : string          지원 내용 서술
  reqs   : [항목, 기준][]                    [추출] 신청 자격
  docs   : [서류명, 양식종류, 탈락여부][]      [추출] 제출 서류
  steps  : [차수, 이름, 설명][]              [추출] 심사 단계
  notes  : string[]                         [추출] 유의사항
}
```

> **`notes`를 따로 둔 이유.** 자부담 비율, 지원 상한, 중복 제한처럼 **놓치면 사용자가 실제로 손해를 보는 조건**이 여기 들어간다. 실물 양식을 확인해 보니 "인테리어 공사비에 자부담 반드시 포함", "총사업비의 70%까지 지원" 같은 것이 공고 본문이 아니라 **첨부 양식의 표 머리말**에 적혀 있었다.
> 요약이나 축약 과정에서 이런 문장이 날아가기 쉬운 자리라 별도 필드로 뺐다. 파싱 전략은 개발이 정하면 되고, 다만 이런 조건이 어디에 어떻게 남는지는 한 번 확인해 주면 좋겠다.

## 5. 문서

```
Section {
  key   : string
  name  : string                 심사 항목명
  score : number                 배점
  guide : string    [추출]       양식 각 칸에 적힌 "~를 기술" 지침
  paras : Para[]
}

Para = { t : string }                      완성된 문단
     | { gap : nodeId, label : string }    위키에 정보가 없어 못 쓴 자리
```

**`gap`이 제품 논지가 화면에 드러나는 자리다.** 어느 위키 노드가 비어서 못 썼는지를 가리킨다. 화면에서 마커가 되고, 누르면 그 노드에 대해 묻고, 답하면 노드에 적립되며 문단이 채워진다. "위키가 있으면 덜 묻는다"는 이야기가 여기서 눈에 보인다.

표현 방식은 바뀌어도 되는데, **어느 노드가 비어서 못 썼는지를 되짚을 수 있는 연결**은 어떤 형태로든 남으면 좋겠다. 그게 없으면 적립 루프가 안 돈다.

완성도 = `(전체 문단 수 - 안 채운 gap 수) / 전체 문단 수`

데모의 항목 넷은 경기도 공고 양식이다. 문제 인식 25 · 해결 방안 25 · 지역 연계 계획 30 · 추진 역량 20.

## 10. 지금 상수인 것

데모에서 값이 박혀 있는 자리다. 어떻게 채울지는 열려 있다.

| 무엇 | 어디 | 메모 |
|------|------|------|
| 파일에서 노드 추출 | 1장 Node | HWP·DOCX·PDF 파싱이 앞에 걸린다 |
| 공고 수집과 정규화 | 4장 Program | 사이트마다 구조가 다르다. 대상 개수는 미정 |
| 공고 취지 추출 | `Program.purpose` | 적합도의 한쪽 |
| 제약 보존 | `Detail.notes` | 4.2 메모 참조 |
| 양식에서 항목·배점·지침 추출 | 5장 Section | 첨부 안에 있다 |
| 자격 판별 | 1.2 + `Detail.reqs` | 아래 참조 |
| 적합도 계산과 이유 생성 | `fit`, `why`, `nodes` | 이유가 안 나오는 경우 처리는 미정 |
| 문서 생성 | `Para.t` | |
| gap 판정 | `Para.gap` | 위키 노드가 비었는지 확인 |

### 10.1 자격 판별을 결정론으로 두려는 이유

같은 프로필과 같은 공고에 항상 같은 답이 나와야 한다고 봤다. 심사 기준에도 "안정적으로 결과를 잘 도출해내나"가 있다. 그리고 자격은 요건과 값의 대조라 규칙으로 표현이 되는 영역이기도 하다.

다만 실제 공고 요건이 규칙으로 안 떨어지는 경우가 얼마나 되는지는 아직 모른다. 파싱해 보고 판단하면 될 것 같다. **비정형 요건이 많으면 방식을 다시 이야기해야 한다.**

### 10.2 문서 생성에서 사실을 다루는 방식

금액·자격·마감일 같은 값은 공고 데이터에서 온 것만 쓰자고 정했다. 이유는 이런 값이 틀리면 사용자가 실제로 손해를 보기 때문이다. 잘못된 지원 금액을 믿고 예산을 짜는 식이다.

구현 방법은 여러 가지가 있을 것이다. 프롬프트로 제약하든, 생성 후 검증하든, 템플릿으로 끼워 넣든 결과가 같으면 된다.

## 11. 정해진 것: 노드가 원본 청크를 갖는다 (2026-08-16)

`서비스_설계_개발논의용.md` 3장의 **GraphRAG 구조로 간다.** 원본 문서를 노드로 두지 않고, 각 노드가 자기 근거가 되는 **청크를 매단다.**

```
Document (올린 파일 원본)
  └─ Chunk (전처리된 원문 조각 + 위치정보: 파일 · 쪽 · 표 좌표)

Node (구조화 항목)
  ├─ value        구조화된 값
  ├─ evidence ──▶ 자기 근거가 되는 Chunk[]
  └─ ...
```

### 11.1 왜 이렇게 가나

1. **출처가 문자열이 아니라 연결이 된다.** 지금은 `meta.출처`가 `'IR_2026Q2.pdf 8쪽'`이라는 글자다. 사람이 읽을 수는 있지만 원문으로 되짚을 수 없다. 청크를 매달면 노드에서 원문 조각을 바로 연다.
2. **문서 생성의 재료가 여기서 나온다.** 설계안 [8] 3번이 "해당 노드에 매달린 evidence 청크만 retrieve"라고 한 것이 이 구조를 전제한다. `Node.value`는 손실 압축이라 서술과 수치가 날아간다. 원문이 있어야 문단을 쓴다.
3. **환각을 막는 자리가 생긴다.** 설계안 원칙 ②가 "나중에 붙이면 불가능"이라고 한 것이 이것이다.

### 11.2 지금과 달라지는 것

| | 지금 (1~10장) | 앞으로 |
|---|--------------|--------|
| 노드 타입 | 넷. `core` `content` `entity` `source` | **셋.** `source`가 빠진다 |
| 원본 파일 | 그래프의 노드 | **노드가 아니다.** `Document` 계층 |
| 출처 | `meta.출처` 문자열 | **`evidence: Chunk[]`** |
| 선 종류 | 셋. 하위 · 관련 · **출처** | **둘.** 하위 · 관련 |
| 노드 수 | 21 | **15** |
| 연결 수 | 37 | **21** |

**선이 43% 준다.** `05_그래프설계근거.md` 4.1이 "원본 파일을 그래프에서 기본으로 숨기면 선이 절반 이하로 준다"고 한 것을, 숨기는 대신 **애초에 노드로 두지 않아** 달성한다. 4.1의 "필요할 때만 켠다"는 노드 상세에서 근거 청크를 여는 것으로 대신한다.

### 11.3 남는 것

**`Ingest`(7장)는 그대로 쓴다.** 파일이 어떤 노드를 만들었는지는 여전히 필요하다. 화면의 "파일 관리"가 이 관계를 보여준다. 다만 그래프에는 안 그린다.

**`meta.상태`와 `flag`를 설계안의 `confidence` · `status`와 어떻게 합칠지는 아직 안 정했다.** 설계안은 상태 셋(`unverified` / `estimated` / `confirmed`)에 `confidence` 값이고, 지금은 상태 다섯에 `flag` 넷이다. `끊김`(어디에도 안 이어짐)과 `모순`(파일마다 값이 다름)은 그래프 위상과 병합 결과에서 나오는 것이라 신뢰도 점수로는 표현이 안 된다. **별도 안건이다.**

### 11.4 화면에 걸리는 것

1. 위키 그래프에서 **원본 파일 켜고 끄기 버튼이 없어진다.** 켤 노드가 없다.
2. 노드 상세의 **출처 한 줄이 근거 청크 목록으로 바뀐다.** 누르면 원문 조각이 열린다.
3. 문서 화면에서 문단마다 근거를 표시할 수 있게 된다. 설계안 [8] 3번의 "문단별 근거 표시"다.
