# plan/06 — 목록 수집과 조회

> 상태: 진행중
> 종류: 슬라이스 (01·02 관통)
> 선행: —
> 우선순위: 최우선

**공고 목록 API를 받아 DB에 넣고 화면에서 보는 것**까지만 한다. 첨부는 열지 않는다.

---

## 목표

두 출처의 목록 API가 DB에 쌓이고, 관리 화면에서 목록과 상세를 볼 수 있다.
그리고 **저장소에 실행 가능한 명령이 처음으로 생긴다.**

---

## 왜 이걸 먼저 하는가

00~05는 단계다. 이건 단계를 세로로 자른 것이라 **01의 스택 확정과 02의 수집 일부를 관통한다.**

지금 코드가 0줄이라 [01](01-기반.md)·[02](02-수집과-추출.md)·[04](04-화면.md)의 `검증` 절이 전부 비어 있다. [T-0003](01-기반.md#t-0003-스택-확정)이 "빈 저장소가 실행 가능한 상태"를 완료 조건으로 건 것이 이것이고, **그게 채워지기 전까지는 다른 계획의 완료를 판정할 수단이 없다.**

그리고 **스키마 모양은 코퍼스가 결정한다**([ADR-0009](../adr/0009-구-백엔드-재사용-보류.md)). 공고 3만 건을 실제로 넣고 화면으로 들여다보는 것이 L1 추출 스키마를 설계하기 위한 선행 조건이다. 지금 스키마를 쓰면 지어낸 값이 된다.

|------|-----|

### 서버측 날짜 필터는 틀린 값을 준다

| 질의 | matchCount | 응답 첫 건의 실제 마감일 |
|------|-----------|------------------------|
| `pbanc_rcpt_end_dt <= 20200101` | 7,366 | **20201231** ← 조건 위반 |
| `pbanc_rcpt_end_dt = 20260101` | 26,907 | **20261231** ← 조건 위반 |
| `pbanc_rcpt_end_dt >= 20270101` | 29,690 | **20260827** ← 조건 위반 |
| `pbanc_rcpt_end_dt >= 20260816` | 29,689 | 20260827 |
| `pbanc_rcpt_end_dt <= 20260816` | 29,689 | 20260827 |

`>=`와 `<=`가 같은 수를 내고, **조건을 위반하는 레코드가 결과에 섞여 나온다.** 에러도 0건도 아니라 그럴듯한 숫자와 그럴듯한 레코드를 준다.

코드값 `EQ`와 이름 `LIKE`는 정상이다. `rcrt_prgs_yn=Y` → 274, `ZZZZ` → 0, `biz_pbanc_nm LIKE 창업패키지` → 407(첫 건 "2026년 초기창업패키지 로켓십 IR 경진대회").

## 정한 것

| 항목 | 결정 | 이유 |
|------|------|------|
| 언어 | Python 3.13 | HWP 파서. 스파이크 `hwp_text.py`가 OLE + raw deflate + 레코드 워크로 추출률 100%를 냈다. 3.14는 신규 의존성 휠이 비어 있을 수 있어 한 단계 내린다 |
| 패키지 | uv | 락파일 + 파이썬 버전 고정. 현재 `.venv`는 시스템 3.14.4를 그대로 쓰고 있다 |
| 웹 | FastAPI | 나중에 제품 프론트에 JSON을 주는 서버와 같은 프로세스다 |
| 관리 화면 | Jinja2 템플릿 | 운영 도구는 `SPEC.md` §6 범위 밖이다. 제품 프론트와 섞지 않는다. API 계약을 아직 안 정해도 된다 |
| DB | PostgreSQL (docker compose) | 원문 payload를 JSONB로 보존한다. 제품과 같은 DB를 쓴다 |
| ORM | SQLAlchemy 2.0 + Alembic | 추출 스키마는 코퍼스를 보고 정하므로 스키마가 계속 바뀐다 |
| 수집 실행 | CLI | 버튼·스케줄러·큐는 지금 붙이면 과설계다 |
| LLM 제공자 | **안 정한다** | 이 슬라이스는 LLM을 한 번도 부르지 않는다 |

확정 근거는 [T-0003](01-기반.md#t-0003-스택-확정)이 ADR로 남긴다.

### 저장 원칙 — 출처별 원본 테이블 + 통합 뷰

**API가 준 컬럼을 전부 만든다.** 기업마당 22개, K-Startup 30개를 각자 자기 테이블에 그대로 둔다.

```
raw_fetch          응답 통째 (봉투·쿼터 포함)
bizinfo_notice     기업마당 22컬럼 전부
kstartup_notice    K-Startup 30컬럼 전부
notice (뷰)        둘을 공통 8필드로 매핑해 UNION ALL
attachment         첨부 메타
```

| 규칙 | 이유 |
|------|------|
| **컬럼 이름은 API 필드명 그대로.** 대소문자까지 (`pblancNm`) | 번역하거나 눕히면 API 문서와 1:1 대조가 깨진다. Postgres는 따옴표가 필요하지만 SQLAlchemy가 자동으로 붙이고, 손으로 쓰는 SQL은 뷰 정의 한 곳뿐이다 |
| **PK는 API의 자연키** (`pblancId` / `pbanc_sn`) | 실측 전량에서 유일하고 빈 값이 없다(1,538/1,538 · 4,000/4,000). K-Startup의 `id` 필드와 충돌하지도 않는다 |
| **전부 TEXT로 받는다** | API가 날짜도 `"20260827"` 문자열로 준다. 타입을 여기서 강제하면 이상한 값 하나에 적재가 통째로 깨진다 |
| **파생 값은 `derived_` 접두사** | API가 준 값과 우리가 만든 값을 섞지 않는다. 날짜 변환이 여기 들어간다 |
| **처음 보는 필드는 `extra` JSONB로** | API가 필드를 늘려도 적재가 안 멈춘다. **대신 경고와 건수가 남는다.** 조용히 사라지지 않게 |
| **통합은 물리 테이블이 아니라 뷰** | 물리 테이블이면 원본 두 벌과 동기화 문제가 생긴다. 뷰면 매핑을 고칠 때 재적재가 없다 |

**한 테이블에 52컬럼을 몰지 않는 이유**는 44개가 한쪽에서 영원히 NULL이 되기 때문이다. 출처별로 나누면 그 문제가 사라진다.

뷰의 키는 `(source, external_id)` 두 개 조합이다. 각 테이블이 자기 PK를 따로 갖는다. 판정 결과가 공고를 FK로 참조해야 하면 그때 물리 테이블로 바꾼다. [03](03-자격-판별.md)의 일이다.

### 수집 원칙 — 서버측 필터를 쓰지 않는다

전량이 기업마당 1회 + K-Startup 149회다. **일 한도 10,000의 1.5%**다. 아낄 이유가 없는데, 아끼려다 조용히 틀린 모집단을 얻는다. 마감일 기준 증분 수집을 했다면 그 오염을 알아챌 방법이 없었다.

예외는 `rcrt_prgs_yn EQ Y`(274건)뿐이고, **모집단 확정이 아니라 작업 큐 우선순위로만** 쓴다.

### T-0009 API 실측 기록

- 상태: 대기
- 선행: —

위 "이미 확인된 것"을 `adr/evidence/`에 남기고 `SPEC.md` §8을 갱신한다. 코드가 필요 없다.

**왜.** 측정은 끝났는데 남은 곳이 계획 파일뿐이다. 계획은 완료되면 상태만 바뀌는 문서라 실측값의 정본이 될 수 없다([ADR-0001](../adr/0001-정본-문서-체계.md)). 특히 **날짜 필터가 틀린 값을 준다는 사실은 잊으면 반드시 다시 밟는다.** 그럴듯한 숫자가 나오기 때문이다.

**완료 조건**

- `SPEC.md` §8에 일 한도와 전량 건수가 올라간다
- 기업마당 일 한도를 포털 마이페이지에서 확인하거나, **확인 불가로 기록한다**

**건드리는 것** — `adr/evidence/` 새 문서, `SPEC.md` §8

- 상태: 대기
- 선행: —

### T-0011 저장 모델 — 출처별 원본 + 통합 뷰

- 상태: 대기
- 선행: [T-0010](#t-0010-저장소-골격)

| 테이블 | 담는 것 |
|--------|---------|
| `raw_fetch` | 출처, 요청 URL(키 마스킹), 받은 시각, **응답 payload 원문(JSONB)**, item 수, 바이트 수, 잔여 쿼터 |
| `bizinfo_notice` | **API 22컬럼 전부** + `extra` + `derived_apply_start/end` + 해시·시각 |
| `kstartup_notice` | **API 30컬럼 전부** + 같은 부가 컬럼 |
| `notice` (뷰) | 둘을 공통 8필드로 매핑해 `UNION ALL` |
| `attachment` | 공고 FK, 파일명, 확장자, URL, 구분(공고문/기타) |

규칙은 위 "저장 원칙"에 있다.

**왜 원문을 그대로 남기는가.** 실측에서 DOCX 파서가 없어 첨부 20%를 통째로 놓쳤고, **파서를 붙여 다시 보니 결론이 바뀔 수도 있었다**([evidence](../adr/evidence/2026-08-16-첨부파싱-배점실측.md) §5.6). 같은 일을 API 쪽에서는 안 겪게 하는 장치다. 나중에 "이 필드도 쓸걸" 싶을 때 재수집이 필요 없다.

**완료 조건**

- 매핑을 바꿀 때 **뷰 정의만 고치면 되고 재적재가 없다**
- `(출처, 외부 ID)`로 upsert된다. 같은 수집을 두 번 돌려도 행이 늘지 않는다
- 콘텐츠 해시가 다르면 갱신하고 같으면 최종 확인 시각만 올린다
- **API에 없던 필드가 오면 `extra`에 담기고 건수가 보고된다.** 조용히 사라지지 않는다
- `attachment`가 0건인 공고와 아직 안 본 공고가 **구분된다.** 기업마당 28%가 첨부 0개, K-Startup은 전량이 미확인이다
- 통합 목록이 출처 필터·정렬·페이징으로 도는 것을 `EXPLAIN`으로 확인한다

**안 만드는 것** — L1 테이블(요건·평가·양식), 근거 구간, 신뢰도, 프로필, 판정. 전부 [01](01-기반.md)·[02](02-수집과-추출.md)·[03](03-자격-판별.md)의 몫이다.

**건드리는 것** — `alembic/versions/`, 모델 정의

### T-0012 목록 수집기 2종

- 상태: 대기
- 선행: [T-0011](#t-0011-저장-모델--원문과-정규화를-나눈다)

출처별 어댑터를 공통 인터페이스 뒤에 둔다. 두 응답 형태가 완전히 다르다.

**왜 봉투 검증이 정상 경로인가.** 두 API 모두 실패를 HTTP 200으로 준다. 기업마당은 `reqErr`, K-Startup은 봉투 없는 `{"code":0,"msg":"정상"}`이다. 후자는 `data.get('data') or []` 로 받으면 **0건으로 읽고 조용히 넘어간다.** 방어 코드가 아니라 파싱의 첫 단계여야 한다.

**완료 조건**

- `uv run python -m finnect.ingest --source bizinfo` 로 1,538건이 들어간다
- `uv run python -m finnect.ingest --source kstartup` 로 29,789건이 들어간다
- **봉투가 기대한 모양이 아니면 즉시 실패한다.** 기업마당은 `reqErr` 검사, K-Startup은 `matchCount` 키 존재 검사를 item 수보다 **먼저** 한다
- K-Startup 페이징이 `matchCount` 기준으로 끝난다. `totalCount`는 필터와 무관하게 29,789 고정이라 종료 조건으로 쓰면 틀린다
- 매 응답의 `x-ratelimit-remaining`을 기록한다
- 두 번 돌려도 건수가 같다
- **서버측 날짜 필터를 쓰지 않는다.** 코드에 `cond[...::GTE]`가 없다

**건드리는 것** — `ingest/` 어댑터, CLI 진입점

### T-0013 조회 화면

- 상태: 대기
- 선행: [T-0012](#t-0012-목록-수집기-2종)

FastAPI + Jinja2로 목록과 상세 두 장. 인증 없이 로컬에서만 띄운다.

| 화면 | 담는 것 | 읽는 곳 |
|------|---------|---------|
| 목록 | 사업명, 출처, 기관, 접수 기간, 첨부 수, 최종 확인 시각. 출처 필터와 이름 검색. 페이징 | `notice` 뷰 |
| 상세 | **그 출처의 컬럼 전부**(22개 또는 30개) + 첨부 목록 + `extra` + 원본 공고 링크 | 원본 테이블 직접 |

경로는 `/notice/{source}/{external_id}` 다. 뷰의 키가 두 개 조합이라 그렇다.

**왜 상세에서 뷰를 안 거치는가.** 이 화면의 목적은 운영이 아니라 **L1 스키마 설계를 위한 코퍼스 관찰**이다. 공통 8필드만 보이면 무엇을 빠뜨렸는지 알 수 없다. 컬럼 전부를 봐야 다음 단계에서 무엇을 뽑을지 정할 수 있다.

**완료 조건**

- 3만 건 목록에서 페이지 이동이 막히지 않는다
- 상세에서 그 출처가 준 컬럼을 **하나도 빠짐없이** 볼 수 있다
- `design/`의 토큰·컴포넌트를 **따르지 않는다.** 제품 화면이 아니다

**안 하는 것** — 인증, 수집 실행 버튼, 편집, 삭제

**건드리는 것** — `admin/` 라우트와 템플릿

## 검증

```bash
uv sync
docker compose up -d db
uv run alembic upgrade head
uv run python -m finnect.ingest --source bizinfo
uv run python -m finnect.ingest --source kstartup
uv run uvicorn finnect.admin.app:app --reload   # http://127.0.0.1:8000
uv run pytest
uv run ruff check .
```

- [ ] clone한 사람이 `README.md`만 보고 위 명령을 통과시킨다
- [ ] 기업마당 1,538건 · K-Startup 29,789건이 들어간다
- [ ] 같은 명령을 두 번 돌려도 건수가 같다
- [ ] 인증키를 지우고 돌리면 **0건 성공이 아니라 실패**한다 (두 출처 각각)
- [ ] 첨부 0개 공고와 미확인 공고가 화면에서 구분된다
- [ ] 상세에서 원문 payload를 볼 수 있다

**네 번째 항목이 이 슬라이스의 핵심 검증이다.** 두 API가 실패를 HTTP 200으로 주기 때문에, 이걸 통과하지 못하면 나머지 건수는 전부 의미가 없다.
