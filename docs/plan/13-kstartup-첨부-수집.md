# plan/13 — K-Startup 공고에도 첨부를 붙인다

> 상태: 진행중 (2026-08-19) — T-0048 · T-0049 완료 · **T-0050 은 데모 표본 1,308개까지 했다**(해독 96.2%). 전량은 디스크가 막고 T-0051 은 보류다
> 종류: 슬라이스 (F2-2 관통)
> 선행: [07](07-첨부-내려받기와-해독.md) — 내려받기·해독을 그대로 쓴다
> 근거: [2026-08-18 K-Startup 첨부 조사](../adr/evidence/2026-08-18-kstartup-첨부-조사.md)

**[07](07-첨부-내려받기와-해독.md)이 `안 하는 것`에 "K-Startup 첨부를 긁지 않는다. 상세 페이지 스크래핑은 별개 작업이다"라고 적고 넘겼다. 그 별개 작업이 이것이다.**

---

## 목표

```
공고 31,327건
  기업마당   1,538건 ( 4.9%)  ← 첨부 3,354건
  K-Startup 29,789건 (95.1%)  ← 첨부 0건        ← 이걸 채운다
```

**지금 우리가 보는 공고는 전체의 5%뿐이다.** 그리고 [CLAUDE.md](../../CLAUDE.md)의 함정이 **"평가 정보는 공고 본문에 0%"**라고 못 박았으므로, 나머지 95%는 **자격 요건도 양식도 작성 지침도 하나도 없는 상태**다. [plan/11](11-작성-항목-추출과-표시.md)이 만든 "낼 서류" 화면도 기업마당에서만 뜬다.

끝나면 이렇게 된다.

```
uv run python -m finnect.attach --scrape-kstartup   # 첨부 목록 (파일은 안 받는다)
uv run python -m finnect.attach --source kstartup   # 받고 해독. 07 의 코드 그대로
```

---

## 왜 지금인가

**막는 것이 없다.** 조사가 끝났고 기술적 불확실성이 없다 — 파서를 확정했고 다운로드도 확인했다. 남은 것은 시간과 디스크다.

그리고 **효과가 이 레포에서 가장 크다.** OCR([ADR-0030](../adr/0030-OCR은-rapidocr-로컬로-하고-검출은-server-를-쓴다.md))이 기업마당 공고 59건을 열었는데, 이건 **공고 29,789건**을 연다.

## 태스크

### T-0048 상세 페이지에서 첨부 목록 긁기

> **완료** (2026-08-18). `src/finnect/attach/kstartup.py` · CLI `--scrape-kstartup`.
> **아직 안 돌렸다** — 코드만 있다.

- **마감 공고는 `bizpbanc-deadline.do` 로 들어간다.** 실측 29,515/29,789(99.1%)가 마감이라 사실상 전부에 필요하다. 안 바꾸면 18KB 짜리 껍데기가 온다(첨부 0개)
- **파일명은 `file_bg` 의 `title` 에서 가져온다.** 링크 텍스트는 전부 `다운로드` 이고, `Content-Disposition` 은 CP949 를 ISO-8859-1 로 보내 깨진다
- **`fnPdfView` 는 미리보기라 첨부가 아니다.** 세면 개수가 두 배가 된다
- **껍데기와 '첨부 없음'을 구분한다.** 껍데기는 우리가 주소를 잘못 고른 것이고, 첨부 없음은 그 공고의 사실이다
- **재수집이 이걸 안 지운다** — `_flush` 의 삭제 대상이 "이번 적재에 첨부가 딸려 온 공고"로 한정되고 K-Startup 정규화기는 `attachments=[]` 를 낸다. `tests/test_attach_kstartup.py` 가 막아 둔다

### T-0049 전량 긁기

> **완료** (2026-08-19). **56.5분 · 실패 0건 · 껍데기 0건 · 첨부 67,300개.**

- ~~약 4.4시간~~ **56.5분이었다**(0.11초/건). 상세 페이지가 예상보다 빨랐다
- **일 한도는 없었다.** 29,740회를 연속으로 때렸는데 차단도 지연도 없었다
- **`rcrt_prgs_yn` 이 낡아서 껍데기가 온다 — 고쳤다.** 적재 시점의 값이라 그 뒤에
  마감된 공고는 `Y` 로 남는다. 맛보기 50건 중 7건이 그랬고(`178876` 은 접수마감이
  `20260817` 인데 `Y` 였다) ongoing 이 18KB 껍데기를 줬다. **껍데기가 오면 반대쪽
  주소를 한 번 더 본다**(`flip_url`). 전량에서 **123건**이 이렇게 살아났고 껍데기가
  0건이 됐다. 상태를 고쳐 쓰지 않고 주소만 다시 본다 — 공고 상태는 수집이 정할 값이다
- 첨부 없음 2,224건. **껍데기와 구분된다** — 껍데기는 우리가 주소를 틀린 것이고
  첨부 없음은 그 공고의 사실이다
- 포맷 — hwp 33,540 · pdf 15,021 · jpg 9,602 · png 4,502 · txt 1,822 · hwpx 846 ·
  docx 689 · zip 474. **읽는 포맷이 75%다**

### T-0050 내려받기와 해독

> **07 의 코드를 그대로 쓴다.** `attach.service.run()` 은 출처를 안 가린다.
> **데모 표본 1,308개는 받았다** (2026-08-19). **전량은 디스크가 막는다** — 55.3GB 대 여유 24GB.

- ~~약 59,578건 추정~~ **실측 67,300개.** 지금 3,354건의 **20배**
- ~~11GB~36GB~~ **실측 55.3GB.** 크기를 400개 표본으로 쟀다(평균 775KB). HEAD 는
  400 이고 Range 는 무시되지만 **응답 헤더에 `content-length` 는 온다** — 스트림으로
  열어 헤더만 읽고 끊었다. 파일은 안 받았다
- **이 서버 여유가 24GB 다.** 전량은 못 받는다

| 받는 범위 | 공고 | 첨부 | 용량 | 시간 |
|---|---:|---:|---:|---:|
| 전량 | 29,789 | 67,300개 | 55.3GB | ~10시간 |
| [03](03-자격-판별.md) T-0054 필터 통과분 | 15,643 | 40,086개 | 30.1GB | ~6시간 |
| + 읽는 포맷만 | 15,643 | 32,915개 | 19.9GB | ~5시간 |
| **데모 표본** (`--demo --read-only`) | **591** | **1,308개** | **0.83GB** | **~12분** |

**데모 표본으로 간다.** 본선은 시연이 필수이고 MVP 완성도가 30점이라([SPEC](../SPEC.md) §1.5)
전량을 받아 두는 것보다 동선이 끝까지 도는 것이 먼저다.

- **기업마당 통과분(563 공고 · 읽는 포맷 1,235개)과 같은 규모**로 맞췄다. 두 출처가
  화면에서 비슷한 비중으로 뜬다
- **계획서 양식 보유가 118건**이다. 기업마당은 같은 규모에서 28건이라 **4배**다 —
  "들어가면 문서가 이미 써져 있다" 를 보이려면 이 숫자가 핵심이다
- **접수중 122건은 전부 넣는다.** 제품 API 가 `open_only=True` 라 마감된 공고는
  화면에 안 뜬다 — 데모에서 실제로 보이는 것이 그 122건이다
- **무작위 시드를 안 쓴다.** 공고 번호 % 36 이라 언제 돌려도 같은 집합이다.
  넓히려면 나눗수만 줄인다

- **이미지가 43%다.** jpg 9,602개(17.1GB) + png 4,502개(6.6GB) = 23.7GB 인데
  **한 장도 못 읽는다** — 첨부 OCR 은 꺼져 있다([ADR-0030](../adr/0030-OCR은-rapidocr-로컬로-하고-검출은-server-를-쓴다.md))
- **필터는 여기에만 건다. 목록에는 안 건다.** T-0049 가 첨부 URL 을 전량 확보해 뒀으니
  나중에 규칙이 바뀌면 그때 받으면 된다 — [`notice-filter/로직과근거.md`](../../notice-filter/로직과근거.md)
  §12 "수집은 전량" 이 걱정한 "놓치면 복구 못 한다" 를 T-0049 가 이미 막았다
- **포맷을 파일명으로 거르는 대가가 있다.** 기업마당 3,354건 중 7건(0.2%)이 이름과
  내용이 달랐다. 받기 전에는 이름밖에 없어서 피할 방법이 없다
- **오류를 HTTP 200 으로 주지 않는다.** 맛보기 133건이 전부 200 + octet-stream 이었고
  HTML 오류 페이지가 0건이다. 기업마당과 다르다
- 맛보기 133건 실측 — 해독 92건. **지원 포맷 모수로는 92/97(94.8%)** 로 기업마당
  94.6% 와 같다
- **받는 쪽은 필터를 모른다.** `--only <파일>` 이 URL 목록을 읽을 뿐이고 그 목록을
  누가 만들었는지 `attach` 가 모른다(`tests/test_attach_only.py` 가 임포트 경계를
  막는다). 규칙이 바뀌거나 `notice-filter/` 를 통째로 지워도 이 코드는 안 바뀐다

```bash
# 고르는 쪽 — notice-filter/
python3 kstartup.py --json out/kstartup.json --demo --read-only --urls out/demo-urls.txt
# 받는 쪽 — 목록만 읽는다
uv run python -m finnect.attach --only notice-filter/out/demo-urls.txt --source kstartup
uv run python -m finnect.extract      # 낼 서류·작성 항목. 네트워크를 안 쓴다
```

#### 데모 표본 실측 (2026-08-19)

```

  해독 ok 1,282 · empty 43 · unsupported 36 · failed 8 · container 8
  지원 포맷 모수 1,333건 중 1,282건 = 96.2%
```

- **해독률 96.2% 로 기업마당 94.6% 보다 높다.** hwp 813 · pdf 402 · hwpx 40 · docx 27
- **오류를 HTTP 200 으로 주지 않는다.** 1,377건 전부 200 + octet-stream 이라 기업마당의
  HTML 오류 페이지 함정이 없다
- 평균 612KB 로 **추정 775KB 보다 21% 작았다.** n=400 크기 표본이 큰 파일 쪽으로
  쏠렸다는 뜻이라 **전량 55.3GB 추정도 그만큼 과대일 수 있다**(다시 재면 약 44GB).
  그래도 여유 24GB 를 넘는다
- 디스크는 1.8GB → **2.5GB** 가 됐다

### T-0051 커버리지 재측정

> **보류** (2026-08-19). **전제가 바뀌었다.** 전량을 안 받기로 해서 모수가 18배가
> 아니라 41% 늘었다(3,354 → 4,731). 기업마당 94.6% 가 무효가 되는 것이 아니라
> **K-Startup 숫자를 따로 적으면 되는 일**이 됐고, 그 숫자는 T-0050 에서 이미 나왔다

> **전량을 받는 날 어차피 다시 재야 한다** — 그때 한 번에 쓴다.

- 포맷별 해독률을 다시 재고 evidence 를 새로 쓴다
- **공고 단위로도 센다** — "첨부를 하나도 못 읽는 공고"가 K-Startup 에서 몇 건인지
