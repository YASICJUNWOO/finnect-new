## 지금 상태

**코드 0줄.** 문서만 있다. 스파이크 코드(`spike/`)는 버리는 코드다.

마감은 없다. 그래서 **틀린 문서를 미리 쓰지 않는 것**이 이 계획의 원칙이다. 골격(계층 경계, 데이터 모델, API 계약)은 나중에 바꾸면 전부 뜯어야 하므로 먼저 정하고, 계층별 상세 사양(추출 스키마, 요건 표현식, 집필 프롬프트)은 **코퍼스를 보고 나서** 정한다.

근거: 이전 제품의 추출 스키마가 자립준비청년 특화 필드로 짜여 있어 타깃이 바뀌자 통째로 갈아야 했다([ADR-0009](../adr/0009-구-백엔드-재사용-보류.md)). **스키마 모양은 코퍼스가 결정한다.**

## 순서를 이렇게 잡은 이유

**판별이 집필보다 먼저다.** 집필은 판별 결과 위에서 도는데(`SPEC.md` §3), 판별 없이 집필만 만들면 어차피 나중에 배선을 다시 해야 한다.

**화면이 집필보다 먼저다.** F3·F4·F9는 L2 출력만 있으면 완성된다. 여기까지만 해도 "신청 가능한 공고를 찾아준다"는 절반의 제품이 선다. 집필은 그 위에 얹는다.

**수집이 맨 앞이다.** 실측에서 확인했듯 평가 정보는 공고 본문에 0%다. 첨부를 열지 않으면 아무것도 못 한다([ADR-0008](../adr/0008-제품-범위-확대.md)).
