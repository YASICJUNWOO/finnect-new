# ADR-0022: 첨부 원본을 콘텐츠 주소로 로컬 디스크에 두고, 해독 상태를 별도 표에 남긴다

- 상태: 채택됨
- 날짜: 2026-08-17
- 다루는 것: [ADR-0021](0021-인프라-선정을-미룬다.md)의 **A(저장소)** 일부와 **C(파서)**
- 여는 것: [plan/07](../plan/07-첨부-내려받기와-해독.md) · [T-0004](../plan/02-수집과-추출.md#t-0004-지원-포맷-목록-정의)

## 맥락

ADR-0021이 저장소와 파서를 "그것을 실제로 필요로 하는 작업에서 정한다"고 미뤘다. **T-0004가 그 작업이다.** 첨부를 내려받지 않으면 지원 포맷 목록도, 미해독 기록도 만들 수 없다.

들어가기 전에 실측한 것.

| 확인한 것 | 값 |
|---|---|
| 첨부 행 | 3,354건. **전부 기업마당이다** |
| K-Startup 첨부 | 0건. API에 필드가 없어 `AttachmentStatus.UNKNOWN` 상태다 |
| URL 유일성 | 3,354 / 3,354. 중복 없음 |
| 내려받기 | **`HEAD`는 403, `GET`은 200.** 브라우저 UA와 Referer가 필요하다 |
| 표본 1건 | `hwp` 793KB. `Content-Disposition`에 원본 파일명이 온다 |

포맷 분포는 hwp 1,502 · pdf 1,167 · hwpx 309 · zip 166 · xlsx 계열 70 · **png/jpg 121** · docx 계열 12 · pptx 7이다.

**이 중 png/jpg 121건은 어떤 파서로도 0바이트다.** 공고문 자리에 붙은 것만 62건이다. 스캔 PDF와 별개로 이미 존재하는 미해독 덩어리다.

## 결정

### 1. 원본은 로컬 디스크에 콘텐츠 주소로 둔다

```
data/attachments/<sha256[:2]>/<sha256>
```

DB에는 경로·크기·해시·상태만 남긴다. 파일 자체는 안 넣는다.

**오브젝트 스토리지를 지금 올리지 않는다.** 지금 필요한 성질은 "같은 파일을 두 번 안 받는다"와 "파서를 고치면 다시 파싱한다" 둘뿐이고, 로컬 디스크가 그걸 다 준다. 부품을 하나 늘려도 얻는 것이 없다.

**콘텐츠 주소를 쓰는 이유는 재수집 때문이다.** 공고가 갱신되면 `attachment` 행이 통째로 지워지고 다시 깔린다(`ingest/runner.py:164`). 파일 이름을 공고 ID나 첨부 ID로 지으면 그때 고아가 된다. 내용 해시로 지으면 같은 파일이 다시 와도 같은 자리다.

### 2. 해독 상태는 `attachment_file` 별도 표에 남긴다. `attachment`에 컬럼을 붙이지 않는다

같은 이유다. **`attachment`는 재수집 때 지워지고 다시 깔리는 표라 상태를 얹으면 날아간다.** URL을 키로 하는 표를 따로 두면 재수집과 무관하게 산다.

`attachment`는 API가 준 메타, `attachment_file`은 우리가 한 일이다. 저장 모델 규칙대로 둘을 섞지 않는다.

### 3. 파서는 스파이크 구현을 제품 코드로 승격한다. 라이브러리는 스파이크와 같은 것을 쓴다

| 포맷 | 방식 | 근거 |
|---|---|---|
| HWP | OLE + raw deflate + 레코드 워크 (`olefile`) | 쓸 만한 라이브러리가 없다. 스파이크가 100% |
| HWPX · DOCX | ZIP + XML 정규식 | 의존성 0. 스파이크가 100% |
| PDF | `pdfplumber` | 스파이크가 91% |
| ZIP | 안의 파일 **목록만** 읽는다. 텍스트는 안 뽑는다 | 아래 참고 |

**`pdfplumber`를 바꾸지 않는 이유가 실측 때문이다.** 추출률 95%는 이 라이브러리로 잰 값이다. 다른 것으로 갈면 그 숫자가 더는 근거가 아니게 되고, 다시 재야 한다.

`spike/`는 버리는 코드지만 **알아낸 것은 유효하다**(plan/02). 승격하면서 예외 처리와 인코딩 방어만 붙인다.

### 4. ZIP은 열되 안까지 파싱하지 않는다

166건을 그냥 "미지원"으로 적으면 **그 안에 사업계획서 양식이 몇 개 들어 있는지 영영 모른다.** 반대로 재귀 파싱을 지금 붙이면 저장 모델이 한 단계 깊어진다(ZIP 안의 파일은 `attachment` 행이 없다).

그래서 중간을 택한다. **파일 목록만 읽어 `contents`에 담는다.** ZIP 안을 실제로 풀지 말지는 그 목록을 보고 정한다.

### 5. 지원 포맷 목록은 설정에 둔다

`ATTACHMENT_FORMATS` 환경변수로 덮을 수 있다. 코드를 고치지 않고 포맷을 끄고 켤 수 있어야 한다는 것이 T-0004의 완료 조건이다.

### 6. OCR은 이 ADR이 정하지 않는다

[T-0007](../plan/02-수집과-추출.md#t-0007-스캔-pdf-처리-판단)의 몫이고, **그 결정의 근거가 이 작업의 출력이다.** 이미지 첨부와 텍스트 0바이트 PDF를 상태로 남기면 "몇 건이 OCR 없이는 안 되는가"가 숫자로 나온다. 지금 정하면 그 숫자를 안 보고 정하는 것이다.

### 7. 첨부 실행 기록 표를 만들지 않는다

[ADR-0011](0011-수집-실행-화면.md)이 `ingest_run`을 만든 이유는 **두 API가 실패를 HTTP 200으로 주기 때문**이었다. 실패가 "아무 일도 없었음"과 구분되지 않는 것이 문제였다.

여기는 그 문제가 없다. 파일마다 `http_status`·`fetch_error`·`parse_status`가 행에 남아서 실패가 스스로 보인다. 행이 곧 기록이다.

## 결과

- **`data/attachments/`가 생긴다.** 추정 2~3GB. `.gitignore`에 이미 들어 있다
- 첨부 하나가 `attachment`(메타)와 `attachment_file`(우리가 한 일) 두 행으로 갈린다. 재수집이 앞의 것만 지운다
- `pdfplumber`와 `olefile`이 `spike` 그룹에서 **주 의존성으로 올라온다**
- **포기한 것 — 여러 머신에서 못 돌린다.** 파일이 한 디스크에 있어서 워커를 분산하면 못 읽는다. ADR-0021이 예고한 "A와 B가 서로를 다시 보게 되는" 자리가 여기다. 지금은 워커가 없으므로 대가를 안 치른다
- **포기한 것 — 백업 대상이 DB 밖에 하나 더 생긴다.** 다만 전부 공개 URL에서 다시 받을 수 있어서 유실이 치명적이지 않다
- 되돌리는 조건: **처리를 한 프로세스에서 못 끝내는 것이 측정으로 확인되면**(ADR-0021 B) 그때 저장소를 오브젝트 스토리지로 옮긴다. `attachment_file.stored_path`가 그 경계라 바뀌는 코드는 `attach/store.py` 하나다

## 안 다룬 것

- **사용자가 올리는 파일**(F1-1)의 저장 위치와 격리 정책(ADR-0021 H). 공고 첨부는 공개 파일이라 격리가 안 걸린다. **둘을 같은 결정으로 묶지 않는다**
- 벡터 저장, 큐, LLM 제공자. 여전히 ADR-0021대로 각자의 작업에서 정한다
