## 1. 어휘가 넷이고 1:1이 아니다

이 구조를 처음 읽을 때 걸리는 것이 이것이다.

```
계층 (세로)                        재료 (가로 · 계층이 아니다)
────────────────────              ──────────────────────────────
SECTORS   6   구획                 SLOT_ALIASES  43  ──► 슬롯 가지로만
  ORBIT  15   MD 한 장             TOPICS        25  ──► 노드 가지로만
    SLOTS 14 / NODES 10  내용
```

`TOPICS 25` 를 세로줄에 넣으려 하면 안 맞는다. **슬롯 가지에는 topic 이 안 흐른다** —
`headcount` 는 `key="임직원"` 에서 왔지 topic 에서 오지 않았다.

`topics.py:262` 가 이 어긋남을 이미 적어 뒀다.

> `SPEC.md` F1-2 가 센 **열다섯**은 **슬롯 열넷과 다른 셈이다.** 저기는 **화면의 단위**이고
> 여기는 **병합의 단위**다.

전부 `src/finnect/wiki/topics.py` 한 파일에 있다.

| 무엇 | 이름 | 줄 | 개수 |
|---|---|---:|---:|
| 슬롯 이름 + 성질 | `SLOTS` | 73 | 14 |
| 원문 표현 → 슬롯 | `SLOT_ALIASES` | 101 | 43 |
| 노드 이름 | `NODES` | 170 | 10 |
| topic → 노드 | `TOPIC_NODE` | 189 | 23 |
| topic 목록 | `TOPICS` | 222 | 25 (**계산된다**) |
| 구획 | `SECTORS` | 289 | 6 |
| 궤도 배치 | `ORBIT` | 300 | 15 |

`TOPICS` 는 리터럴이 아니다 — `frozenset(TOPIC_NODE) | {"company_profile", "application_history"}` 다.
25개 목록을 눈으로 보려면 `TOPIC_NODE` 23줄에 그 둘을 더해야 한다.

**이 파일 밖에 사본이 없다.** 프롬프트 어휘(`extract.py:258`), 스키마 enum(`extract.py:287`),
자격 슬롯 여덟(`match/profile.py:40`), 집필 라벨(`draft/needs.py:33`), 화면 자리 이름
(`api/wiki_service.py:198`)이 전부 여기서 파생된다.

손으로 적은 부분집합이 하나 있다 — `match/profile.py:45` 의
`NEED_NODES = ("roadmap", "finance", "solution")`. **정의가 아니라 선택**이라 사본은 아니지만,
`NODES` 에서 이름을 바꾸면 여기가 조용히 안 맞는다.

## 2. 라우팅의 판별자는 `kind` 다. `key` 는 그 결정의 결과다

`merge.py:72-90` 이 전부다.

```python
def place(fact: Fact) -> Placement:
    if fact.topic == topics.UNCATEGORIZED:          # 0번 관문
        return Placement(UNCATEGORIZED, "", "온톨로지 밖 topic")

    if fact.kind == "slot":                          # ← 진짜 분기
        slot = topics.slot_of(fact.key)
        if slot is None:
            return Placement(UNCATEGORIZED, "", f"모르는 항목 이름 — {fact.key!r}")
        if not (fact.value or "").strip():
            return Placement(UNCATEGORIZED, "", f"값이 비어 있음 — {fact.key!r}")
        return Placement("slot", slot)

    node = topics.node_of(fact.topic)                # kind != "slot" 이면 전부 여기
    if node is None:
        return Placement(UNCATEGORIZED, "", f"서술 노드가 없는 topic — {fact.topic}")
    return Placement("node", node)
```

**인과가 「key 가 있어서 슬롯으로 간다」가 아니다.** `kind="slot"` 이라서 `key` 가 살아남는다 —
`extract.py:369-380` 이 `kind` 를 먼저 읽고 나머지 다섯 칸을 그걸로 게이팅한다.

```python
kind = d["kind"] if d.get("kind") in ("slot", "node") else "node"   # 기본값이 node
key       = (d.get("key")       or None) if kind == "slot" else None
value     = (d.get("value")     or None) if kind == "slot" else None
as_of     = parsed                       if kind == "slot" else None
qualifier = (d.get("qualifier") or None) if kind == "slot" else None
fact_key  = (d.get("fact_key")  or None) if kind == "node" else None
```

`kind` 는 파이프라인 여덟 자리가 읽는다 — `extract.py:93,97,376-380` · `merge.py:77,109,112` ·
`build.py:188` · `score.py:195`. **`dedupe_key` 가 `kind` 로 갈리므로**, 같은 문장이 한 번은
슬롯 한 번은 노드로 나가면 병합이 안 되고 행이 둘이 된다.

### 미분류로 가는 길이 넷이다

```
1. topic 이 TOPICS 밖            → "온톨로지 밖 topic"        (strict 스키마라 사실상 안 걸림)
2. kind="slot" · slot_of() 실패  → "모르는 항목 이름"
3. kind="slot" · value 가 빔     → "값이 비어 있음"
4. kind="node" · node_of() 실패  → "서술 노드가 없는 topic"    (company_profile · application_history)
```

## 3. LLM 이 정하는 것과 표가 정하는 것

**LLM 출력에 슬롯 이름·노드 이름을 적는 칸이 아예 없다.** 스키마 필수 칸 아홉 개 전부다.

```python
"required": ["topic", "kind", "text", "anchor",
             "fact_key", "key", "value", "as_of", "qualifier"]
```

모델은 `headcount` 라는 글자를 한 번도 안 쓴다. `임직원` 이라고 쓸 뿐이고 `headcount` 는
`place()` 가 만든다. **그래서 SLOTS·NODES 는 선택지가 아니라 계산 결과다.**

| | 정하는 주체 | 제약 |
|---|---|---|
| `kind` | **LLM** | enum `["slot","node"]` — 둘 중 자유 |
| `topic` | **LLM** | enum 25개 — **API가 막는다** |
| `key` | **LLM** | 자유 문자열. 43개는 프롬프트 힌트일 뿐 |
| 슬롯 이름 | **표** | `SLOT_ALIASES` 43 → 14 |
| 노드 이름 | **표** | `TOPIC_NODE` 23 → 10 |

### 강제력이 어디서 오나

`llm.py:120-134` 가 요청을 두 갈래로 보낸다.

```python
"input": [ {"role":"system", ...}, {"role":"user", ...} ],   # ① 자연어 지시
"text": {"format": {"type":"json_schema", "strict": True,     # ② 출력 모양 계약
                    "schema": schema}}
```

**슬롯 별칭 43개는 ①에, topic 25개는 ②에 있다.** ①은 부탁이라 어길 수 있고 ②는 계약이라
못 어긴다. 구멍 ①(아래)이 슬롯 쪽에만 생기는 이유가 이것이다.

### 노드 이름을 모델에게 안 준다

프롬프트에서 노드 관련 언급은 이 한 줄이 전부고, 표에서 생성한 것도 아니다.

```
- `node` — 서술 문장. 문제 인식·솔루션·목표 고객·시장·팀·로드맵 등
```

의도된 것이다(`topics.py:187`).

> **라벨이 세밀할수록 좋고 노드는 집필 단위와 맞아야 해서 25 → 9 로 모은다.**

`patent`·`certification`·`technology`·`development_status` 를 따로 물어야 나중에 쪼갤 수 있다.
모델에게 `솔루션과 기술` 만 보여 주면 전부 거기로 뭉뚱그린다. **접는 것은 코드가 나중에 한다** —
그래서 `TOPIC_NODE` 한 줄만 고치면 재추출 없이 노드 구조를 바꿀 수 있다.

### `key` 만 열어 둔 이유

`topics.py:99` 가 순환을 적어 뒀다.

> 코퍼스 7건에 실제로 나온 표현만 담았다. 없는 표현을 미리 넣지 않는다 —
> 새 문서에서 새 이름이 나오면 `uncategorized` 로 서고, **그때 여기 한 줄을 더한다.**

enum 으로 닫으면 모델이 `차입금` 을 억지로 `자본금` 에 넣고, **우리는 틀린 값을 얻으면서
표가 모자란다는 걸 영영 모른다.** `uncategorized` 는 실패가 아니라 표를 늘리라는 신호다.

## 4. 슬롯과 노드를 가른 이유는 위치가 아니라 병합 키다

`topics.py:8-11` 원문이다.

> 두 층으로 가른다. **병합 키가 다르기 때문이다.**
> - 정형 슬롯: 키가 (이름, 한정어, 시점). 같은 키에 값이 둘이면 **충돌**이다
> - 서술 노드: 키가 없다. 근거 청크를 쌓기만 한다

같은 MD 한 장 안에서도 규칙이 정반대다.

```
「팀 구성」
  직원 수 15         (slot)  → 다른 문서에 "직원 수 12" 가 같은 시점에 있으면 → 충돌. 묻는다
  개발 4명 영업 2명  (node)  → 다른 문서에 비슷한 문장이 있으면            → 그냥 둘 다 쌓는다
```

**컨테이너 구조로는 이걸 표현할 수 없다.** slot/node 는 「어느 절이냐」가 아니라
「중복을 어떻게 합치냐」의 이름이다.

| | 정형 슬롯 | 서술 노드 |
|---|---|---|
| 병합 키 | `slot\|이름\|한정어\|시점\|_norm(값)` | `node\|이름\|fact_key` (없으면 문장 자체) |
| 상태 | `current` / `superseded` / `conflict` | **안 붙는다** |
| 값·시점 | 있다 | 없다 |
| 자격 판정 입력 | 여덟 슬롯 | 안 쓰인다 (④ 분야 판정에만) |

`restate()`(`build.py:226`)가 슬롯 행만 훑는 것도 이 때문이다.

## 5. 층마다 바꾸는 비용이 다르다

**이것이 어휘를 넷으로 나눠 둔 대가이자 이득이다.**

```
SECTORS · ORBIT   ─── 표시 단위       고치면 → 공짜. 화면만 다시 그린다
SLOTS · NODES     ─── 병합 단위       고치면 → 재라우팅 (추출은 그대로)
TOPICS            ─── 추출 세밀도     고치면 → 전량 재추출 (LLM · 돈 · 비결정론)
SLOT_ALIASES      ─── 조회 + 프롬프트  고치면 → 프롬프트가 바뀌어 재추출
```

**재라우팅만 하는 명령이 없다.** 별칭 한 줄을 더해도 `--rebuild` 로 추출부터 다시 해야 하고,
추출이 비결정론이라 위키가 흔들린다(같은 회사를 두 번 세워 **166건 대 187건**).
표를 처음부터 넉넉히 두는 편이 싼 이유다.

report.slots = len({p for k, p in counts if k == WikiPlace.SLOT})        # 자리 수 ≤14

## 8. 도면이 잡은 구멍 중 코드로 재현한 것

`slot_of()` 는 정확 일치 dict 조회다(`topics.py:233`). 연속 공백을 한 칸으로 줄이기만 하고
지우지는 않는다.

```
      '임직원' -> headcount        '직원'   -> None  ← uncategorized
    '상시 근로자' -> headcount        '근로자' -> None  ← uncategorized
     '종업원 수' -> headcount        '종업원' -> None  ← uncategorized
      '직원 수' -> headcount        '인원'   -> None  ← uncategorized
      '구성원' -> headcount        '고용인원' -> None  ← uncategorized

    '본점소재지' -> location        '본점 소재지' -> None  ← 반대 방향도 있다
```

**표 자체가 표기가 섞여 있어 어느 쪽으로 와도 절반이 빗나간다.**
`merge._norm()` 은 이미 공백을 전부 지우므로 같은 정규화를 쓰면 된다.

### 이게 왜 아픈가

§3의 순환이 도는 전제는 **「미분류 = 표에 없는 새 말」** 인데, 띄어쓰기에서 빗나가면
**표에 이미 있는 말도 미분류로 온다.** 사람이 검토 큐에서 `상시근로자` 를 보고 새 표현인 줄
알고 한 줄을 더한다. 표가 중복으로 부풀고 진짜 새 어휘가 그 잡음에 묻힌다.

### 별칭 하나가 자격 판정을 살린다

다시로 문서 넷이 직원 수를 다른 말로 쓴다.

```
상시 근로자   7   2025-08-22
종업원 수     8   2025-11-30
구성원       10   2026-01-31   ← 자격 판정이 실제로 쓴 값
임직원       15   2026-08-31   ← 미래 날짜라 _pick 이 안 쓴다
```

`match/profile.py:148` 이 `as_of <= on` 인 것 중 최신을 고른다. **표에 `임직원` 하나만 있었다면
남는 게 미래 날짜 하나뿐이라 직원 수 조건이 붙은 공고를 아예 판정하지 못한다.**
