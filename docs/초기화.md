# 초기화 — 개발용 코퍼스를 작게 세운다

기업마당 **97건** · K-Startup **138건**. 전부 합쳐 12분이다.

> 두 출처를 전량으로 세우는 절차는 [`dataset.md`](dataset.md) 에 있다.
> 저기가 정본이고 **여기는 그 절차의 좁은 경로다** — 어긋나면 `dataset.md` 가 이긴다.

## 흐름 — 출처마다 칸이 하나 다르다

```
기업마당    목록 ─────────────→ 필터 ─→ 표본 ─→ 첨부 받기
            1,512              548     97
           (요청 1회)

K-Startup   목록 ─→ 직접 읽기 ─→ 필터 ─→ 표본 ─→ 첨부 받기
           29,863   1,000건만    503     138
                    (--limit)
```

**K-Startup 에만 「직접 읽기」가 있다.** 목록 API 가 첨부를 안 주고 상세 API 도
없어서, 공고마다 `detl_pg_url` 을 열어 HTML 에서 파일명을 긁어야 한다. 기업마당은
첨부가 목록 응답에 같이 와서 이 칸이 아예 없다.

**읽기가 필터보다 앞이다.** 필터의 축 여섯 중 축2d′ 가 첨부 파일명을 본다 —
「교육·행사·멘토링·융자·인력」 분야를 빼되 **양식이 첨부돼 있으면 살린다.**
읽기를 뒤로 돌리면 그 구제가 안 돌아 통과분의 3%쯤이 억울하게 빠진다.

**표본이 첨부 받기 앞이다.** 뒤에 두면 받아 놓고 버린다.

## 이미 찬 DB 에서는 1~3 을 건너뛴다

**이 문서는 빈 DB 를 전제한다.** 아래 «예상» 표가 잰 「지우기」도 공고 1,051건 ·
첨부 1.27GB 에서 잰 값이라, 전량이 들어 있는 DB 에 그대로 대면 **이미 지불한 것을
버린다.**

2026-08-24 실측 — 이 레포의 로컬 DB 상태다.

| | 이 DB | 이 문서의 3단계가 만드는 것 |
|---|---:|---:|
| K-Startup 중 첨부 목록을 읽어 둔 공고 | **27,565** | ~965 (`--limit 1000`) |
| `attachment` 행 | 70,654 | 2,660 |
| 내려받아 해독한 파일 | 4,731 | 671 |
| 첨부 원본 디스크 | **2,505 MB** | — |

3단계는 전량이 100분이라 문서가 1,000건으로 좁혔는데, **여기는 그 100분이 이미
지불돼 있다.** `--purge` 를 돌리면 27,565건의 읽기와 2.5GB 를 버리고 3.6분만 다시
채운다. 그래서 이 상태에서는 **0 → 4** 로 간다.

```
0. --dump      한다.  5단계가 라이브에 없는 기업마당 공고를 지운다 — 아래 함정 넷째
1. --purge     건너뛴다
2. ingest      건너뛴다
3. --scrape    건너뛴다.  조건은 `attachment` 행이 이미 있는 것이다 — 아래 함정 둘째
4. 목록 만들기   여기서 시작한다
```

**대신 `--demo` 를 다시 골라야 한다.** 표본 235건은 「1,000건만 읽었을 때」의 산물이다.
더 읽어도 **접수중은 안 늘고**(2026-08-24 실측 — 27,565건 중 모집중 **262**건이고
문서가 1,000건에서 관측한 263과 사실상 같다) 마감 후보만 늘어서, `demo_pick` 의
`% N` 이 고르는 몫이 커진다. `--demo 120` 을 그대로 쓰면 138건보다 크게 나온다.

## 절차

### 0. 뜬다 — **파일 이름을 바꾼다**

```bash
uv run python -m finnect.dataset --dump out/백업-YYYY-MM-DD.jsonl
```

**`out/공고-백업.jsonl` 을 덮으면 안 된다.** 2026-08-22 09:10Z 덤프이고 기업마당
**1,538건**이 들어 있는데, 그중 26건은 이미 라이브 API 에서 사라져 **그 파일에만
있다.** 기업마당 공고는 마감되면 API 에서 없어지고 재수집으로 복구되지 않는다
([근거](../notice-filter/로직과근거.md) §12). `.gitignore` 라 레포에도 없다.

K-Startup 은 마감돼도 목록 API 에 남아서 언제든 다시 받는다.

### 1. 지운다

```bash
uv run python -m finnect.dataset --purge          # 센다. 안 지운다
uv run python -m finnect.dataset --purge --yes    # 지운다
```

공고 2표 · `attachment` · `attachment_file` · `notice_profile` · `notice_fit` 과
**첨부 원본 디렉터리를 통째로** 비운다. `document`·`draft`·`wiki_*` 는 안 건드린다.

### 2. 목록을 받는다 — 전량이다

```bash
uv run python -m finnect.ingest --source bizinfo --full     # 1,512건 · 요청 1회 · 5초
uv run python -m finnect.ingest --source kstartup --full    # 29,863건 · 150회 · 2분
```

**`--full` 이 빠지면 안 된다.** `finnect.ingest` 기본값이 2026-08-24 부터 필터링된
수집이다(K-Startup 모집중만 · 기업마당 중분류 스무 개 제외) — 여기서 그걸 쓰면 4·5단계가
좁힐 재료를 미리 잃는다.

**수집에 필터를 안 건다.** 기업마당은 요청이 1회라 걸어도 안 빨라지고, K-Startup 은
페이징이라 149회를 다 돌아야 전체를 본다. 좁히는 것은 4·5단계다.

`--limit` 을 쓰지 않는다 — 잘린 것을 정본으로 삼으면 뒤 단계가 무엇을 못 본 건지
모른다.

### 3. K-Startup 만 — 직접 읽는다

```bash
uv run python -m finnect.attach --scrape-kstartup --limit 1000
```

**`--limit` 이 여기서 표본 노릇을 한다.** 전량 29,863건을 열면 100분인데 1,000건이면
2.9분이다(0.18초/건).

**1,000건이 임의의 수가 아니다.** 읽는 순서가 `rcrt_prgs_yn DESC` 라 **모집중을 먼저
연다**(`attach/kstartup.py` `_targets`). 모집중이 원래 263건쯤이라 1,000건 안에서 다
끝나고 마감으로 넘어간다 — **더 열어도 접수중은 안 늘고 마감 공고만 늘어난다.**

파일은 안 받는다. 디스크를 안 쓴다.

### 4. 고른다 — 목록 파일을 만든다

**기업마당** — 라이브 API 를 다시 부른다.

```bash
cd notice-filter
BIZINFO_API_KEY=$(grep '^BIZINFO_API_KEY=' ../.env | cut -d= -f2-) \
  python3 run.py --no-serve --ids ../out/bizinfo-남길.txt
cd ..
```

`run.py` 는 **우리 DB 를 안 본다.** `.env` 도 안 읽으므로(의존성 0이 설계다) 키를
환경변수로 넘긴다. **`filter.py --ids` 가 아니다** — 저건 규칙 모듈이라 `--test` 뿐이다.

**K-Startup** — 우리 DB 를 덤프해서 넣는다. `notice-filter` 는 DB 를 모른다.

```bash
docker exec finnect-db psql -U finnect -d finnect -t -A -c "
SELECT COALESCE(json_agg(json_build_object(
  'notice', json_build_object(
    'pbanc_sn', k.pbanc_sn, 'biz_pbanc_nm', k.biz_pbanc_nm,
    'aply_trgt_ctnt', k.aply_trgt_ctnt, 'supt_biz_clsfc', k.supt_biz_clsfc,
    'biz_enyy', k.biz_enyy, 'pbanc_ctnt', k.pbanc_ctnt,
    'derived_apply_end', k.derived_apply_end),
  'attachments', COALESCE((SELECT json_agg(json_build_object(
      'filename', a.filename, 'ext', a.ext, 'url', a.url))
    FROM attachment a WHERE a.source='kstartup' AND a.external_id=k.pbanc_sn), '[]'::json)
)), '[]'::json) FROM kstartup_notice k
WHERE EXISTS (SELECT 1 FROM attachment a
              WHERE a.source='kstartup' AND a.external_id=k.pbanc_sn);" \
  > out/kstartup-덤프.json

cd notice-filter
python3 kstartup.py --json ../out/kstartup-덤프.json \
  --demo 120 --today $(date +%F) --read-only \
  --ids ../out/kstartup-남길.txt --urls ../out/kstartup-받을것.txt
cd ..
```

**`WHERE EXISTS` 가 3단계에서 읽은 것만 넘긴다.** 안 읽은 공고는 첨부가 `[]` 라
축2d′ 구제가 못 돌아 과배제된다.

**`--today` 를 빼면 표본이 안 걸린다.** `is_open()` 이 `end >= today` 인데 기본값이
빈 문자열이라 **날짜가 있는 공고가 전부 접수중이 된다** — 실측 501/503 이 통과했다.
날짜 형식은 `2026-08-22` 다(`derived_apply_end` 가 `date` 컬럼이라 대시가 붙는다).

### 5. 솎는다 — 표본이 여기서 확정된다

```bash
uv run python -m finnect.dataset --prune out/bizinfo-남길.txt  --source bizinfo  --sample 5
uv run python -m finnect.dataset --prune out/kstartup-남길.txt --source kstartup
```

숫자를 보고 `--yes` 를 붙인다.

**표본을 뜨는 자리가 출처마다 다르다.** 기업마당은 `--sample 5`(`--prune` 이 뜬다)이고
K-Startup 은 `--demo`(`kstartup.py` 가 이미 떴다)라 `--sample` 이 없다. 아래
«표본을 왜 다르게 뜨나» 참조.

`--source` 가 필수인 이유는 두 출처의 공고번호가 같은 자릿수라서다.

### 6. 첨부를 받는다

```bash
uv run python -m finnect.attach --source bizinfo
uv run python -m finnect.attach --only out/kstartup-받을것.txt --source kstartup
```

K-Startup 은 URL 목록으로 좁힌다. `--read-only` 가 만든 목록이라 지금 한 글자도 못
읽는 jpg·png 가 빠져 있다(첨부 OCR 은 꺼져 있다).

**여기까지가 코퍼스다.** 아래 «예상 — 총 12분» 이 재는 것도 여기까지다.

### 7. 뽑는다 — 여기부터 LLM 이다

6단계는 글자를 얻는 데까지이고 7단계가 판정이다. **`OPENAI_API_KEY` 가 있어야 돈다**
— 없으면 무엇이 없는지 말하고 멈춘다(ADR-0037). 조용히 규칙으로 안 물러난다.

```bash
uv run python -m finnect.extract                     # ① 구간 자르기 + 칸 항목 · LLM 0회
uv run python -m finnect.extract --classify          # ② 구간 종류 + 서술형 항목 트리 (LLM)
uv run python -m finnect.match --normalize           # ③ 공고 정규화 (LLM)
uv run python -m finnect.draft --read-forms          # ④ 양식 읽기 (LLM)
uv run python -m finnect.match --company c_dasiro    # ⑤ 자격 → 분야 → 추천 3건 · LLM 0회
```

**순서 제약은 둘뿐이다.** ④가 ②에 매여 있고(`narrative` 구간이 있어야 모수가 생긴다)
⑤가 ③에 매여 있다(`notice_profile` 이 비면 전부 `확인 필요` 로 남는다). ①②와 ③은
서로를 모르므로 **③을 먼저 돌려도 된다** — 2~3분이라 결과를 빨리 보는 쪽이 낫다.

**초안은 이 줄에 없다.** `--notice` 가 필수라 ⑤ 추천을 보고 공고를 고른다.

```bash
uv run python -m finnect.draft --company c_dasiro --notice bizinfo:<공고번호>
```

#### 얼마나 드나

2026-08-22 이 문서의 6단계까지 돌린 코퍼스(공고 235 · 첨부 고유 sha 2,204)에 대고 잰 값이다.

| | 호출 | 입력 토큰 | 비용 | 시간 |
|---|---:|---:|---:|---:|
| ① `extract` | 0 | — | **0** | 1~2분 |
| ② `--classify` | **3,112** | **6.08M** | ~$1.4 | **1.5~3시간** |
| ③ `--normalize` | **234** | — | ~180원 | 2~3분 |
| ④ `--read-forms` | ②가 끝나야 안다 | — | — | — |
| ⑤ `--company` | 0 | — | **0** | 1초 |

**호출 수와 입력 토큰은 실측이다.** 구간은 실제 텍스트를 `segment.split()` 으로 쪼개
셌고(구간 4,304 · 규칙이 가른 `fields` 902 · `unknown` 3,402 · 표지뿐이라 안 묻는 것
290), 토큰은 `SYSTEM` 788 + 표본 400개 평균 1,167(o200k_base)이다.

**비용의 출력 쪽과 시간은 추정이다.** `reason` 한 문장을 60토큰으로 잡았는데 `llm.py`
가 `reasoning` 을 안 넘겨서 API 기본값이 붙는다 — 추론 토큰이 출력으로 과금되면 총액이
$3~4 로 간다. **재는 법은 이미 있다:**

```bash
uv run python -m finnect.extract --classify 40 --dry   # 40회 · 약 $0.02 · DB 는 안 건드린다
```

`--dry` 도 LLM 은 부르고 `Usage.line()` 이 진짜 입출력 토큰을 찍는다. **×78 하면 전량이다.**

**프롬프트 캐싱은 안 걸린다.** 공통 접두사가 `SYSTEM` 788토큰뿐이라 OpenAI 최소치
1,024 아래다. ADR-0037 이 "7,717 구간 돌릴 때 잰다" 로 미뤄 둔 항목인데, 지금
프롬프트로는 답이 **안 걸린다** 이다.

## 표본을 왜 다르게 뜨나

**K-Startup 에 균등 표본을 쓰면 화면이 빈다.** 필터 통과 503건 중 접수중이 137건뿐이라
`% N` 으로 고르면 접수중이 같이 잘린다. 제품 목록은 마감 공고를 빼므로(`open_only=True`)
잘린 만큼이 그대로 화면에서 사라진다.

2026-08-22 실측 — 503건에 대고 잰 값이다.

| 방식 | 남는 공고 | 접수중 | 계획서 양식 | 접수중이면서 양식 |
|---|---:|---:|---:|---:|
| 전부 | 503 | 137 | 135 | 23 |
| `--sample 5` (균등) | 94 | **0** | 28 | **0** |
| `--sample 4` (균등) | 143 | **1** | 41 | **0** |
| `--demo 12` | 175 | 137 | 35 | 23 |
| `--demo 20` | 150 | 137 | 28 | 23 |
| **`--demo 120`** | **138** | **137** | **23** | **23** |

`demo_pick` 이 **접수중을 나눗수와 무관하게 전부 넣고** 나머지에서 `% N` 을 고른다.
그래서 **137이 하한이고 100건은 안 된다** — 100으로 맞추려면 화면에 뜰 공고를
버려야 한다.

기업마당에는 이 문제가 없다. 필터 ⑫가 마감을 이미 빼서 통과분 548건이 전부
접수중이거나 「예산 소진시까지」류다.

**「접수중이면서 양식 있는 것」 23건이 천장이다.** 화면에서 골라 들어가 초안까지
쓸 수 있는 K-Startup 공고가 그만큼이고, **표본을 어떻게 떠도 안 늘어난다.**
나머지 양식 112건은 마감 공고에 붙어 있어 화면엔 안 뜨지만 집필 재료로는 쓴다
(`draft --notice` 로 직접 지정).

## 예상 — 총 12분

2026-08-22 실측 — 이 문서의 명령을 그대로 돌린 결과다. **6단계까지다** — 7단계는
위 «얼마나 드나» 에 따로 있고 거기가 훨씬 길다.

| 단계 | | 시간 |
|---|---|---:|
| 지우기 | 공고 1,051 · 첨부 원본 1.27GB | 5초 |
| 목록 받기 | 기업마당 **1,512** · K-Startup **29,863** | 2분 |
| 직접 읽기 | 1,000건 → 첨부 있음 **965건 · 2,660개** | 3.6분 |
| 필터 | 1,512 → **548** · 965 → **503** | 20초 |
| 솎기 | 548 → **97** · 503 → **138** | 10초 |
| 첨부 받기 | 671개 중 목록에 든 것 | 6분 |

최종 **공고 235건**(기업마당 97 · K-Startup 138) · 첨부 메타 671개.
화면에 뜨는 것은 **234건**(기업마당 97 전부 + K-Startup 137).

**직접 읽기는 결정론이다.** 같은 코퍼스에 두 번 돌려 965건 · 2,660개가 바이트로
같았다 — `_targets` 의 정렬(`rcrt_prgs_yn DESC, pbanc_sn DESC`)에 무작위가 없다.

## 함정

- **`--today` 없이 `--demo` 를 쓰면 표본이 안 걸린다.** 위 4단계 참조
- **3단계를 건너뛰면 K-Startup 이 과배제된다.** 축2d′ 구제가 `attachment` 의
  `filename`·`ext` 만 보는데 첨부 행이 없으면 한 건도 안 돈다. **막는 것은 3단계를
  돌린 사실이 아니라 `attachment` 행이다** — 이미 긁어 둔 DB 에서는 다시 긁을 필요가
  없다(위 «이미 찬 DB 에서는 1~3 을 건너뛴다»)
- **빈 목록 파일로 솎으면 전량 삭제다.** `read_list` 가 한 줄도 없으면 거절하지만
  **필터가 0건을 낸 목록은 거절 못 한다** — 5단계 미리보기 숫자를 본다
- **라이브와 DB 가 어긋나면 그 차이가 지워진다.** 4단계가 기업마당 라이브를 부르므로
  2단계 이후 마감된 공고는 목록에 없어 5단계가 지운다. 08-22 에는 둘 다 1,512 였다
- **기업마당 공고번호는 숫자가 아니다.** `PBLN_000000000103611` 이라 `bucket()` 이
  sha256 경로를 탄다. 결정론이라 몇 번을 돌려도 같은 97건이 서지만 **눈으로 검산이
  안 된다** — `dataset/sample.py` 가 숫자 경로를 먼저 둔 이유가 그 검산이었고,
  그 docstring 은 「`pblancId` 가 숫자다 · 이 경로를 타는 값은 없다」로 **틀리게
  적혀 있다**
- **솎기가 2026-08-22 전에는 이 규모에서 죽었다.** `dataset/service.py` 가
  `tuple_(source, external_id).in_([2만개])` 로 복합 IN 을 만들어 Postgres 의
  `max_stack_depth` 를 넘겼다. 열 하나짜리 IN 으로 바꾸고 2,000개씩 쪼개 고쳤다
- **`sn` 이 공고번호가 아니다.** `filter.py` 가 내는 `sn` 은 화면용 뒤 6자리이고
  DB 키는 `pblancId` 다. `--ids` 가 그것을 쓴다
- **배포 DB 에 이 절차를 쓰지 않는다.** `dataset` CLI 는 로컬 DB 를 본다
- **`extract --classify` 는 진행 로그가 없다.** `service.py:250` 의 `print` 가
  `if dry:` 안에만 있어서, 안 죽었다는 것 말고는 몇 시간 동안 아무것도 안 나온다.
  **다른 창에서 `document` 를 세도 안 보인다** — 커밋이 끝에 한 번뿐이라 그 세션에는
  0 이다. 살아 있는지 보는 길은 Langfuse 하나다(`trace.py` 가 호출마다 보낸다)
- **`extract --classify` 는 죽으면 통째로 날아간다.** `classify_unknown()` 의
  `s.commit()` 이 루프 밖이고 `clf.classify()` 의 `LlmError` 를 안 잡는다 —
  3,000회를 돌고 죽으면 롤백이다. `match/service.py` 는 같은 버그를 `_COMMIT_EVERY = 50`
  으로 이미 고쳤는데(2026-08-20) `extract` 로 안 넘어왔다. 코드를 안 고치고 넘기려면
  `--classify 400` 을 여덟 번 돌린다 — **호출마다 제 몫을 커밋한다.** 대신 모델이
  `unclear` 로 답한 구간은 `unknown` 으로 남고 정렬이 `(sha256, seq)` 고정이라
  **다음 회차 앞머리에 다시 선다**
- **`extract --classify` 만 직렬이다.** `match --normalize`(`match_workers=8`)와
  `draft`(`draft_workers=8`)는 병렬인데 여기만 평범한 for 루프다. 3,112회가 한 줄로
  서는 것이 1.5~3시간의 정체다
