# ADR-0030: OCR 은 RapidOCR 로컬로 하고, 검출 모델은 `server` 를 쓴다

- 상태: 채택됨
- 날짜: 2026-08-18
- 채우는 것: [ADR-0021](0021-인프라-선정을-미룬다.md)이 미룬 **C(HWP 파서 · OCR · 표 추출)** 중 OCR
- 닫는 것: [T-0007](../plan/00-미결-해소.md#t-0007-스캔-pdf-처리-판단) 스캔 PDF 처리 판단 · [plan/12](../plan/12-사업-위키-구축.md) T-0042
- 근거: [2026-08-18 OCR 엔진 실측](evidence/2026-08-18-OCR-엔진-실측.md) — **눈으로 본 것은 7건이다**
- 관련: [ADR-0029](0029-사용자-파일을-회사-단위-콘텐츠-주소로-로컬에-둔다.md)

## 맥락

**OCR 로 가는 것은 이미 정해져 있었다.** 남은 것은 엔진과 범위다([T-0007](../plan/00-미결-해소.md#t-0007-스캔-pdf-처리-판단)).

두 곳에서 필요하다.

1. **사업자등록증.** 거의 사진이고, **위키의 정형 슬롯 다섯 중 넷이 여기서 나온다.** 그 넷이 M1 자격 판별의 입력이다
2. **공고 첨부 158건.** 텍스트 레이어가 0자다. [실측](evidence/2026-08-17-첨부-해독-실측.md)이 **그중 34건은 그 공고의 유일한 근거**라고 적었다

그리고 [ADR-0029](0029-사용자-파일을-회사-단위-콘텐츠-주소로-로컬에-둔다.md)가 제약을 하나 걸어 뒀다 — 사용자 파일을 로컬에 두기로 한 이유가 "개인정보를 외부로 내보내는 문을 데이터 0건에서 열지 않는다"였다. **클라우드 OCR 은 그 문을 여는 것과 같다.**

## 결정

### 1. RapidOCR 을 쓴다

PaddleOCR 모델을 ONNX 로 옮긴 것이다.

| | |
|---|---|
| **로컬이다** | ADR-0029 를 안 어긴다. 사업자등록증과 재무제표가 밖으로 안 나간다 |
| **가볍다** | `onnxruntime` 하나면 된다. PaddlePaddle 프레임워크가 필요 없다 |
| **한국어 전용 인식 모델이 있다** | `korean_PP-OCRv5_rec_mobile`. 중국어 모델로 한글을 읽는 것이 아니다 |

**클라우드 API(Google · Naver Clova)를 안 쓴다.** 정확도로는 앞설 것이나 ADR-0029 와 정면으로 부딪히고, 그 결정을 뒤집을 근거가 아직 없다. **Tesseract 도 안 쓴다** — 한국어와 표에 약하다.

### 2. 검출 모델은 `server` 다. 기본값을 쓰지 않는다

**이 한 줄이 실측의 핵심이다.**

| 검출 | 사업자등록증 정형 슬롯 | 1쪽 |
|---|---|---|
| PP-OCRv6 `small` (기본값) | **5/8** — **소재지·업종이 아예 안 나온다** | 3.6초 |
| PP-OCRv5 `mobile` | 5/8 | 3.1초 |
| **PP-OCRv5 `server`** | **7/8** | **13.7초** |

**소재지와 업종은 자격 판별의 입력이라 없으면 안 된다.** 지역 요건과 업종 요건이 거기서 나온다. 5배 느린 것을 받는다 — 사용자가 올리는 파일은 몇 장이고, 사람이 기다리는 구간은 F1-1-9 진행 표시가 덮는다.

**해상도와 임계값은 답이 아니었다.** 200 → 300dpi 는 차이가 없었고 `box_thresh` 완화는 오히려 나빠졌다(4/8).

### 3. 인식과 검출을 둘 다 PP-OCRv5 로 맞춘다

`Rec.lang_type="korean"` 만 주면 터진다 — 기본 검출이 PP-OCRv6 이고 **그 버전에 한국어 인식 모델이 없다.** 그리고 값은 문자열이 아니라 **Enum** 이어야 한다.

### 4. OCR 은 기본으로 안 돈다. 부를 때만 돈다

`extract.parse()` 의 계약을 바꾸지 않는다. 텍스트 레이어를 읽는 것과 그림에서 글자를 찾는 것은 **비용이 세 자릿수 배 다르다**(밀리초 대 십수 초).

| 어디 | 언제 |
|---|---|
| **사용자 파일** | 기본으로 켠다. 사업자등록증이 반드시 오고 몇 장뿐이다 |
| **공고 첨부** | **기본으로 끈다.** 켜는 것은 따로 결정한다 — 아래 |

### 5. 라벨을 OCR 로 읽지 않는다. 패턴으로 슬롯을 정한다

실측에서 **라벨은 거의 다 깨지고 값은 정확했다.** `법 인 등 록 번 호` 가 `후눌을` 로 나오는데 `110111-8842301` 은 정확하다. 자간을 넓힌 글자에서 무너진다.

사업자등록증은 **양식이 고정이다.** 라벨을 읽을 이유가 없다.

```
\d{3}-\d{2}-\d{5}   → 사업자등록번호
\d{6}-\d{7}         → 법인등록번호
'주식회사' 포함      → 법인명
행정구역으로 시작    → 소재지
```

**패턴 매칭이 라벨 OCR 보다 견고하다.** 이 원칙은 사업자등록증 밖으로 넓히지 않는다 — 고정 양식에서만 성립한다.

### 6. OCR 텍스트로 제목에 기대는 규칙을 만들지 않는다

굵은 서체와 장식 글자가 깨진다 — `름눌을` `H거3` `융기공Yㅇ`. 본문은 쓸 만하고 제목은 못 믿는다. **표 구조도 안 나온다**(양산시 건이 74줄에 301자, 줄당 4자).

## 결과

- **첨부 158건은 이 결정으로 열렸지만 이 결정이 실행하지는 않는다.** 켜면 [plan/07](../plan/07-첨부-내려받기와-해독.md)이 측정한 2,827/3,354 를 다시 재야 하고, 실측이 총 쪽수를 안 세서 **비용을 모른다.** 별 작업으로 남긴다 — **34건의 유일한 근거가 거기 걸려 있다**
- **의존성이 셋 는다.** `rapidocr` · `onnxruntime` · `pypdfium2`. **`requirements.txt` 에 넣지 않는다** — 배포본은 읽기 경로뿐이고([ADR-0026](0026-읽기-경로만-vercel에-올린다.md)) 서버리스 함수에 ONNX 런타임을 실을 이유가 없다. 임포트는 함수 안에서 한다
- **모델을 처음 쓸 때 내려받는다.** 첫 실행에 네트워크가 필요하고, 그 뒤로는 캐시된다. **오프라인 실행이 첫 회에는 안 된다**
- **정확도를 숫자로 약속하지 않는다.** 정답 텍스트가 없어 못 쟀다. 모델이 매긴 신뢰도(0.83~0.96)는 자기 채점이라 근거로 쓰지 않는다
- **되돌리는 조건: 한국어 정확도가 실사용에서 부족하다고 확인되면** 클라우드 OCR 을 다시 본다. 그때는 ADR-0029 의 "개인정보를 밖으로 안 낸다"를 같이 뒤집어야 하므로 **두 ADR 을 한꺼번에 고친다**
- **포기한 것 — 표를 못 읽는다.** 재무제표가 사진으로 오면 연도-항목-값 대응이 안 나온다. `RapidTable` 같은 표 인식을 붙일지는 그런 파일이 실제로 올 때 정한다
