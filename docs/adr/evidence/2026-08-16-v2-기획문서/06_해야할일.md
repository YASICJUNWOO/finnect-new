# 06_해야할일

> 시연 전에 손볼 것, 백엔드에서 만들어야 할 것, 조사가 필요한 것을 모았다.
> 기능 단위로 무엇이 되고 안 되는지는 `04_구현현황.md` 3장에 있다.
> 기준 2026-08-16. 데모는 화면이 다 이어지지만 **생성과 판별은 전부 목업이다.**
>
> **순위는 기획이 보기에 그렇다는 것이고 확정이 아니다.** 실제로 해 보면 순서가 달라질 수 있으니 판단해서 정하면 된다.

---

## 1. 시연 전에 고쳐야 하는 것

누르면 아무 일도 없어서 시연 중 사고가 나는 것들이다.

| | 어디 | 무엇 |
|---|------|------|
| 1 | 위키 노드 패널 | **직접 수정**과 **원본 열기** 버튼이 죽어 있다 |
| 2 | 문서 화면 | **직접 수정** 버튼이 죽어 있다 |
| 3 | 위키 정리 패널 | **전체 정리 제안 보기**가 죽어 있다 |
| 4 | 공고 상세 | **저장**은 동작하나 저장됐다는 표시가 약하다 |
| 5 | 상단 영역 | **알림 아이콘과 위키 동기화 문구**는 장식이다. 눌러도 아무 일도 없다 |

버튼을 빼든 동작시키든 정하면 된다. 시연 동선에서 누르지 않을 것이면 빼는 편이 안전하다.

## 2. 백엔드

| 무엇 | 왜 필요한가 |
|------|-------------|
| **첨부 문서 파싱** | 배점·양식·항목별 지침·제약이 전부 공고 첨부 HWP 안에 있다. 이게 안 되면 문서 생성의 근거가 없다 |
| **파일에서 위키 노드 추출** | 온보딩이 지금 파일명만 읽고 내용은 안 읽는다 |
| **자격 판별** | v1에서 만든 룰엔진이 v2 코드에 안 넘어왔다 |
| **공고 취지 추출과 적합도 계산** | 적합도가 지금 상수다 |
| **문서 생성** | 본문이 고정돼 있어 값을 바꿔 보여줄 수 없다 |
| 공고 수집과 정규화 | 사이트마다 구조가 다르다. 대상 개수는 미정 |

기획이 보기에는 **첨부 파싱이 가장 앞에 걸린다.** 나머지 대부분이 여기서 나오는 데이터를 쓴다. 다만 파싱이 얼마나 어려운지에 따라 순서를 다시 짜야 할 수도 있어서, 먼저 가능성을 보고 판단하는 편이 나을 것 같다.

의존 관계만 적어 두면 이렇다.

```
첨부 파싱 ─┬─▶ 배점·지침 ──▶ 문서 생성
           └─▶ 자격 요건 ──▶ 자격 판별 ──▶ 추천
공고 취지 ─────────────────▶ 적합도 ────▶ 추천
파일 추출 ─────────────────▶ 위키 ──┬──▶ 적합도
                                     └──▶ 문서 생성
```

상세는 `03_데이터모델.md` 10장.

## 3. 조사 과제

`../internal/02_회의록_시연피드백.md` 9장에서 옮겼다. 멘토가 지시한 것들이다.

| 무엇 | 방법 | 왜 |
|------|------|-----|
| **연간 공고 건수와 지역 분포** | K-Startup과 기업마당의 1년치 공고 수를 센다. 기초지자체 사례를 확인한다 | 멘토가 시장 규모를 잡는 방법으로 직접 지시했다. 심사에 시장·수익성 20점이 새로 생겼다 |
| 초기 창업자 대상 사업의 비중 | 위 공고를 업력 요건으로 갈라 센다 | 멘토가 "초기 지원 사업이 더 많을 것 같다"고 했다 |
| **신청 API 실재 여부** | K-Startup 등에 신청 연동 API가 있는지 | 확인 없이 안 된다고 단정했던 부분이다 |
| HWP 파싱 가능성 | 라이브러리와 정확도 | 2장 1번의 전제 |
| 절세와 세금 감면 영역 | 창업기업 세액감면, 지방세 감면의 종류와 규모 | 확장성 항목에 쓴다 |
