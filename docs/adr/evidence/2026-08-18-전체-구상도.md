## 1. 사용자 파일 → LLM Wiki

단계 아홉이다.

| # | 단계 | 도면이 적은 것 |
|---|------|---------------|
| ① | 파일 업로드 | 지원 파일 PDF · DOCX · XLSX · PPTX · 이미지 · TXT 등. `company_id` 부여. **HWP 가 목록에 없다** |
| ② | 파싱 / 전처리 | 텍스트 추출 · 표/숫자 파싱 · OCR(이미지) · 메타데이터 추출. **위치/출처 보존.** 텍스트 문서와 표·숫자 문서로 갈라 구조화 파싱 |
| ③ | Chunking | 의미 단위 분할 · 문서 구조 보존 · 위치(페이지/섹션/행) · 출처 위치 보존 |
| ④ | LLM Fact Extraction | 사실(Fact) 추출 · 고정 topic 분류 · series 결정(엔티티/이벤트) · **confidence 부여**. `topic은 온톨로지에서 선택 (자유 생성 금지)` |
| ⑤ | topic 기반 라우팅 / 통합 | topic → 목적지 노드 결정(온톨로지) · 엔티티는 기존 값과 비교/병합(Upsert) · 이벤트는 날짜 부착 후 Append · uncategorized → review 큐. `결정론적 라우팅` |
| ⑥ | Wiki 문서 생성 / 갱신 + Source 연결 | 주제별 Markdown 생성/갱신 · 변경 이력/버전 관리 · 모든 사실에 출처 연결. `Wiki = 통합된 지식` |
| ⑦ | 저장 — Node Store | 엔티티 노드(정형 데이터) → SQL 조회 |
| ⑧ | Embedding | 의미 분할 후 임베딩 생성 (Embeddings + Metadata) |
| ⑨ | Vector DB | **Wiki Chunk** + Embeddings + Metadata (`company_id` 파티션) |

### LLM Wiki 구조 (Business Wiki)

폴더 여덟이고 그 안이 `.md` 파일이다.

| 폴더 | 종류 | 파일 |
|---|---|---|
| Company | 엔티티 | 회사 소개.md · 비전.md · 팀.md · … |
| Product / Service | 엔티티, 인스턴스 가변 | `service-A/` 소개.md · 기능.md · 차별점.md   `service-B/` … |
| Market | 엔티티 | 시장 현황.md · 시장 규모.md · 트렌드.md · 경쟁사.md |
| Customer | 엔티티 | 타겟 고객.md · 고객 문제.md · 고객 인터뷰.md |
| Business Model | 엔티티 | 수익 모델.md · 가격 정책.md · 판매 전략.md |
| Strategy | 엔티티 | 사업 목표.md · 마케팅 계획.md · 추진 계획.md |
| Financial | 엔티티, 시계열 | 매출.md · 비용.md · 자금계획.md |
| Custom | 엔티티, 인스턴스 가변 | `특허/` `인증/` `기술/` … |

## 2. 저장소 구성

| | 이름 | 담는 것 |
|---|---|---|
| A | Original File Storage (원본 보관) | 원본 파일 보관 (PDF / DOCX / XLSX / PPTX / 이미지 / TXT) → **Source of Truth** |
| B | Node Store (조회용) | 정형 엔티티 데이터 (SQL DB) → 정확한 조회 |
| C | Vector DB (RAG용) | **Wiki Chunk** + Embedding + Metadata (`company_id` 파티션) |
| D | Metadata DB | 출처/페이지/섹션/버전/구조 · 온톨로지 매핑 · 신뢰도 등 관리 |
| E | Review Queue | uncategorized Fact 및 충돌 검토 항목 |

**③이 만든 원본 청크를 담는 자리가 목록에 없다.**

## 3. Fact Extraction

> `원문을 바로 Wiki로 재작성하지 않고 사실 단위로 추출한다.`

흐름은 `원문 → Fact Extraction → Fact + Metadata → Wiki`.

예시 Fact 로 이것이 적혀 있다.

```json
{
  "company_id": "c_001",
  "topic": "customer_problem",
  "series": "entity",
  "fact": "고객 인터뷰 30명 중 21명이 금융상품 선택에 어려움을 겪음",
  "source": { "document": "고객인터뷰.pdf", "page": 8 },
  "confidence": 0.9
}
```

## 5. 충돌 정보 관리 (엔티티)

```
이전 값 (2026.01)              →      현재 값 (2026.08)
직원 수: 10명                          직원 수: 15명
Source: 회사소개.pdf (p.4)             Source: 피치덱_최신.pdf (p.6)
상태: 이전                             상태: 최신
```

- `최신성 기준 우선 (필요 시 비즈니스 규칙 적용)`
- `새 파일 추가 시 전체 Wiki 재생성 없이 변경분만 반영`

## 6. 공고 DB

| | 무엇 | 역할 |
|---|---|---|
| A | Structured Data (정형) | 기본정보 · 지원자격 · 제출서류 · 사업계획서 항목 · 평가기준 · 작성조건 → **규칙 판단** |
| B | Original Document (원본 보관) | PDF / HTML / 원문 텍스트 → **원문의 Source of Truth** |
| C | Embedding (의미 검색용) | **공고 원문 Chunk Embedding** → 의미 기반 공고 검색 / 추천 |

**공고 쪽은 원문 청크를 임베딩한다.** 사용자 쪽(⑨)만 Wiki Chunk 다.

## 7. 공고 추천 (3단계)

| # | 단계 | 내용 |
|---|------|------|
| ① | Structured Filter (조건 필터링) | 지원자격 · 신청기 · 지역 · 업종/분야 · 사업자 여부 → `지원 가능한 공고 생성` |
| ② | Semantic Search (의미 기반 검색) | 사용자 사업 Embedding ↔ 공고 Embedding → `Top-K 공고 선정` |
| ③ | LLM 재평가 (적합도 평가) | **적합도 점수** · 추천 이유 · 주의 사항 · 핵심 조건 → `추천 결과` |

상세보기는 `공고 원문 해당 부분 Retrieval → 근거 설명`. 추천 결과 항목은 공고명 · 기관 · **적합도 점수** · 추천 이유 · 핵심 조건 · 주의사항.

## 8. 사업계획서 자동 작성

`① 공고 선택 → ② 공고 요구사항 로딩 → ④ 사용자 Wiki RAG (필요 시) → ④ 공고 원문 Retrieval (필요 시) → ⑤ LLM 생성 → ⑥ 검증/감사 → ⑦ 완성 사업계획서`

- ②는 작성 항목 · 글자 수/분량 · 필수 내용 · 평가 기준
- ⑤는 공고 요구사항 + Wiki RAG 결과 + 원문 근거 → LLM 생성
- ⑥은 필수 항목 · 글자 수 · 하위 감사 · 공고 표현 수 제한 등
- ⑦은 PDF / DOCX / 한글 / 마크다운
- 아래에 `각 항목별 출처(근거) 표시 + 수정/보완 가능`

**위키로 돌아오는 화살표가 없다.**
