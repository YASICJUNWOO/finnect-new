## 0. 한 줄 결론

**두 API 모두 실패를 HTTP 200으로 준다. 그리고 K-Startup의 서버측 날짜 필터는 조건을 위반하는 레코드를 섞어 준다.**

둘 다 에러를 내지 않는다. 그럴듯한 숫자와 그럴듯한 레코드가 나온다. 이 문서에서 하나만 남긴다면 §3이다.

## 1. 재현 방법

`.env`에 키가 있어야 한다(`.env.example` 참조). 아래는 2026-08-17에 그대로 실행해 이 문서의 값을 재확인한 명령이다.

```bash
set -a; . ./.env; set +a
```

### 기업마당

```bash
curl -sS -G 'https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do' \
  --data-urlencode "crtfcKey=$BIZINFO_API_KEY" \
  --data-urlencode 'dataType=json' \
  --data-urlencode 'searchCnt=10'
```

| 파라미터 | 값 | 비고 |
|---|---|---|
| `crtfcKey` | 인증키 | **쿼리스트링으로 간다.** 로그 마스킹 필수 |
| `dataType` | `json` | `rss`도 된다 |
| `searchCnt` | 건수 | 그대로 건수 제한이다. §4 |
| `searchLclasId` · `hashtags` | — | 서버측 필터. 쓰지 않는다 |
| `pageUnit` · `pageIndex` | — | 공식 문서에 있으나 쓸 일이 없다. 전량이 요청 1회다 |

### K-Startup

```bash
curl -sS -G 'https://apis.data.go.kr/B552735/kisedKstartupService01/getAnnouncementInformation01' \
  --data-urlencode "serviceKey=$DATA_GO_KR_API_KEY" \
  --data-urlencode 'page=1' \
  --data-urlencode 'perPage=3' \
  --data-urlencode 'returnType=json'
```

| 파라미터 | 값 | 비고 |
|---|---|---|
| `serviceKey` | 인증키 | 공공데이터포털 일반 인증키. **API마다 활용신청이 별도다** |
| `page` · `perPage` | 페이징 | `perPage` 상한 2,000. §4 |
| `returnType` | `json` | |
| `cond[필드::연산자]` | 서버측 필터 | **날짜 필드에는 쓰지 않는다.** §3 |

**상세 API가 없다.** 목록 API 하나뿐이라 첨부는 `detl_pg_url` 스크래핑밖에 방법이 없다.

## 3. 서버측 날짜 필터는 틀린 값을 준다

**이 문서의 핵심이다.** 2026-08-17 재현.

| 질의 | `matchCount` | 응답 첫 3건의 `pbanc_rcpt_end_dt` | |
|---|---|---|---|
| `cond[pbanc_rcpt_end_dt::GTE]=20270101` | 29,690 | `20260827` · `20260824` · `20260906` | **3건 전부 조건 위반** |
| `cond[pbanc_rcpt_end_dt::LTE]=20200101` | 7,366 | `20201231` · `20200131` · `20200117` | **3건 전부 조건 위반** |

2026-08-16에 측정한 것들(오늘 재현하지 않음).

| 질의 | `matchCount` | 첫 건 마감일 |
|---|---|---|
| `pbanc_rcpt_end_dt = 20260101` | 26,907 | `20261231` ← 위반 |
| `pbanc_rcpt_end_dt >= 20260816` | 29,689 | `20260827` |
| `pbanc_rcpt_end_dt <= 20260816` | 29,689 | `20260827` |

**`>=`와 `<=`가 같은 수를 낸다.** 연산자가 반영되지 않는 것으로 보이나 원인은 확인하지 않았다. 확인한 것은 결과뿐이다 — **조건을 위반하는 레코드가 섞여 나온다.**

### 코드값 `EQ`와 이름 `LIKE`는 정상이다

| 질의 | 결과 | 재확인 |
|---|---|---|
| `cond[rcrt_prgs_yn::EQ]=Y` | 274건 | ✅ 2026-08-17 · **268건 2026-08-24** |
| `cond[rcrt_prgs_yn::EQ]=ZZZZ` | 0건 | ✅ 2026-08-17 |
| `cond[biz_pbanc_nm::LIKE]=창업패키지` | 407건 (첫 건 "2026년 초기창업패키지 로켓십 IR 경진대회") | 08-16만 |

**모집중 전량이 요청 1회에 온다**(2026-08-24). `perPage=300` 과 같이 주면
`matchCount` 268 · `currentCount` 268 · 배열 길이 268 로 한 장에 끝난다. `perPage`
상한이 2,000 이라 이 필터에서는 페이징이 아예 필요 없다.

**같은 응답의 `totalCount` 는 29,863 이다.** 필터를 무시한 값이라 종료 조건으로 쓰면
268건을 받고도 149페이지를 돈다 — §2 의 «`matchCount` 기준» 이 이 자리에서 실물로
재현된다.

**274 → 268 은 시간이 지난 것이다.** 플래그가 수집 시점 스냅샷이라 썩는다 — 우리 DB 의
`rcrt_prgs_yn='Y'` 274건 중 **74건(27%)이 오늘 기준 이미 마감일을 지났다**(2026-08-24
실측). 반대 방향으로는 안 틀린다 — 플래그가 `N` 인데 마감일이 남은 공고는 **0건**이라,
이 필터는 실제로 열린 것의 **상위집합**이다.

### 기업마당 `searchLclasId` 코드값 (2026-08-24 실측)

**응답에 코드가 안 온다.** 이름(`pldirSportRealmLclasCodeNm`)만 오고 `extra` 가 1,538건
전부 비어 있다. 그래서 코드를 **역으로 찔러서** 확인했다 — `searchCnt=5` 로 각 코드를
부르고 돌아온 `pldirSportRealmLclasCodeNm` 을 봤다.

| 코드 | 대분류 | `totCnt` |
|:---:|---|---:|
| `01` | 금융 | 216 |
| `02` | 기술 | 286 |
| `03` | 인력 | 162 |
| `04` | 수출 | 223 |
| `05` | 내수 | 112 |
| `06` | 창업 | 73 |
| `07` | 경영 | 415 |
| `09` | 기타 | 15 |

**합 1,502 로 무필터 `totCnt` 와 정확히 같다.** `08` 은 0건이고 `00`·`10`·`11`·`12`·`99`
도 0건이라, 여덟 자리 중 `08` 만 비어 있다.

**좁히는 데 쓰지 않는다.** 무필터가 요청 **1회**인데 분류별로 부르면 **8회**가 된다 —
서버측 필터가 오히려 손해다. 이름 컬럼이 DB 에 이미 있어서 좁히는 것은 조회 계층에서
한다. 이 표가 필요한 자리는 나중에 **특정 분류만 갱신**하고 싶을 때다.

### 그래서 정한 것

**서버측 날짜 필터를 쓰지 않는다.** 코드에 `cond[...::GTE]` 계열이 없다. `rcrt_prgs_yn EQ Y`만 예외이고 **모집단 확정이 아니라 작업 큐 우선순위로만** 쓴다.

마감일 기준 증분 수집을 했다면 **그 오염을 알아챌 방법이 없었다.** 에러도 0건도 아니기 때문이다.

## 4. 건수 제한은 두 출처 다 서버측에서 된다

**잘라 받아도 전량 건수는 그대로 온다.** 이게 [ADR-0011](../0011-수집-실행-화면.md)의 맛보기 수집을 가능하게 한 조건이다. 없으면 "500건만 받았다"와 "500건뿐이다"가 구분되지 않는다.

| 출처 | 파라미터 | 결과 | 전량 필드 | 재확인 |
|---|---|---|---|---|
| 기업마당 | `searchCnt=10` | 10건 | `totCnt` = **1538** | ✅ 2026-08-17 |
| 기업마당 | `searchCnt=100` / `500` | 100 · 500건 | `totCnt` = 1538 | 08-16만 |
| K-Startup | `perPage=3` | 3건 | `matchCount` = **29789** | ✅ 2026-08-17 |
| K-Startup | `perPage=1000` / `2000` | 1,000 · 2,000건 | `matchCount` = 29789 | 08-16만 |
| K-Startup | `perPage=3000` | **실패** (§5) | — | ✅ 2026-08-17 |

**`perPage` 상한은 2,000이다.**

**페이징 종료는 `matchCount` 기준이다.** `totalCount`는 필터와 무관하게 29,789 고정이라 종료 조건으로 쓰면 필터를 걸고도 149페이지를 돈다. 필터가 없을 때는 둘이 같은 값이라 이 차이가 드러나지 않는다.

> **미결.** 전량을 `perPage=2000`으로 받으면 요청이 149회 → **15회**로 준다. 현재 코드는 `PER_PAGE=200`을 유지한다. 149라는 수가 문서와 코드 주석 여러 곳에 근거로 박혀 있어 같이 고쳐야 하고, 병목이 네트워크가 아니라 3만 건 적재라 이득이 크지 않다.

## 5. 실패는 HTTP 200으로 온다

두 출처 다 그렇다. 2026-08-17 재현.

| 출처 | 재현 | 응답 | 크기 |
|---|---|---|---|
| 기업마당 | `crtfcKey=WRONGKEY` | `{"reqErr":"존재하지 않는 인증키 입니다."}` | 55B |
| K-Startup | `perPage=3000` | `{"code":0,"msg":"정상"}` | **26B** |

**K-Startup 쪽이 더 위험하다.** 봉투가 통째로 없는데 `msg`가 `"정상"`이다. `data.get("data") or []`로 받으면 **0건 성공으로 읽고 조용히 넘어간다.**

그래서 봉투 검증은 방어 코드가 아니라 **파싱의 첫 단계**다(`ingest/envelope.py`). item 수보다 봉투를 먼저 본다 — 기업마당은 `reqErr` 문자열, K-Startup은 `matchCount` 키 존재.

정상 응답의 K-Startup 봉투 키는 다섯이다: `currentCount` · `matchCount` · `page` · `perPage` · `totalCount`.

**날짜가 없는 것이 정상 상태다.** K-Startup은 `pbanc_rcpt_bgng_dt` · `pbanc_rcpt_end_dt`가 표본 4,000건 전부 8자리였다.

D-day 계산, 마감 임박 강조, 마감 카운트다운이 전부 이 위에 선다. 어떻게 담고 화면에 뭐라고 쓸지는 **[`SPEC.md`](../../SPEC.md) §9-5 미결**이다.

### 첨부

| 출처 | 상태 |
|---|---|
| 기업마당 | `fileNm` · `flpthNm`이 `@`로 이어붙인 병렬 배열. `printFileNm` · `printFlpthNm`는 공고문 별도 필드 |
| 기업마당 `fileNm` 0개 | **431건 (28%).** 1개 667 · 2개 250 · 3개 123 · 4개 55 · 5개 12 |
| 기업마당 `printFileNm` | **1,538건 전부 (100%)** — 2026-08-17 추가 |
| K-Startup | **API에 첨부 필드가 없다.** 상세 페이지 스크래핑이 유일한 방법 |

**첨부 0개인 공고와 아직 안 본 공고는 다르다.** K-Startup은 전량이 미확인이고, `attachment_status`가 이 둘을 구분한다.

#### 2026-08-17 정정 — "첨부 0개 431건"은 `fileNm`만 센 값이다

위의 431건을 **"확인된 첨부 0개"**로 적었는데 정확하지 않다. 저장 모델(`ingest/bizinfo.py:_attachments`)은 `printFileNm`(공고문)도 첨부로 담고, **기업마당은 그것을 1,538건 전부에 붙인다.** 그래서 **저장된 첨부가 0개인 기업마당 공고는 한 건도 없다.**

```
$ 전량 적재 후 집계 (2026-08-17)
kind별:      기타 1,816 · 공고문 1,538
기타 0개:    431건   ← 위 표의 '첨부 0개 431건'
저장 0개:    0건
```

**이건 세는 기준이 둘이라는 뜻이지 어느 쪽이 틀렸다는 뜻이 아니다.** 다만 "공고 하나에 첨부가 없을 수 있다"로 읽으면 틀린다. 기업마당 쪽은 **공고문 하나가 항상 있다.** 공고 본문의 평가 정보가 0%인 것과 겹쳐 읽으면, 열 파일이 최소 하나는 보장된다는 뜻이다.

K-Startup 상세를 긁을 때 **마감 공고는 `bizpbanc-deadline.do`로 들어가야 첨부가 렌더된다.** `bizpbanc-ongoing.do`는 마감 건에 빈 껍데기(19KB)를 준다([첨부파싱 실측](2026-08-16-첨부파싱-배점실측.md) §2).

## 8. 확인 불가로 남은 것

### 기업마당 일 한도

**확인 불가.** [T-0009](../../plan/06-목록-수집과-조회.md#t-0009-api-실측-기록)의 완료 조건이 "포털 마이페이지에서 확인하거나 확인 불가로 기록한다"였고, 후자로 닫는다.

| 확인한 것 | 결과 | 날짜 |
|---|---|---|
| 공식 안내 페이지 `apiDetail.do?id=bizinfoApi` | 호출 제한·트래픽 한도·rate limit 문구가 **없다** | 2026-08-17 |
| 응답 헤더 | 쿼터 관련 헤더가 **하나도 없다** | 2026-08-17 |
| 포털 마이페이지 | **못 봤다.** 로그인이 필요하고 계정 소유자만 볼 수 있다 | — |

**한도가 없다는 뜻이 아니라 공개된 곳에서 못 찾았다는 뜻이다.** 전량이 요청 1회라 현재 사용량으로는 문제가 되지 않지만, 첨부 다운로드가 붙으면 요청 수가 달라진다. 그때 다시 본다.

### 재현하지 않은 값

이 문서의 값 중 2026-08-16 측정 뒤 다시 돌리지 않은 것은 각 표에 `08-16만`으로 적었다. 전량 적재(1,538 · 29,789)와 분포 통계(첨부 개수, 접수 기간)가 여기 해당한다. 전량 건수 자체는 `totCnt` · `matchCount`로 2026-08-17에 재확인됐다.

### 원인을 확인하지 않은 것

§3의 날짜 필터가 **왜** 틀린 값을 주는지는 확인하지 않았다. 확인한 것은 결과뿐이다. 원인을 모르므로 **일부 조건에서는 맞을 것이라고 가정하지 않는다.** 날짜 필터 전체를 쓰지 않는다.
