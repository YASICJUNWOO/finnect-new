## 원칙

**LLM을 거치지 않는다(F2-3).** 같은 입력에 항상 같은 판정이 나와야 한다. 판정에 확률적 요소가 들어가면 "어제는 된다더니 오늘은 안 된다"가 생긴다. 근거는 [ADR-0002](../adr/0002-3계층-분리.md).

**판정 근거를 화면에 보여주지 않는다.** 그래서 틀린 판정을 사용자가 알아챌 방법이 없다. 정확도 부담이 전부 여기로 온다. 근거는 [ADR-0003](../adr/0003-판별-비노출.md).

## 할 것

### 요건 표현식 설계

**이 단계의 핵심이자 가장 위험한 부분이다.**

공고 요건을 코드가 평가할 수 있는 형태로 표현해야 한다. 미리 설계하지 않는 이유는 [`README.md`](README.md)에 적었다 — **모양은 코퍼스가 결정한다.**

02에서 쌓인 실제 요건 문장 30건 이상을 읽고 나서 설계한다.

다뤄야 하는 요건 종류(`SPEC.md` F2-1):

| 종류 | 예 |
|------|-----|
| 업력 | 신청일 기준 창업 후 3년 이내 |
| 연령 | 만 39세 이하 |
| 소재지 | 국내 / 특정 지자체 |
| 업종 | 제한 업종 비해당 |
| 결격 사유 | 국세·지방세 체납 없을 것 |
| 중복 수령 제한 | 동일 사업 재수혜 불가 |

**중복 수령 제한도 요건의 한 종류로 다룬다.** 별도 기능으로 만들지 않는다([ADR-0003](../adr/0003-판별-비노출.md)).

### F2-2 파생 값 계산

**저장값을 그대로 쓰면 틀린다.** 공고마다 기준일이 다르다.

- 사업자등록일 → 신청일 기준 업력
- 생년월일 → 신청일 기준 만 나이

기준일이 "신청일"인지 "모집마감일"인지도 공고마다 다르다. 실측에서 초기창업패키지 사업계획서 양식이 "(모집마감일 기준)"이라고 명시한 것을 확인했다.

### 판정 불가를 어떻게 다룰지

요건이 자유 텍스트로만 서술돼 규칙으로 표현되지 않거나, F0-6 신뢰도가 낮은 경우다.

**보수적으로 다룬다.** 다만 "보수적"이 무엇인지 정해야 한다 — 목록에서 빼면 받을 수 있는 공고를 놓치고, 넣으면 못 받을 공고를 추천한다. 이 트레이드오프는 이 단계에서 결정하고 ADR로 남긴다.

### F2-4 전체 재판정

프로필이 바뀌면 색인 전체를 다시 판정한다. 공고 수천 건 × 요건 수십 개이므로 성능을 본다.

### T-0055 제품 편입

> **[17](17-맞는-공고를-고른다.md)로 넘겼다** (2026-08-20). **옮긴 것이 아니라 새로 만들었다** —
> 재 보니 옮길 것이 거의 없었다.
>
> ```
> c_dasiro 위키 실값(업력 2.44년 · 직원 15명)으로 K-Startup 전량 재판정
>   기본값(2.5년 · 4인)  통과 15,643
>   실값                 통과 15,656      차이 13건 (0.08%)
> ```
>
> **`filter_notice()` 가 사용자를 축 둘로만 본다**(축3 업력 · 축2f 규모). 나머지 열한
> 축은 공고만 보고, 위키의 자격 슬롯 여덟 중 **소재지·업종·연령·중복수혜 넷은 축이
> 아예 없었다.** 그 넷이 실제로 회사를 가르는 축이다 — 지역 제한 공고가 K-Startup
> 13,521건(45%) · 기업마당 1,003건(65%) 이다.
>
> 그래서 [17](17-맞는-공고를-고른다.md)이 `src/finnect/match/eligible.py` 에 **다섯 축을
> 새로 만들었고**(소재지·업종·연령·규모·중복수혜), 이 폴더는 **층0(제품 범주)으로
> 남아 밖에 산다.** 목록 파일로 넘긴다 — `attach --only` 와 같은 경계다.
>
> 아래 네 줄은 그때 적어 둔 것이고 **셋이 그대로 지켜졌다.**

- `filter_notice()` 는 dict 하나를 받아 dict 하나를 돌려준다. 임포트 경계는 이미 좁다
- **`reasons` 를 화면에 내보내지 않는다.** [ADR-0003](../adr/0003-판별-비노출.md) 이 `채택됨` 이고 대체되지 않았다 — 자격 판별 근거는 사용자에게 안 보여준다. `notice-filter/` 의 HTML 이 근거를 보여주는 것은 **검증 도구라서** 허용되는 것이고, 제품 화면으로 그대로 옮기면 ADR-0003 위반이다
- **필터는 조회 계층이지 수집 계층이 아니다**([§12](../../notice-filter/로직과근거.md)). 수집은 항상 전량이다 — 기업마당은 마감되면 API 에서 사라져 우리 DB 가 유일한 사본이다
- 완료 조건: **ADR 한 편** + 코드와 문서를 같은 커밋에

**셋이 지켜졌다.** `reasons` 는 `Judgement` 안에만 살고 API 스키마에 없다(ADR-0003).
수집은 여전히 전량이고 후보 좁히기는 조회 계층이다. 임포트 경계는
`tests/test_match_only.py` 가 막는다 — `match/` 어디에서도 이 폴더를 임포트하지 않고,
그 대가로 절 나누기 정규식이 `match/bodies.py` 에 한 벌 더 산다.

**ADR 은 안 썼다.** 새 결정이 아니라 [ADR-0013](../adr/0013-판정-두-층.md)의 M1 을
구현한 것이고, 이 폴더를 제품에 넣는 결정이 아니라 **넣지 않기로 한 것**이다.

**골든셋을 만든다.** 실제 공고 N건에 대해 사람이 판정한 정답을 만들고 엔진 출력과 대조한다. 판별을 화면에 안 보여주기로 한 이상, **이 수치가 제품 품질의 유일한 증거다.**

- [ ] 골든셋 대비 정확도를 낸다. 위양성(못 받을 공고를 추천)과 위음성(받을 공고를 누락)을 따로 센다
- [ ] 같은 입력을 두 번 넣으면 판정이 완전히 동일하다 (F2-3 결정론)
- [ ] 기준일이 다른 공고에서 업력·나이가 각각 다시 계산된다 (F2-2)
