## 원칙 하나 — LLM 이 회사 쪽을 안 본다

```
전  공고 정규화 709회  +  (회사 × 적합도 N회)     회사 1,000개 → 곱해진다
후  공고 정규화 709회                              회사 1,000개 → 그대로 709회
```

**LLM 은 공고만 읽는다.** 회사와의 대조는 전부 코드다.

이건 이 레포가 이미 쓰는 패턴이다 — `wiki/topics.py` 가 *"LLM 은 라벨과 근거 위치만 붙이고 목적지는 정하지 않는다. LLM 이 목적지를 정하면 같은 사실이 어제는 A, 오늘은 B 로 가서 위키가 돌릴 때마다 달라진다"* 고 적은 그것이고, [ADR-0031](../adr/0031-사실-추출을-포트-뒤로-미루고-스텁으로-배관을-먼저-세운다.md)이 같은 이유로 포트를 팠다.

**대가를 적어 둔다.** 회사 쪽을 안 보므로 "이 회사에게 이 공고가 왜 맞는가" 를 모델이 문장으로 못 만든다. 이유는 **템플릿**이 만든다(T-0074). 어색하면 그때 상위 3건에만 LLM 을 붙인다 — **재기 전에 안 붙인다**(CLAUDE.md 규칙).

회사 단위 · 회사당 1회

## 태스크

### T-0070 공고 정규화 — 공고가 누구를 찾나

공고 하나를 LLM 이 읽고 **구조화 필드**로 낸다. `notice_profile` 에 앉고 **회사와 무관하다.**

```
입력   기업마당    pblancNm + bsnsSumryCn 1절(지원대상) · 2절(지원내용)
       K-Startup   biz_pbanc_nm + aply_trgt_ctnt + pbanc_ctnt
출력   regions[] · industries[] · conditions[] · keywords[] · purpose · anchor
```

- **첨부를 한 개도 안 연다.** 지원대상이 본문 필드에 있다. 첨부에 있는 것은 양식이고 그건 [16](16-항목마다-초안을-쓴다.md)이 쓴다
- **제목의 지역 태그를 쓰지 않는다.** 실측으로 틀렸다 — `[경기]` 46건 중 성남시는 **2건**이고 나머지는 김포·화성·안양·시흥·안산·용인이다. 그리고 `전국·미표기` 205건 안에 수성알파시티(대구)·대구콘텐츠코리아랩·제주형 그린바이오·울산창조경제혁신센터가 섞여 있다. **광역 태그는 시·군 사업을 가리고, 태그 없음은 전국을 뜻하지 않는다**
- `anchor` 가 본문에 없으면 **그 공고를 버리고 센다.** `wiki/extract.py` 와 같은 규율이다 — 조용히 비면 "아무것도 안 나온 것" 과 구분이 안 된다
- **캐시 키를 `content_hash` 로 잡지 않는다.** 조회수(`inqireCo`)가 해시 재료라 **기업마당은 재수집마다 1,538건 전부가 '변경'** 이다. 거기 걸면 매번 709회를 다시 쓴다. **본문만의 해시**를 따로 뜬다
- 완료 조건: 공고 **40건을 손으로 라벨해 대조**하고 불일치를 전부 나열한다. 정확도를 숫자로만 보고하지 않는다

### T-0071 회사 프로필 — 위키에서 읽기만 한다

`wiki_fact` 에서 자격 슬롯 넷과 노드를 읽어 `CompanyProfile` 을 만든다. **새 LLM 호출이 0회다.**

- **파생값을 저장하지 않는다.** 업력과 만 나이는 **판정 시점에 계산한다** — `wiki/topics.py` 가 *"공고마다 기준일이 다르다"* 고 못 박았다. 기준일이 신청일인지 마감일인지도 공고마다 다르므로 둘 다 낼 수 있어야 한다
- **`current` 를 그냥 읽으면 틀린다.** `c_dasiro` 의 `headcount` `current` 가 `as_of 2026-08-31` 이다 — 미래 시점 값이라 신청일 기준 판정에 쓰면 아직 오지 않은 상태로 판정한다. **신청일 이전의 최신값**을 골라야 한다
- **`conflict` 는 판정 불가다.** `c_dasiro` 의 `funding` 에 이미 충돌 2행이 서 있다. 자격 슬롯에 충돌이 나면 그 축을 판정하지 않는다
- 자격 슬롯 넷 중 셋이 **사업자등록증 한 장**에서 나온다(소재지·업종·개업일 — [ADR-0030](../adr/0030-OCR은-rapidocr-로컬로-하고-검출은-server-를-쓴다.md)). 그래서 온보딩이 그 한 장을 요구하는 것이 이 태스크의 전제다

### T-0072 자격 대조 — 못 넘으면 뺀다 (M1)

`notice_profile` × `CompanyProfile`. **LLM 0회.**

| 축 | 공고 쪽 | 회사 쪽 | 안 맞으면 |
|---|---|---|---|
| 소재지 | `regions[]` | `location` | **탈락.** 주소 문자열이라 결정론이 잘 된다 |
| 업종 | `industries[]` | `industry` · `industry_item` | **확인 필요.** `ICT` 와 `정보통신업` 이 안 겹친다 |
| 대표자 연령 | `conditions[]` | `ceo_birth` | **탈락.** 숫자 비교다 |
| 규모 | `conditions[]` | `headcount` | **탈락.** 아래 — 실측으로 추가한 축이다 |
| 중복수혜 | `conditions[]` | `gov_program` | **확인 필요.** 같은 사업인지 모른다 |

**넷이 아니라 다섯이다.** `규모` 는 계획에 없었고 손 라벨 15건을 돌려 보고 넣었다 —
`소상공인` 조건 넷이 그대로 통과해 **추천 3건을 통째로 차지했다.** 자세한 것은 아래
[6번이 찾은 결함](#6번이-찾은-결함-둘).

**축마다 확신이 다른 것이 이 표의 요점이다.** 오탈락은 화면에서 사라져서 사용자가
알아챌 방법이 없고(ADR-0003), 오추천은 열어 보면 안다. 그래서 확신이 낮은 축을
탈락으로 두지 않는다.

- **배제형 원칙을 그대로 쓰지 않는다.** `notice-filter` 의 *"조건이 명시되지 않으면 통과"* 는 **공고 쪽이 빈 경우**의 규칙이다. **회사 쪽이 비면 다른 문제다** — 공고는 "충북 소재" 라고 분명히 말했고 우리가 사용자를 모르는 것뿐이다. `SPEC.md` F3-1-5 대로 **판정하지 않고 `unknown` 으로 남긴다**
- **`notice_profile` 이 없으면 판정하지 않는다.** 목록에는 남고 추천에는 안 오른다. 그래서 키가 없어도 화면이 성립한다([`../DESIGN.md`](../../DESIGN.md) §6.1 이 목록을 둘로 나눈 이유)
- **저장하지 않는다.** 실측 — K-Startup 29,789건 전량 재판정 **0.36초**(12μs/건). F2-4 "프로필이 바뀌면 전체 재판정" 이 공짜다. 캐시를 만들면 무효화가 문제가 된다(위 조회수)

### T-0073 분야 대조 — 지금 필요한 것인가 (M2 앞단)

공고의 **지원분야 코드값**과 위키의 **로드맵·자금·기술** 노드를 대조해 순서를 민다. **LLM 0회.**

- **뺄 수 없다. 민다.** 해외진출도 자격은 된다 — 지금 이 회사 로드맵에 안 맞을 뿐이고 내년에는 맞을 수 있다. [ADR-0013](../adr/0013-판정-두-층.md)이 정한 그대로다: *자격은 못 넘으면 화면에서 뺀다 / 적합도는 순서를 정한다.* **새 층이 아니라 M2 의 결정론 앞단이라 ADR 을 새로 쓰지 않는다**
- **대조표를 두 벌 만든다.** 두 출처의 분류가 **이름 교집합이 거의 0** 이다 — 기업마당 중분류 39종 ∩ K-Startup 11종 = **0**, 대분류 8종 ∩ = `{인력}` 하나. 공통 분류로 접으면 39종의 해상도를 잃는다. `notice-filter/kstartup.py` 가 같은 결론에 도달했다
- **K-Startup 쪽은 힘이 약하다.** `사업화` 하나가 7,161건(24%)이라 갈라 주지 않는다. 거기서는 ⑤(취지)가 더 일한다
- **`기술개발(R&amp;D)` 처럼 HTML 엔티티가 남아 있다.** 저장할 때 고치지 않는다(API 가 준 것을 그대로 담는 원칙) — **읽는 쪽에서 한 번** 푼다
- 완료 조건: 39종·11종에 노드를 매달면서 **몇 건을 눈으로 봤는지** 적는다. `notice-filter` 가 축2d 20건·축2e 24건을 그렇게 했다

### T-0074 순서와 이유 — 템플릿으로 만들고 잰다 (M2)

취지 키워드와 사업 내용 노드의 겹침으로 순서를 내고, 겹친 노드로 이유 한 줄을 만든다. **LLM 0회.**

실제 출력이다(`c_dasiro` 위키 · 2026-08-20).

```
공고 keywords   [소상공인, 판로]
겹친 노드       [identity] 바코드와 QR로 입출고 기록을 자동으로 남겨…
   ↓
"소상공인·판로가 주제예요. 바코드와 QR로 입출고 기록을 자동으로 남겨, 발주 시점을
 놓치지 않게 하는 소상공인용 재고관리 소프트웨어"
```

**겹친 키워드만 문장에 온다.** 공고 취지를 되풀이하지 않고 **우리 위키에 실제로
있는 것만** 말한다 — 안 겹친 키워드를 넣으면 근거 없는 문장이 된다.

- [ADR-0013](../adr/0013-판정-두-층.md)이 예시로 든 문장이 이 모양이다 — *"이 공고는 지역상생이 주제이고 당신 사업은 지역화폐라 맞습니다."*
- **근거가 자동으로 매달린다.** 어느 `wiki_fact.id` 에서 나왔는지 코드가 알고 있어서 LLM 출력을 검증할 필요가 없다. `draft_evidence` 가 `fact_id` 를 든 것과 같은 이유고 **나중에 붙일 수 없다**
- **점수를 만들지 않는다.** 등급 셋(`맞다` · `애매` · `아니다`)뿐이고 같은 등급 안의 순서는 코드가 정한다 — ④ 일치 → 겹침 수 → 마감 임박. 연속값을 만들면 화면에 안 내도 **설명할 눈금이 없는 순서**가 된다(`Fact` 에 `confidence` 를 안 넣은 것과 같다)
- **겹친 노드가 0건이면 추천하지 않는다.** `SPEC.md` §9-2("이유를 못 만들 때")가 여기서 닫힌다 — 템플릿이라 못 만드는 경우가 그 하나뿐이다
- 완료 조건: **실제 문장 40건을 눈으로 보고 어색한 비율을 보고한다.** 그 숫자를 보고 LLM 을 붙일지 정한다

### T-0075 API — 추천 세 건을 내보낸다

```
GET /api/companies/{company_id}/recommendations   → 추천 3건 + 이유          ← 새로
GET /api/notices                                  → 전체 · 마감 임박순       ← 그대로
```

`DESIGN.md` §6.1 의 두 섹션을 **경로 둘로 나눴다.** `/api/notices` 를 안 건드린 이유는
위키가 없어도 그쪽이 떠야 하기 때문이다.

- **`notice_fit` 을 읽기만 한다.** 판정은 `python -m finnect.match` 가 미리 돌린다 —
  화면 요청 경로에서 LLM 을 부르지 않는 것(F6-1 과 같은 원칙)이고, 페이지 열 때마다
  1,790건을 정규식으로 훑지 않는 이유도 그것이다
- **`api/service.py` 가 `match.service` 를 임포트하지 않는다.** 저쪽이 `llm` 을 끌고
  오는데 `requirements.txt` 에 httpx 가 없다 — 임포트하면 **로컬은 통과하고 배포본만
  죽는다**(CLAUDE.md 함정). `tests/test_admin_api.py` 가 막아 둔다
- **404 를 내지 않는다.** 판정이 안 돌았으면 `computed: false` 다 — 화면이 "아직
  없어요" 와 "맞는 것이 없어요" 를 다르게 말해야 한다
- **마감이 지난 것은 낸 뒤에 뺀다.** 판정은 어제 돌았어도 오늘 마감일 수 있다

| `notice_fit` | ⑤의 출력. `(회사, 공고)` 1행. 등급·이유·낡음 |
| `notice_fit_evidence` | 그 이유가 어느 사실에서 나왔나. **`fact_id` 를 든다** — 나중에 못 붙인다 |

```
낡음 = wiki_fact.updated_at > notice_fit.computed_at
```

**③④ 는 저장하지 않는다.** 재계산이 0.36초라 캐시가 손해다. ⑤만 앉히는 이유는 이유 문장을 매번 다시 만들 필요가 없고 근거 링크를 들어야 하기 때문이다.

**마이그레이션을 만들면 배포 DB 에도 돌려야 한다.** 2026-08-18 `document` 를 로컬에만 만들었더니 공고 상세가 통째로 500 이 됐다.

### 1번 — 손 라벨 15건 대조

| 필드 | 일치 | 불일치 |
|---|---|---|
| `regions` | **15/15** | — |
| `industries` | 13/15 | 둘 다 **부분 누락**이다. `['시스템반도체','팹리스']` → `['시스템반도체']` · `['제조','식품','생활용품']` → `['식품','생활용품']` |

**`regions` 가 다 맞은 것이 이 표의 요점이다.** 제목 태그가 틀린 셋을 본문으로
바로잡았다 — `[경기] 성남시`→`성남시` · `[대구] 유성구`→`유성구`(대전이다) ·
`대경권(대구)`(태그 없음)→`대구광역시`.

`industries` 누락은 **안전한 방향**이다. 덜 적히면 겹칠 기회가 줄어 `확인 필요` 가
늘 뿐, 잘못 탈락시키지 않는다.

### 6번이 찾은 결함 넷

**넷 다 눈으로 보고 찾았다.** 배관 테스트로는 하나도 안 잡혔다.

**① `소상공인` 조건을 규칙이 못 읽어 추천 3건이 통째로 오추천이었다.**
못 읽은 조건 13건 중 4건이 이것이었고 그 넷이 그대로 `맞다` 가 됐다. `c_dasiro` 는
직원 10명이라 소상공인이 아니다.
→ `eligible._규모` 를 넣었다. **10인 상한만 확실하다** — 업종별 기준이 5인·10인인데
대응표가 없어서 10명 이상은 탈락, 10명 미만은 `확인 필요` 다. 못 읽은 조건이
**13건 10종 → 7건 7종** 으로 줄었다.

**② 이유의 근거를 잘못 골랐다.** 문장이 이랬다.

```
소상공인이 주제예요. 성남·용인 소상공인 30명 중 21명(70%)이 재고를 수기 또는
기억으로만 관리하고 있었다
```

**시장 조사 결과이지 우리가 맞는 이유가 아니다.** `identity`("소상공인용 재고관리
소프트웨어")가 맞는데 59자로 더 길어서 짧은 `problem` 에 밀렸다.
→ `rank.NODE_RANK` 를 넣었다. 겹침 수 → **노드 종류** → 길이 순.

**③ 보내는 것과 대조하는 것이 달랐다.** `NoticeBody.text` 와 `user_prompt()` 를 따로
만들어서, 모델이 구역 둘을 걸쳐 인용하면 앵커에 `--- 지원내용 ---` 이 들어오는데
대조 대상에는 그 줄이 없었다. **정상 응답이 버려졌다.**
→ `user_prompt(b)` 가 `b.text` 를 그대로 쓴다.

**④ 앵커가 우리가 넣은 구분선과 HTML 엔티티에서 깨졌다.** 표본 200건에서 **8건(4%)**
이 버려졌는데 전부 우리 쪽 문제였다.

```
모델    "관내 사회적경제기업\n제품 디자인설계, 3D 모델링, 목업 및 간이금형 제작"
원문    "관내 사회적경제기업\n\n--- 지원내용 ---\n제품 디자인설계, 3D 모델링 …"
                            ↑ 모델이 구분선을 요약해 버렸다

모델    "… R&D역량을 보유한 기업"        ← 정직하게 풀어 썼다
원문    "… R&amp;D역량을 보유한 기업"     ← 우리가 안 풀었다
```

→ `normalize.squash()` 가 구역 표시를 지우고, `bodies.clean_summary()` 가
`html.unescape` 로 엔티티를 전부 푼다(`&nbsp;` 하나로는 부족했다).
**8건 → 1건.** 남은 하나는 진짜로 모델이 조각을 재구성한 것이다.

### 3번 — 층0 이 실제로 일한다

`--only` 없이 돌렸더니 추천 1건이 나왔는데 **나쁜 추천이었다.**

```
맞다  2026년 소프트웨어 산업발전 유공자 포상계획 재연장 공고
      소프트웨어가 주제예요. 바코드와 QR로 입출고 기록을 …
```

`유공자 포상` 은 지원사업이 아니다. `소프트웨어` 한 낱말이 걸렸을 뿐이다.
**층0(`notice-filter` 축2 — '정부가 주는 물건' 으로 배제)이 빼는 자리**이고, 목록을
넘기니 사라졌다. `--only` 경계가 값을 하는 것을 여기서 봤다.

### 5번·6번 — ④가 일하고 ⑤는 이 표본에서 못 맞췄다

층0 적용 후 자격을 넘은 8건이 이렇게 갈렸다.

```
맞다   0건
애매   5건   ← 전부 ④ 분야가 살렸다. ⑤ 키워드 교집합은 0/5
아니다 3건
```

애매 5건을 눈으로 봤다 — **5/5 가 합리적이다.**

```
[경기] 성남시 기술자료 임치 수수료 지원사업        ← 성남 + 특허 보유. 맞다
2026년 2차 기술개발제품 공공기관 실증지원 사업
민관협력 오픈이노베이션 지원 (창업기업 · 공공데이터) 2건
BOUNCE 2026 스타트업 오픈이노베이션 페스타
```

**④ 분야 대조가 다섯을 전부 살렸다.** 결정론 표 하나가 여기서 값을 했다.

### 임베딩 트리거 조건이 측정됐다

계획이 *"취지 키워드 교집합이 0 인데 사람이 보면 맞는 공고의 비율을 재고, 그게
크면 붙인다"* 고 적어 뒀다. **두 번 재 봤다.**

```
손 라벨 15건    자격 통과 4  ·  겹침 0 이 4  ·  사람이 보면 맞는 것 2   → 2/4
층0 표본        자격 통과 8  ·  겹침 0 이 5  ·  사람이 보면 맞는 것 5   → 5/5
```

**미탐이 크다.** `특허`·`기술자료`·`오픈이노베이션`·`공공데이터` 가 우리 노드의
`특허 출원 … 재고 기록 동기화 방법 및 장치` 와 낱말이 안 겹친다. 문자열 교집합이
닿지 않는 자리다.

**그런데 임베딩보다 싼 답이 하나 먼저 있다.** ④ 분야 대조가 **어느 노드의 어느
낱말에 걸렸는지 이미 알고 있다**(`sectors.Match.cues`). 그걸로 이유를 만들면
`애매` 5건에 이유가 붙어 추천이 선다 —

```
"로드맵 2단계가 경기 남부 영업망 구축이라 이 분야가 맞아요"
```

**그것을 먼저 하고, 그 뒤에도 미탐이 남으면 임베딩을 얘기한다.**
