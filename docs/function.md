# function.md — 핵심 기능

> 실제로 동작하는 제품이 갖출 기능을 담는다. 공고 원문을 데이터로 만드는 파이프라인(F0)부터 화면 기능(F1~F9)까지다.
> 계정·과금, 알림 발송, 사람이 쓰는 운영 도구는 아직 제외한다. 뺀 목록은 5장에 있다.
> 작성일 2026-08-15. 같은 날 범위를 개정했다. **데모에서 보이는 기능만 담던 문서를 제품 범위로 넓혔다.**
> 개정 이유: 배점이 공고 본문이 아니라 첨부 문서 안에 있어, 첨부 파싱 없이는 F5 공고 분석이 성립하지 않는다.

---

## 1. 한 줄 정의

내 사업 정보로 **신청 가능한 공고를 판정**하고, 그 판정 결과를 **심사 배점에 맞춘 사업계획서 초안**으로 잇는다.

핵심은 판정과 집필을 잇는 연결이다. 둘 중 하나만 있으면 이미 있는 서비스다.

---

## 2. 동작 순서

기능은 이 순서로 돈다. 판별이 먼저고 화면은 그 결과를 받는다.

판별에는 입력이 둘 필요하다. 공고 쪽 입력을 만드는 것이 F0이고 사용자 쪽 입력이 F1이다.

```
F0 공고 데이터 파이프라인            F1 내 정보
   수집 → 파싱 → 추출 → 색인            사용자 입력
   화면 없음                            │
   │                                    │
   └────────────────┬───────────────────┘
                    ▼
             F2 자격 판별  ← 화면 없음. 엔진이 전체 공고를 판정한다
                    │
                    ▼
             F3 지원사업 리스트  ← 판정 결과가 곧 목록이다
                    │
                    ▼ 아이템 클릭
             F4 공고 상세  ← 잘 정리된 요강
                    │
                    ▼ 계획서 쓰기
             F5 공고 분석 → F6 내용 채우기 → F7 초안 작성 → F8 문서 산출
                    │
                    ▼
             F9 신청 현황
```

이 순서가 `service_spec.md` §2.4의 계층 표기와 대응한다. **F0이 L1(추출), F2가 L2(판별), F5~F8이 L3(집필)이다.** 계층을 나누는 이유는 무엇을 생성해도 되고 무엇을 생성하면 안 되는지가 계층마다 다르기 때문이다. L1과 L2는 값을 만들지 않고 원문에서 가져오거나 계산만 한다. L3만 문장을 만든다.

---

## 3. 핵심 기능

### F0. 공고 데이터 파이프라인

**화면이 없는 기능이다.** 공고 원문을 F2가 판정할 수 있고 F5가 배점을 읽을 수 있는 구조로 만든다. 이 계층의 출력이 L1이다.

| 기능 | 동작 |
|------|------|
| F0-1 공고 수집 | 출처 API에서 공고 목록과 본문을 받는다. 콘텐츠 해시로 변경분만 갱신한다 |
| F0-2 첨부 파싱 | 첨부 문서(HWP·HWPX·PDF)를 내려받아 텍스트로 만든다 |
| F0-3 구조화 추출 | 본문과 첨부 텍스트에서 자격 요건, 지원 규모, 접수 기간, 심사 배점, 제출 서류, 유의사항을 스키마에 맞춰 뽑는다 |
| F0-4 교정 루프 | 비었거나 스키마를 벗어난 항목은 해당 원문 구간을 다시 읽어 재추출한다 |
| F0-5 근거 구간 보존 | 추출한 값마다 원문의 어느 구간에서 나왔는지 남긴다 |
| F0-6 추출 신뢰도 | 항목별 확신도를 남긴다. 낮은 항목은 F2에서 보수적으로 다룬다 |
| F0-7 색인 갱신 | 추출 결과를 판정 가능한 형태로 적재한다. 갱신되면 F2 재판정 대상이 된다 |

**F0-2는 뺄 수 없다.** 평가 정보는 공고 본문에 전혀 없다. 실측에서 기업마당 본문 0/200건, K-Startup 본문 0/200건이었다. 첨부를 안 열면 평가 관련 데이터가 0이다.

**다만 배점에 대한 전제는 틀렸다.** 2026-08-16 실측 결과 초기창업패키지·창업도약패키지는 **평가항목 이름만 공개하고 배점을 공개하지 않는다.** 창업 분야 전체로도 배점표 명시율은 25%다. 첨부 파싱은 되지만(95%) 뽑을 배점이 없는 공고가 다수다. 전문은 `dev_research.md`, 영향 범위는 `service_spec.md` §11.2에 있다.

⚠️ **이에 따라 F5-2 "배점 높은 순으로 나열"과 F6-2 "질문별 배점 표기"는 다시 써야 한다.** 아직 고치지 않았다.

**F0-5가 F7-3의 근거다.** 사실 고정은 모델에게 지어내지 말라고 지시해서 되는 것이 아니라, 쓸 수 있는 값의 출처를 데이터가 들고 있어야 성립한다.

### F1. 내 정보

| 기능 | 동작 |
|------|------|
| F1-1 판별용 정보 | 사업자 형태, 사업자등록일, 대표자 생년월일, 소재지, 업종, 정부지원사업 수령 이력 |
| F1-2 집필용 정보 | 문제 인식, 솔루션, 목표 고객, 매출과 성과, 성장 전략, 팀 구성. PSST 구조에 맞춘다 |
| F1-3 수정과 재판정 | 판별용 값을 고치면 전체 공고를 다시 판정한다 |

두 묶음은 탭으로 나눈다. 데모는 값이 채워진 상태로 시작하며 이 화면은 시연 동선에서 뺀다.

### F2. 자격 판별

**화면이 없는 기능이다.** 사용자 정보로 색인된 공고 전체를 판정하고, 그 결과가 F3 리스트가 된다. 판정 과정과 근거를 사용자에게 보여주지 않는다.

| 기능 | 동작 |
|------|------|
| F2-1 요건 대조 판정 | 프로필 값과 공고 요건을 대조해 신청 가능 여부를 판정한다. 업력, 연령, 소재지, 업종, 결격 사유, 중복 수령 제한을 모두 요건의 한 종류로 다룬다 |
| F2-2 파생 값 계산 | 사업자등록일에서 신청일 기준 업력을, 생년월일에서 만 나이를 계산한다. 공고마다 기준일이 달라 저장값을 그대로 쓰면 틀린다 |
| F2-3 결정론 보장 | LLM을 거치지 않는다. 같은 입력에 항상 같은 판정이 나온다 |
| F2-4 전체 재판정 | 프로필이 바뀌면 색인 전체를 다시 판정한다 |

### F3. 지원사업 리스트

| 기능 | 동작 |
|------|------|
| F3-1 신청 가능 공고만 노출 | F2가 가능으로 판정한 공고만 올린다 |
| F3-2 카드 정보 | 사업명, 주관기관, 출처 구분, 마감까지 남은 일수, 지원 규모 |
| F3-3 마감 임박 순 정렬 | 기본 정렬. D-7 이내는 강조한다 |
| F3-4 출처 필터 | 전체, 중앙부처, 지자체 |
| F3-5 준비 시작 | 이 공고를 신청 현황에 넣는다 |

### F4. 공고 상세

공고 요강을 읽기 좋게 정리한 화면이다. 원문을 옮기지 않고 항목으로 나눠 보여준다.

| 기능 | 동작 |
|------|------|
| F4-1 개요 | 사업명, 주관기관, 접수 기간, 마감, 지원 규모, 접수 방법 |
| F4-2 지원 내용 | 무엇을 얼마나 어떤 기간에 주는지 |
| F4-3 신청 자격 | 공고가 요구하는 자격 요건 목록 |
| F4-4 제출 서류 | 서류명과 지정 양식 여부. 양식 미준수 탈락 조건은 강조한다 |
| F4-5 심사 방식과 배점 | 항목별 배점을 표와 막대로 |
| F4-6 유의사항 | 제출 후 수정 불가처럼 탈락으로 이어지는 조항 |
| F4-7 원본 공고 링크 | 화면에 원문을 인용하지 않고 링크로 연결한다 |
| F4-8 계획서 작성 시작 | F5로 진입 |

### F5. 공고 분석 (계획서 1단계)

판정이 집필로 이어지는 지점이다. 배점과 자격 판정이 둘 다 있어야 나오는 출력이다.

| 기능 | 동작 |
|------|------|
| F5-1 결론 3줄 | 분석 결과를 세 줄로 먼저 말한다. 근거는 접어 둔다 |
| F5-2 심사 항목과 배점 정리 | 배점 높은 순으로 나열한다 |
| F5-3 목차 구조 파악 | PSST인지 자체 양식인지, 항목이 무엇인지 |
| F5-4 강조 지점 | 배점 큰 항목과 내 강점이 겹치는 곳을 지목한다 |
| F5-5 부족 정보 특정 | 초안을 쓰려면 필요한데 없는 것. 그대로 다음 단계 질문이 된다 |

### F6. 내용 채우기 (계획서 2단계)

| 기능 | 동작 |
|------|------|
| F6-1 부족 정보만 질문 | 이미 가진 정보는 묻지 않는다 |
| F6-2 질문별 배점 표기 | 이 답이 어느 심사 항목 몇 점에 쓰이는지 붙인다 |
| F6-3 기보유 정보 자동 채움 | 내 정보의 집필용 값을 채워 보여주고 고칠 수 있게 한다 |
| F6-4 강조축 선택 | 기술력, 시장성, 팀 역량 중 무엇을 앞세울지 |
| F6-5 금지 표현 지정 | 쓰지 않을 표현을 미리 받는다 |
| F6-6 건너뛰기 | 건너뛰면 그 항목이 일반 서술이 된다고 알린다 |
| F6-7 답변 누적 | 답이 내 정보에 저장되어 다음 공고에서 다시 묻지 않는다 |

### F7. 초안 작성 (계획서 3단계)

| 기능 | 동작 |
|------|------|
| F7-1 항목별 생성 | 심사 항목 단위로 나눠 쓴다. 배점 높은 순 |
| F7-2 스트리밍 출력 | 첫 출력까지 5초를 넘기지 않는다 |
| F7-3 사실 고정 | 금액, 자격, 마감일은 공고 데이터만 쓴다. 모델이 새로 만들지 않는다 |
| F7-4 항목 재생성 | 항목 단위로 다시 쓴다 |
| F7-5 사용자 수정 보존 | 손댄 문단은 재생성해도 덮지 않는다 |
| F7-6 2단계 답변 인라인 수정 | 이 화면에서 해당 항목의 2단계 답을 펼쳐 바로 고친다 |
| F7-7 분량 카운터 | 공고 분량 제한 대비 현재 분량 |

### F8. 문서 산출

| 기능 | 동작 |
|------|------|
| F8-1 미리보기 | 항목을 합쳐 문서 형태로 보여준다 |
| F8-2 누락 항목 체크 | 안 쓴 심사 항목을 알린다 |
| F8-3 파일 내보내기 | PDF로 내려받는다 |
| F8-4 책임 고지 | 최종 자격 확인과 제출은 사용자 책임임을 명시한다 |

### F9. 신청 현황

| 기능 | 동작 |
|------|------|
| F9-1 상태별 목록 | 검토 중, 준비 중, 작성 중, 제출 준비 완료, 제출함 |
| F9-2 마감 임박 경고 | D-7 이내 건을 화면 맨 위로 |
| F9-3 다음 할 일 | 각 건에서 지금 해야 할 하나를 명시하고 버튼을 붙인다 |
| F9-4 계획서 진행률 | 심사 항목 중 몇 개를 썼는지 |
| F9-5 상태 수동 전환 | 사용자가 직접 바꾼다. 제출 여부를 시스템이 판단하지 않는다 |

## 5. 이번에 뺀 것

되살릴 때를 위해 한 줄씩만 남긴다.

**판별 과정 노출.** 요건별 대조 표, 미충족 사유 문구, 확인 필요 3분류, 자격 표 인라인 보완, 판별 조건 칩. 판별은 뒷단에서 하고 화면은 결과만 받는다.

**운영 도구.** 사람 검수 큐, 정답 세트 관리 화면, 정확도 지표 대시보드, 링크 유효성 검사, 사용 로그. 수집·첨부 파싱·추출·신뢰도는 F0으로 들어왔다. 여기 남은 것은 **그 결과를 사람이 들여다보고 고치는 화면**이라 성격이 다르다. 판정 정확도를 무엇으로 어떻게 재는지는 별도 검증 문서에서 다룬다.

**계정과 과금.** 회원가입, 로그인, 건당 결제, 이용 내역.

**알림 발송.** 마감 알림 이메일과 카카오 알림톡. 화면 내 배지까지만 만든다.

**문서 고급 기능.** HWPX 지정 양식 적용, 도식 자동 생성, 표 자동 생성. `dev_research.md`에서 가능성을 확인한 뒤 다시 정한다.

**계획서 재활용.** 지난 계획서를 새 공고 배점과 양식에 맞춰 변환하는 기능. 반복 신청자에게 가치가 크지만 데모 시간이 없다.

**기타.** 캘린더 뷰, 참고자료 업로드, 가점 판정, 변경 이력.
