## 할 것

### F0-1 수집
출처별 어댑터. 기업마당과 K-Startup은 응답 형태가 완전히 다르므로 공통 인터페이스 뒤에 둔다. 콘텐츠 해시로 변경분만 갱신한다.

### F0-2 첨부 파싱

**지원 포맷 목록을 설정으로 관리한다.** → [T-0004](#t-0004-지원-포맷-목록-정의)

| 포맷 | 방식 | 추출률 |
|------|------|--------|
| HWP | OLE + raw deflate + 레코드 워크 | 100% |
| HWPX | ZIP + XML | 100% |
| DOCX | ZIP + XML | 100% |
| PDF | 텍스트 레이어 | 91% |
| ZIP | 미확인. 실측 표본에 27개 있었다 | — |
| XLSX | 미확인. 21개 | — |

**미지원 포맷과 파싱 실패를 조용히 넘기지 않는다.** 상태로 남겨 F0-6 신뢰도에 반영한다.

스캔 PDF(텍스트 레이어 없음)는 → [T-0007](#t-0007-스캔-pdf-처리-판단)

### F0-3 구조화 추출

**API 필드로 되는 것을 먼저 쓴다.** K-Startup이 업력·연령·지역·대상·마감일을 100% 준다. LLM을 부를 필요가 없다.

| 출처 | 방법 |
|------|------|
| 업력·연령·지역·대상·마감 | API 필드 직접 사용 |
| 제외 대상 | API 42.5% + 나머지는 공고문 |
| 평가 항목·평가 관점·단계·커트라인·가점 | 첨부에서 LLM 추출 |
| 배점 | 첨부에서 LLM 추출. **없는 것이 정상** |
| 양식 목차·세부항목·분량 제한 | 첨부에서 추출 |
| 제출 서류·유의사항 | 첨부에서 추출 |

**추출 스키마는 여기서 처음 설계한다.** 실제 창업 공고 문장을 보고 정한다.

## 태스크

### T-0004 지원 포맷 목록 정의

- 상태: 대기
- 선행: [T-0003](01-기반.md#t-0003-스택-확정)

F0-2가 다루는 첨부 포맷 목록을 **설정으로 관리**하고, 미지원·실패를 조용히 넘기지 않게 만든다. 확인된 포맷과 추출률은 위 F0-2 표에 있다.

**왜.** **실측 중 실제로 당했다.** DOCX 파서가 없어 초기창업패키지 첨부 20개 중 4개를 못 읽었고, 그 상태로 "배점이 없다"는 결론을 냈다. 파서를 붙여 다시 보니 결론은 같았지만 **바뀔 수도 있었다.**

창업진흥원은 사업계획서 양식을 HWP와 DOCX 두 벌로 붙인다. 포맷 하나가 빠지면 그 공고에 대한 판단이 통째로 틀릴 수 있다.

**완료 조건**

- 지원 포맷 목록이 코드가 아니라 설정에 있다
- **미지원 포맷을 만나면 기록에 남는다.** 조용히 건너뛰지 않는다
- 파싱 실패가 F0-6 신뢰도에 반영된다
- 공고 단위로 "첨부 N개 중 M개 해독"이 보인다

**건드리는 것** — `spec-extract.md`(이 단계에서 작성), 수집 파이프라인 설정

### T-0007 스캔 PDF 처리 판단

- 상태: 대기
- 선행: —

텍스트 레이어가 없는 스캔 PDF를 OCR로 읽을지, 미해독으로 남길지 정한다.

**왜.** 실측에서 PDF 추출 실패율이 9%(2/22)였고, 실패는 전부 4~5MB 스캔 이미지 PDF였다. 전체로는 5%다. **다만 표본에서 확인한 스캔 PDF 3건은 전부 K-Startup 회원가입·마이데이터 사용 매뉴얼이었다.** 평가 문서가 아니다. 이 비율이 일반적이라면 OCR 실익이 없다.

**확인할 것**

1. 스캔 PDF가 **어떤 종류의 문서**인지 더 넓은 표본에서 확인한다. 매뉴얼·안내물이 대부분인가, 공고문 본체도 섞이는가
2. 공고문 본체가 스캔으로 오는 비율
3. 그 비율이 유의미하면 OCR 비용과 정확도를 잰다

| 스캔 공고문 비율 | 결정 |
|------------------|------|
| 거의 없음 | OCR 안 한다. 미해독으로 기록만 남긴다 |
| 유의미함 | OCR 도입 검토. 다만 **한글 표 OCR 정확도**를 먼저 잰다 |

**미해독으로 남기더라도 조용히 넘기지 않는다.** F0-6 신뢰도에 반영하고, 그 공고는 L2 판정에서 보수적으로 다룬다([T-0004](#t-0004-지원-포맷-목록-정의)).

**완료 조건**

- 스캔 PDF의 문서 종류 분포를 잰다
- OCR 도입 여부를 정하고 이유를 남긴다

**건드리는 것** — `spec-extract.md`(이 단계에서 작성), 결정이 크면 `adr/` 새 문서

### T-0005 배점 명시율 재검증

- 상태: 대기
- 선행: —

창업 분야 배점표 명시율 **25%**를 더 큰 표본으로 다시 잰다.

**왜.** 25%는 **40건 표본**에서 나온 값이다. 방향을 정하기엔 충분하지만 설계 근거로 쓰기엔 얇다. [ADR-0010](../adr/0010-배점-전제-폐기.md)의 대체 설계 선택이 이 숫자에 걸려 있다. 특히 3안(배점 주는 공고로 타깃 축소)을 고른다면 **25%가 타깃 시장 크기 그 자체**가 된다.

**탐지기 주의 — 이 작업의 진짜 난점은 표본 크기가 아니라 탐지 정밀도다.** 실측에서 탐지기를 세 번 고쳤다.

| 방식 | 결과 | 문제 |
|------|------|------|
| `배점` 키워드 + 점수 3개 이상 | 30% | 오탐 많음. 일정표 숫자를 잡았다 |
| 위 + 부분합 100 | 45% | **더 나쁨.** 숫자 많은 창에서 우연히 맞는 조합이 거의 항상 나온다 |
| **`배점`이 표의 열 머리글인 구조** | **25%** | 10건 육안 검증 오탐 0 |

**세 번째 방식만 신뢰한다.** 재검증도 이 방식으로 하고, 표본이 커져도 **육안 검증을 건너뛰지 않는다.**

**완료 조건**

- 표본 150건 이상
- 육안 검증 비율을 명시한다 (전수가 아니면 몇 건을 봤는지)
- 출처별·기관 유형별 분포를 낸다. 실측에서 **지자체·경진대회는 주고 중앙부처 패키지는 안 주는** 경향이 보였다
- 결과를 `adr/evidence/`에 남기고 `SPEC.md` §8을 갱신한다

**건드리는 것** — `adr/evidence/` 새 문서 또는 기존 문서 갱신, `SPEC.md` §8 확인된 사실, `adr/0010-배점-전제-폐기.md`
