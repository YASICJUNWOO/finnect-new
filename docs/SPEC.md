## 1. 제품

### 1.1 한 줄 정의

가진 파일을 통째로 던지면 **내 사업 위키**가 만들어지고, 그 위키로 **맞는 공고를 골라 주고**, 들어가면 **문서가 이미 써져 있다.**

### 1.2 왜 이걸 쓰는가

기준 질문은 "Claude에 직접 넣는 것보다 뭐가 나은가"다. 답은 위키다.

공고를 붙여넣으면 그 공고 하나에만 답하고 매번 내 사업을 다시 설명해야 한다. 구조화된 사업 정보를 갖고 있으면 둘을 할 수 있다.

1. **수백 건을 한 번에 대조한다.** 공고를 하나씩 열어보지 않아도 된다.
2. **설명하지 않아도 문서가 써진다.** 이미 알고 있기 때문이다.

그리고 쓸수록 위키가 두꺼워져 다음 공고는 더 잘 써진다. §3 그림의 되먹임 화살표가 그것이다.

### 1.3 대상

창업 3년 이내 사업자. 디자인 도구를 쓰지 않고, 화면을 오래 들여다보지 않으며, 판단을 빨리 끝내고 싶어 한다.

### 1.4 원칙

1. **위키가 뿌리다.** 다른 기능은 전부 위키에서 나온다. 위키가 없으면 추천도 집필도 성립하지 않는다.
2. **자격과 적합도를 섞지 않는다.** 자격은 못 넘으면 끝이고 적합도는 정도의 문제다. 하나로 합치면 "자격 미달인데 취지가 잘 맞는" 공고가 생긴다([ADR-0013](adr/0013-판정-두-층.md)).
3. **자격 판별은 안 보인다.** 못 넘은 공고는 화면에 올리지 않는다. 요건 대조표를 두지 않는다([ADR-0003](adr/0003-판별-비노출.md)).
4. **적합도는 이유와 함께만 내보낸다.** 이유가 없으면 추천이 아니라 목록이다.
5. **확률을 말하지 않는다.** 선정 결과가 공개되지 않아 근거 데이터가 없다. 화면에서 확률이라는 말을 쓰지 않는다.
6. **사용자가 손대기 전에 문서가 써져 있다.** 생성 버튼을 누르게 하지 않는다.
7. **모든 값에 출처를 매단다.** 나중에 붙이는 것은 불가능하다([ADR-0014](adr/0014-통합-그래프와-근거-청크.md)).
8. **대행하지 않는다.** 목표는 문서 완성이지 제출이 아니다.

### 1.5 무엇으로 재는가

**핵심 지표는 "제출까지 걸린 시간"이 아니라 "사용자가 손댄 분량"이다.** 아무것도 안 채워도 문서가 몇 퍼센트 차 있는가로 본다.

이 제품은 FIN:NECT 챌린지 본선 출품작이고 배점이 설계에 걸린다. 문제정의·혁신성 20 · **MVP 완성도 30** · 시장·수익성 20 · 기술 확장성 20 · 참여도 10이다. 기술 배점이 40에서 20으로 줄었으므로 **파이프라인의 정교함을 자랑하는 데 시간을 쓰지 않는다.** 파이프라인은 근거로 쓰고 그것이 만드는 경험을 시연으로 보인다.

### 1.6 범위

파일 업로드부터 제출 가이드까지다. 계정·과금, 알림 발송, 제출 대행, 사람이 쓰는 운영 도구는 제외한다. 뺀 목록은 6장에 있다.

## 2. 데이터 계층

환각 방지는 프롬프트가 아니라 **계층 분리**로 한다. 계층마다 무엇을 생성해도 되는지가 다르다.

| 계층 | 하는 일 | 생성 권한 | 기능 |
|------|---------|-----------|------|
| **D 문서** | 올린 파일 → 위치정보(파일·쪽·표 좌표)를 품은 청크 | **없음** | F1-1 |
| **W 위키** | 청크 → 구조화 노드. **값마다 근거 청크를 매단다** | **없음.** 추출과 병합만 | F1 |
| **P 공고** | 공고 본문·첨부 → 요건·취지·양식·지침·제약 | **없음** | F2 |
| **M1 자격** | 위키 사업체 정보 + 공고 요건 → 통과·탈락 | **없음.** 대조와 계산만. **LLM을 거치지 않는다** | F3-1 |
| **M2 적합도** | 위키 사업 내용 + 공고 취지 → 순서와 이유 | **이유 한 줄만** | F3-2 |
| **G 집필** | 노드에 매달린 근거 청크 + 공고 양식·지침 → 초안 | **문장만.** 수치·고유명사는 청크와 공고 데이터에서만 | F6 |

세 가지가 이 표를 묶는다.

1. **통합 그래프 하나가 허브다.** 위키 시각화·매칭·집필이 같은 소스를 쓴다. 소스가 갈라지면 불일치가 생긴다.
2. **모든 값에 출처를 매단다.** 노드 원문 보기, 문단별 근거 표시, 환각 방지를 한 번에 푼다.
3. **검색은 집필에서만 한다.** 대상은 **오직 사용자 본인 문서**다. per-user 격리가 필수다.

근거는 [ADR-0013](adr/0013-판정-두-층.md) · [ADR-0014](adr/0014-통합-그래프와-근거-청크.md). v1의 L1/L2/L3는 [ADR-0002](adr/0002-3계층-분리.md)가 정의했고 이 표로 대체됐다.

### 2.1 M1이 LLM을 거치지 않는 이유

같은 프로필과 같은 공고에 항상 같은 답이 나와야 한다. 판정에 확률적 요소가 들어가면 "어제는 된다더니 오늘은 안 된다"가 생긴다.

대가로 **M1이 다룰 수 없는 요건이 생긴다.** 자유 텍스트로만 서술된 조건은 규칙으로 표현되지 않는다. 이때는 LLM 폴백으로 판정하되 **"확인 필요"로 표시하고 확정으로 다루지 않는다.**

**규칙으로 안 떨어지는 요건이 얼마나 되는지는 아직 모른다.** 첨부를 파싱해 보고 판단한다. 비정형 요건이 많으면 방식을 다시 정한다.

## 3. 동작 순서

```
   [ 사용자가 가진 파일 뭉치 ]
     사업계획서·IR·소개서·재무제표·메모, 무엇이든
              │
              ▼
   F1  사업 위키 구축            ◀─────────────────┐
       파일을 읽어 항목으로 쪼개고 잇는다            │
              │                                    │
              ▼                                    │ 적립
   F3  자격 판별 + 적합도 판정                       │
       자격은 결정론, 적합도는 취지 대조              │
              │                                    │
              ▼                                    │
   F4  추천                                         │
       맞는 것 소수 + 왜 맞는지 한 줄                 │
              │                                    │
              ▼ 공고 선택                           │
   F5  공고 상세                                    │
              │                                    │
              ▼                                    │
   F6  문서 자동 완성  ◀── 위키에서 끌어와 이미 써짐  │
       못 채운 곳만 표시 ──── 사용자가 채운 답 ───────┘
              │
              ▼
   F7  제출 가이드      F8  신청 현황
```

**오른쪽 화살표가 제품의 전부다.** 사용자가 채운 답이 위키로 돌아가 쌓이고, 다음 공고에서는 그만큼 덜 묻는다.

F2 공고 데이터 처리는 화면이 없어 그림에서 뺐다. F3의 입력이 된다.

## 4. 기능

기능 번호는 v2 체계다. v1의 F0~F9와 대응하지 않는다([ADR-0012](adr/0012-v2-피봇-사업-위키.md)).

### F1. 사업 위키

제품의 뿌리다. 다른 모든 기능이 여기서 나온다.

#### F1-1. 구축

| ID | 동작 |
|----|------|
| F1-1-1 파일 통째로 받기 | 형식 구분 없이 여러 개 한 번에 받는다. 분류해서 올리라고 요구하지 않는다 |
| F1-1-2 원본 보관 | 올린 파일은 그대로 둔다. 추출 결과와 분리한다 |
| F1-1-3 청크로 쪼개기 | 파일 타입별로 나눠 처리하고 **위치정보(파일·쪽·표 좌표)를 보존한다** |
| F1-1-4 항목으로 구조화 | 청크에서 사업 정보를 항목 단위로 뽑는다. 항목 목록은 F1-2 |
| F1-1-5 근거 매달기 | 각 노드가 자기 근거가 되는 청크를 직접 들고 있다 |
| F1-1-6 항목 간 연결 | 관련 있는 항목을 서로 잇는다 |
| F1-1-7 충돌 표시 | 여러 파일에서 다른 값이 나오면 **둘 다 보관하고** 어느 쪽을 쓸지 묻는다 |
| F1-1-8 파일별 독립 처리 | 파일 하나가 실패해도 나머지는 진행한다. 전체를 한 트랜잭션으로 묶지 않는다 |
| F1-1-9 구축 진행 표시 | 무엇이 채워지고 있는지 실시간으로 보여준다 |

**F1-1-8이 실패 설계의 핵심이다.** 상태는 파일 단위로 `uploaded → parsing → extracting → linking → needs_review / done / failed`를 돈다. 일시 오류는 재시도 큐로, 파서가 못 읽는 파일은 사용자에게 반송한다. 화면에는 "4개 완료, 1개 실패(재업로드)"로 나온다.

**F1-1-3은 타입별로 완전히 다르다.** 조용히 가장 많이 실패하는 구간이다.

| 타입 | 처리 |
|------|------|
| 텍스트 PDF (IR·소개서) | 텍스트 레이어 추출 |
| 스캔 PDF·이미지 (사업자등록증) | **OCR 필수.** 등록증은 거의 사진이다 |
| **HWP · HWPX** | **전용 파서 필수.** 정부·창업판 문서는 HWP가 지배적이다 |
| XLSX (재무제표) | **표 구조와 셀 좌표 보존.** 뭉개면 연도-항목-값 대응이 깨진다 |
| DOCX · PPTX | 텍스트 + 표 |

#### F1-2. 위키가 담는 것

두 묶음이다. 쓰임이 다르다.

| 묶음 | 항목 | 쓰임 |
|------|------|------|
| **사업체 정보** (5) | 사업자 정보, 소재지, 업종, 대표자, 수령 이력 | **M1 자격 판별**의 입력. 정형 |
| **사업 내용** (9) | 문제 인식, 솔루션과 기술, 목표 고객, 시장과 경쟁, **지역 연계**, 매출과 성과, 팀 구성, 로드맵, 자금 현황 | **M2 적합도**와 **G 집필**의 입력. 서술 |

여기에 **정체성** 노드 하나가 따로 있다. 사업 한 줄 정의이고 그래프의 중심이다. 합쳐서 열다섯이다.

**업력과 만 나이는 저장하지 않고 계산한다.** 공고마다 기준일이 다르다(공고일 기준 · 신청일 기준). "업력 1년 4개월"을 저장하면 어느 시점 기준인지 알 수 없어 판정이 틀린다. 사업자등록일과 생년월일만 두고 판정 시점에 계산한다.

#### F1-3. 노드 한 장

항목 하나가 문서 한 장이다. 머리말과 본문, 그리고 **자기 근거가 되는 원문 조각**으로 이뤄진다.

```
─────────────────────────────────────────
 종류    솔루션
 제목    재고관리 자동화 소프트웨어
 상태    확정
 태그    기술, 개발단계
 갱신    2026-08-15
─────────────────────────────────────────
 본문
 바코드와 QR로 입출고 기록을 자동으로 남긴다.
 현재 1단계 모듈 프로토타입 개발을 마쳤다.

 근거 2                              ← 펼치면 원문 조각
 ▸ 2025_초기창업패키지_사업계획서.hwp  12쪽 · 기술 구현
 ▸ 회사소개서_v3.docx                 4쪽 · 제품

 관련  → 목표 고객   → 경쟁 제품   → 팀 구성
─────────────────────────────────────────
```

**출처는 문자열이 아니라 연결이다.** 파일명과 쪽수를 글자로 적으면 사람이 원본을 다시 열어야 확인된다. 노드가 청크를 직접 들고 있으면 그 자리에서 읽힌다.

**충돌이 잡힌 노드는 어긋난 근거를 나란히 펼친다.** 어느 쪽이 맞는지 고르는 일이라 둘을 같이 봐야 한다.

이 형태는 임의로 정한 것이 아니다. 마크다운 본문에 머리말을 얹고 문서끼리 링크로 잇는 구조는 옵시디언과 llm-wiki가 공통으로 쓰고, 2026년 6월 구글이 **Open Knowledge Format**으로 표준화한 것과 같다.

#### F1-4. 관리

**옵시디언에서 볼트를 다루는 감각으로 만든다.**

| ID | 동작 |
|----|------|
| F1-4-1 연결 구조 보기 | 노드가 어떻게 이어져 있는지 그림으로 본다. 배치는 [ADR-0017](adr/0017-위키-그래프-궤도-배치.md) |
| F1-4-2 채움 상태 | 채워진 노드, 빈 노드, 손봐야 할 노드를 구분한다 |
| F1-4-3 노드 상세 | F1-3의 한 장을 연다 |
| F1-4-4 역참조 | 이 노드를 가리키는 다른 노드를 보여준다 |
| F1-4-5 직접 수정 | 본문과 머리말을 그 자리에서 고친다 |
| F1-4-6 노드 추가 | 빈손으로 새 노드를 만든다 |
| F1-4-7 원본 파일 목록 | 올린 파일과 각 파일이 만든 노드를 잇는다 |
| F1-4-8 파일 추가 | 나중에 더 올려 위키를 두껍게 한다 |
| F1-4-9 변경 이력 | 언제 무엇이 어디서 들어왔는지 시간순으로 |

**검색은 넣지 않는다.** 노드가 열다섯이라 화면 하나에 다 보인다. **100개를 넘으면 검색과 목록을 같이 다시 이야기한다.** 목차 화면도 같은 이유로 폐기했다.

#### F1-5. 정리

**LLM이 위키를 훑어 손봐야 할 곳을 찾아준다.** 이게 없으면 위키는 금세 지저분해지고 안 쓰이게 된다.

| ID | 동작 |
|----|------|
| F1-5-1 모순 찾기 | 서로 어긋나는 내용을 짚는다 |
| F1-5-2 오래된 내용 찾기 | 갱신일이 지난 노드를 짚는다. 매출·팀 구성처럼 자주 바뀌는 항목 우선 |

**하지 않는 것.** 합격 확률을 예측하지 않는다. 점수 하나로 뭉뚱그리지 않는다. 화면에서 확률이라는 말을 쓰지 않는다.

**적합도 숫자와 막대를 화면에 두지 않는다.** 목록이 이미 적합도순이므로 순서가 정보를 담는다. 근거는 [`../DESIGN.md`](../DESIGN.md) §6.

### 5.1 정보구조

### 5.3 내 사업(S7)의 구성

탭 셋에 겹치는 패널 둘이다.

| 탭 | 담는 것 |
|----|---------|
| **궤도** | 노드가 어떻게 이어져 있는지. 기본 탭 |
| **원본 파일** | 파일과 그 파일이 만든 노드 |
| **변경 이력** | 언제 무엇이 어디서 들어왔는지 |

궤도 위에 **정리 패널**(F1-5)과 **노드 상세 패널**(F1-3)이 겹쳐 뜬다. 둘 다 궤도에서 위치를 확인하며 보는 것이 자연스러워 별도 탭으로 두지 않는다.

### 5.4 위키 관리에 화면을 따로 주는 이유

1. **차별점이 눈에 보여야 한다.** 위키가 있다고 말로만 하면 안 산다.
2. **관리하지 않으면 썩는다.** 파일에서 뽑은 정보는 서로 어긋나고 낡는다.
3. **신뢰가 여기서 생긴다.** 문서가 자동으로 써지는 것이 마법처럼 보이면 오히려 못 믿는다. 어떤 정보를 근거로 썼는지 열어볼 수 있어야 한다.

## 6. 범위 밖

되살릴 때를 위해 한 줄씩만 남긴다.

**제출 대행.** 행정사 업역과 법적 책임 문제를 열지 않는다. 규제 경계 확인 후 다시 판단한다.

**합격 확률 예측.** 근거 데이터가 없다. 적합도로 대체한다.

**자격 판별 과정 노출.** 요건별 대조 표, 미충족 사유 문구, 판별 조건 칩. → [ADR-0003](adr/0003-판별-비노출.md)

**운영 도구.** 사람 검수 큐, 정답 세트 관리, 정확도 대시보드, 링크 유효성 검사, 사용 로그. 수집·파싱·추출은 F2로 들어왔다. 여기 남은 것은 **그 결과를 사람이 들여다보고 고치는 화면**이다.

**계정과 과금.** 회원가입, 로그인, 결제.

**알림 발송.** 마감 알림 이메일과 알림톡. 화면 내 배지까지만.

**문서 고급 기능.** HWPX 지정 양식 적용, 도식 자동 생성, 자금계획 표 자동 작성. 자금계획 표는 실물 양식의 필수 요소라 다음 순위 후보다.

**위키 검색과 목차.** 노드 100개를 넘으면 다시 이야기한다.

**빠진 연결 제안 · 중복 병합 제안.** F1-5에서 뺐다.

**시장 규모 산정.** 발표 자료 영역으로 분리했다.

### 8.1 이 사실들이 설계를 바꾸는 곳 넷

**1. 배점이 없다 → F2-9와 F6은 배점에 기대지 못한다.** 집필의 축은 양식 목차와 작성 지침이다([ADR-0019](adr/0019-집필의-축을-양식으로.md)). 배점이 있으면 쓰고 없으면 안 쓴다. **배점 순 정렬과 배점 기반 분량 배분을 전제한 기능을 만들지 않는다.**

**2. 마감일의 절반 이상이 날짜가 아니다 → 스키마가 이를 표현해야 한다.** `deadline: 'YYYY-MM-DD'` 하나로는 기업마당의 57%를 담지 못한다. D-day 계산, 마감 임박 강조(F4-5), 마감 카운트다운(F7-2)이 전부 이 위에 선다. **날짜가 없는 것이 정상 상태다.**

**3. 첨부 파싱은 이미 가능한 것이 확인됐다.** 추출률 95%다. 기획 문서가 "HWP 파싱 가능성"을 아직 조사 과제로 두고 있으나 이미 실측됐다. **창업진흥원은 사업계획서 양식을 HWP와 DOCX 두 벌로 붙인다. 포맷 하나를 빠뜨리면 그 공고 판단이 통째로 틀린다.**

**4. 공고 건수도 이미 적재돼 있다.** 세는 것은 쿼리 한 번이다. 다만 **1년치로 자르는 것과 지역 분포는 아직 안 돌렸다.**
