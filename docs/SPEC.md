## 1. 제품

### 1.1 한 줄 정의

내 사업 정보로 **신청 가능한 공고를 판정**하고, 그 판정 결과를 **공고가 요구하는 사업계획서 초안**으로 잇는다.

핵심은 판정과 집필을 잇는 연결이다. 둘 중 하나만 있으면 이미 있는 서비스다.

### 1.2 대상

초기창업자. 사업자등록을 마쳤고 정부 창업지원사업에 신청할 의사가 있는 사람이다.

### 1.3 범위

공고 원문을 데이터로 만드는 파이프라인(F0)부터 화면 기능(F1~F9)까지다.
계정·과금, 알림 발송, 사람이 쓰는 운영 도구는 아직 제외한다. 뺀 목록은 6장에 있다.

### 1.4 원칙

1. **판별은 안 보인다.** 판정 과정과 근거를 화면에 늘어놓지 않는다. 목록에 오른 것 자체가 판정 결과다.
2. **공고는 구조로 보여준다.** 원문을 옮기지 않고 항목으로 나눈다. 원문 확인은 링크로 넘긴다.
3. **결론 먼저, 근거는 접는다.**
4. **집필은 세 번에 나눠 한다.** 분석하고, 묻고, 쓴다.
5. **확정 어투를 쓰지 않는다.** 최종 확인과 제출은 사용자 몫이다.
6. **대행하지 않는다.** 초안 작성을 돕는 것이지 대신 신청해 주는 것이 아니다.

## 2. 데이터 계층

이 제품의 환각 방지는 프롬프트가 아니라 **계층 분리**로 한다. 계층마다 무엇을 생성해도 되는지가 다르다.

| 계층 | 하는 일 | 생성 권한 |
|------|---------|-----------|
| **L1 추출** | 공고 원문 → 구조화 데이터 (요건, 금액, 기간, 서류, 평가) | **없음.** 원문에서 가져오기만 한다 |
| **L2 판별** | 프로필 + L1 → 신청 가능 여부 | **없음.** 대조하고 계산만 한다. LLM을 거치지 않는다 |
| **L3 집필** | L1 + 프로필 + 사용자 답변 → 계획서 초안 | **문장만.** 금액·자격·마감일은 L1 값을 인용한다 |

기능과의 대응은 **F0 = L1, F2 = L2, F5~F8 = L3**이다.

근거는 [ADR-0002](adr/0002-3계층-분리.md).

### 2.1 화면별 계층과 생성 금지

| 화면 | 쓰는 계층 | 이 화면이 생성하지 않는 것 |
|------|-----------|---------------------------|
| S8 내 정보 | 사용자 입력 | 없음 |
| S1 지원사업 리스트 | L2 | 자격 문구를 생성하지 않는다 |
| S2 공고 상세 | L1 | 요건, 금액, 마감일, 평가 항목, 서류를 생성하지 않는다. 지원 내용 개요만 정제 허용 |
| S3 공고 분석 | L1 + L2 | 분석 서술은 생성하되 수치와 판정은 계층 출력만 인용 |
| S4 내용 채우기 | 사용자 입력 | 없음 |
| S5 초안 작성 | L3 | 금액, 자격, 마감일을 생성하지 않는다 |
| S6 문서 산출 | S5 결과 | 없음 |
| S7 신청 현황 | L2 + 사용자 상태 | 마감일을 생성하지 않는다 |

## 3. 동작 순서

판별에는 입력이 둘 필요하다. 공고 쪽 입력을 만드는 것이 F0이고 사용자 쪽 입력이 F1이다.

```
F0 공고 데이터 파이프라인            F1 내 정보
   수집 → 파싱 → 추출 → 색인            사용자 입력
   화면 없음                            │
   │                                    │
   └────────────────┬───────────────────┘
                    ▼
             F2 자격 판별  ← 화면 없음. 엔진이 전체 공고를 판정한다
                    │
                    ▼
             F3 지원사업 리스트  ← 판정 결과가 곧 목록이다
                    │
                    ▼ 아이템 클릭
             F4 공고 상세  ← 잘 정리된 요강
                    │
                    ▼ 계획서 쓰기
             F5 공고 분석 → F6 내용 채우기 → F7 초안 작성 → F8 문서 산출
                    │
                    ▼
             F9 신청 현황
```

## 4. 기능

### F0. 공고 데이터 파이프라인

**화면이 없는 기능이다.** 공고 원문을 F2가 판정할 수 있는 구조로 만든다. 출력이 L1이다.

| ID | 동작 |
|----|------|
| F0-1 공고 수집 | 출처 API에서 공고 목록과 본문을 받는다. 콘텐츠 해시로 변경분만 갱신한다 |
| F0-2 첨부 파싱 | 첨부 문서를 내려받아 텍스트로 만든다. **지원 포맷 목록을 명시적으로 관리한다** |
| F0-3 구조화 추출 | 본문과 첨부에서 자격 요건, 지원 규모, 접수 기간, 평가 항목, 제출 서류, 유의사항, 분량 제한을 스키마에 맞춰 뽑는다 |
| F0-4 교정 루프 | 비었거나 스키마를 벗어난 항목은 해당 원문 구간을 다시 읽어 재추출한다 |
| F0-5 근거 구간 보존 | 추출한 값마다 원문의 어느 구간에서 나왔는지 남긴다 |
| F0-6 추출 신뢰도 | 항목별 확신도를 남긴다. 낮은 항목은 F2에서 보수적으로 다룬다 |
| F0-7 색인 갱신 | 추출 결과를 판정 가능한 형태로 적재한다. 갱신되면 F2 재판정 대상이 된다 |

**F0-2는 뺄 수 없다.** 평가 정보는 공고 본문에 전혀 없다. 실측에서 기업마당 본문 0/200건, K-Startup 본문 0/200건이었다. 첨부를 안 열면 평가 관련 데이터가 0이다.

**F0-2의 지원 포맷 목록은 결론을 바꾼다.** 실측 중 DOCX 파서가 없어 첨부의 20%를 통째로 놓쳤다. 창업진흥원은 사업계획서 양식을 HWP와 DOCX 두 벌로 붙인다. 포맷 하나가 빠지면 그 공고에 대한 판단이 통째로 틀릴 수 있다.

**F0-5가 F7-3의 근거다.** 사실 고정은 모델에게 지어내지 말라고 지시해서 되는 것이 아니라, 쓸 수 있는 값의 출처를 데이터가 들고 있어야 성립한다.

근거는 [ADR-0008](adr/0008-제품-범위-확대.md), 실측은 [evidence](adr/evidence/2026-08-16-첨부파싱-배점실측.md).

### F1. 내 정보

| ID | 동작 |
|----|------|
| F1-1 판별용 정보 | 사업자 형태, 사업자등록일, 대표자 생년월일, 소재지, 업종, 정부지원사업 수령 이력 |
| F1-2 집필용 정보 | 문제 인식, 솔루션, 목표 고객, 매출과 성과, 성장 전략, 팀 구성 |
| F1-3 수정과 재판정 | 판별용 값을 고치면 전체 공고를 다시 판정한다 |

두 묶음은 탭으로 나눈다. 각 묶음 위에 무엇에 쓰이는지 한 줄로 적는다.

### F2. 자격 판별

**화면이 없는 기능이다.** 판정 결과가 곧 F3 리스트다. 판정 과정과 근거를 사용자에게 보여주지 않는다.

| ID | 동작 |
|----|------|
| F2-1 요건 대조 판정 | 프로필과 공고 요건을 대조한다. 업력, 연령, 소재지, 업종, 결격 사유, 중복 수령 제한을 모두 요건의 한 종류로 다룬다 |
| F2-2 파생 값 계산 | 사업자등록일에서 신청일 기준 업력을, 생년월일에서 만 나이를 계산한다. 공고마다 기준일이 달라 저장값을 그대로 쓰면 틀린다 |
| F2-3 결정론 보장 | LLM을 거치지 않는다. 같은 입력에 항상 같은 판정이 나온다 |
| F2-4 전체 재판정 | 프로필이 바뀌면 색인 전체를 다시 판정한다 |

**요건 데이터의 상당량은 이미 구조화돼 있다.** K-Startup API가 업력·연령·지역·대상·마감일을 100% 채워서 준다. 제외 대상만 42.5%다. F0-3의 부담이 예상보다 작다.

근거는 [ADR-0003](adr/0003-판별-비노출.md).

### F3. 지원사업 리스트

| ID | 동작 |
|----|------|
| F3-1 신청 가능 공고만 노출 | F2가 가능으로 판정한 공고만 올린다 |
| F3-2 행 정보 | 사업명, 주관기관, 출처 구분, 마감까지 남은 일수, 지원 규모 |
| F3-3 마감 임박 순 정렬 | 기본 정렬. D-7 이내는 강조한다 |
| F3-4 출처 필터 | 전체, 중앙부처, 지자체 |
| F3-5 준비 시작 | 이 공고를 신청 현황에 넣는다 |

빈 상태에서는 내 정보를 채우면 판단할 수 있는 공고가 늘어난다고 안내한다.

### F4. 공고 상세

공고 요강을 읽기 좋게 정리한 화면이다. 원문을 옮기지 않고 항목으로 나눈다.

| ID | 동작 |
|----|------|
| F4-1 개요 | 사업명, 주관기관, 접수 기간, 마감, 지원 규모, 접수 방법 |
| F4-2 지원 내용 | 무엇을 얼마나 어떤 기간에 주는지 |
| F4-3 신청 자격 | 공고가 요구하는 자격 요건 목록. **내 값과 판정을 넣지 않는다** |
| F4-4 제출 서류 | 서류명과 지정 양식 여부. 양식 미준수 탈락 조건은 강조한다 |
| F4-5 심사 방식 | 평가 단계와 항목. **배점은 공고가 줄 때만 표시한다** |
| F4-6 유의사항 | 제출 후 수정 불가처럼 탈락으로 이어지는 조항 |
| F4-7 원본 공고 링크 | 화면에 원문을 인용하지 않고 링크로 연결한다 |
| F4-8 계획서 작성 시작 | F5로 진입 |

### F5. 공고 분석 (계획서 1단계)

판정이 집필로 이어지는 지점이다.

| ID | 동작 |
|----|------|
| F5-1 결론 3줄 | 분석 결과를 세 줄로 먼저 말한다. 근거는 접어 둔다 |
| F5-2 심사 항목 정리 | 공고가 요구하는 평가 항목과 각 항목의 평가 관점 |
| F5-3 목차 구조 파악 | 지정 양식의 항목·세부항목과 분량 제한 |
| F5-4 강조 지점 | 항목별 요구와 내 강점이 겹치는 곳을 지목한다 |
| F5-5 부족 정보 특정 | 초안을 쓰려면 필요한데 없는 것. 그대로 다음 단계 질문이 된다 |

> ⚠️ **F5-2와 F5-4는 재작성 대기 중이다.** 원래 "배점 높은 순으로 나열"과 "배점 큰 항목과 겹치는 곳"이었으나, 실측 결과 주요 공고가 배점을 공개하지 않는다. 위 문구는 배점 의존을 걷어낸 잠정안이고, 확정 설계는 [ADR-0010](adr/0010-배점-전제-폐기.md)에서 정한다. **미결이다.**

### F6. 내용 채우기 (계획서 2단계)

| ID | 동작 |
|----|------|
| F6-1 부족 정보만 질문 | 이미 가진 정보는 묻지 않는다 |
| F6-2 질문의 쓰임 표기 | 이 답이 어느 심사 항목에 쓰이는지 붙인다 |
| F6-3 기보유 정보 자동 채움 | 내 정보의 집필용 값을 채워 보여주고 고칠 수 있게 한다 |
| F6-4 강조축 선택 | 기술력, 시장성, 팀 역량 중 무엇을 앞세울지 |
| F6-5 금지 표현 지정 | 쓰지 않을 표현을 미리 받는다 |
| F6-6 건너뛰기 | 건너뛰면 그 항목이 일반 서술이 된다고 알린다 |
| F6-7 답변 누적 | 답이 내 정보에 저장되어 다음 공고에서 다시 묻지 않는다 |

> ⚠️ **F6-2도 재작성 대기 중이다.** 원래 "질문별 배점 표기"였다. [ADR-0010](adr/0010-배점-전제-폐기.md) 참조.

### F7. 초안 작성 (계획서 3단계)

| ID | 동작 |
|----|------|
| F7-1 항목별 생성 | 심사 항목 단위로 나눠 쓴다 |
| F7-2 스트리밍 출력 | 첫 출력까지 5초를 넘기지 않는다 |
| F7-3 사실 고정 | 금액, 자격, 마감일은 공고 데이터만 쓴다. 모델이 새로 만들지 않는다 |
| F7-4 항목 재생성 | 항목 단위로 다시 쓴다 |
| F7-5 사용자 수정 보존 | 손댄 문단은 재생성해도 덮지 않는다 |
| F7-6 2단계 답변 인라인 수정 | 이 화면에서 해당 항목의 2단계 답을 펼쳐 바로 고친다 |
| F7-7 분량 카운터 | 공고 분량 제한 대비 현재 분량. 초기창업패키지는 15페이지 내외다 |

F7-3은 백엔드 규칙으로만 존재한다. 화면에 표시하지 않는다. 근거는 [ADR-0006](adr/0006-사실고정-화면-미표시.md).

### F8. 문서 산출

| ID | 동작 |
|----|------|
| F8-1 미리보기 | 항목을 합쳐 문서 형태로 보여준다 |
| F8-2 누락 항목 체크 | 안 쓴 심사 항목을 알린다 |
| F8-3 파일 내보내기 | PDF로 내려받는다 |
| F8-4 책임 고지 | 최종 자격 확인과 제출은 사용자 책임임을 명시한다 |

### F9. 신청 현황

| ID | 동작 |
|----|------|
| F9-1 상태별 목록 | 검토 중, 준비 중, 작성 중, 제출 준비 완료, 제출함 |
| F9-2 마감 임박 경고 | D-7 이내 건을 화면 맨 위로 |
| F9-3 다음 할 일 | 각 건에서 지금 해야 할 하나를 명시하고 버튼을 붙인다 |
| F9-4 계획서 진행률 | 심사 항목 중 몇 개를 썼는지 |
| F9-5 상태 수동 전환 | 사용자가 직접 바꾼다. **제출 여부를 시스템이 판단하지 않는다** |

### 5.3 화면별 흐름

**S1 지원사업 리스트.** 서비스 기본 화면이다. 상단에 "신청할 수 있는 공고 N건" 한 줄, 아래에 판정 통과 공고만 행으로 나열. 기본 정렬은 마감 임박 순. 출처 필터(전체/중앙부처/지자체)와 행 우측 준비 시작 버튼. 행 본문 클릭 시 S2.

**S2 공고 상세.** 위에서 아래로 여섯 블록이다. 개요 → 지원 내용 → 신청 자격 → 제출 서류 → 심사 방식 → 유의사항. 하단에 계획서 쓰기 버튼 고정. **신청 자격 블록에 내 값이나 판정을 넣지 않는다.** 이 화면은 공고를 설명하는 화면이지 나를 심사하는 화면이 아니다.

**S3 계획서 공고 분석.** 진입 즉시 분석이 돈다. 결론 3줄을 먼저 띄우고 나머지 블록은 접힌 상태. 5번 블록(아직 모르는 것)이 다음 화면의 질문이 된다.

**S4 계획서 내용 채우기.** 세 묶음이다. 사업 내용(부족한 항목만) → 원하는 방향(강조축·금지 표현) → 참고. 질문마다 어느 심사 항목에 쓰이는지 한 줄로 붙인다. 건너뛰기를 허용하고 그 결과를 알린다.

**S5 계획서 초안 작성.** 메인을 2분할한다. 좌측 항목 네비(항목명·작성 상태), 우측 에디터. 에디터 상단에 얇은 컨텍스트 바(항목명·분량·원문 링크·2단계 답변 펼치기). 초안은 스트리밍. 사용자가 직접 고친 문단은 재생성해도 덮지 않는다. 실패는 항목 단위로 처리하고 만든 항목은 유지한다.

**S6 문서 산출.** 심사 항목 순서로 합쳐 미리보기 → 안 쓴 항목 알림 → 책임 고지 → PDF 내려받기. 완료 시 신청 현황 상태를 바꿀지 묻는다.

**S7 신청 현황.** 최상단 마감 임박 경고(D-7 이내), 아래 상태별 그룹. 각 행에 사업명·D-day·진행률·**다음 할 일과 버튼**. 다음 할 일 열이 이 화면의 존재 이유다. 없으면 즐겨찾기와 다를 게 없다.

**S8 내 정보.** 두 탭. 개인정보 / 사업 정보(판별용 + 집필용 두 묶음). 인라인 편집. 판별용 항목을 고치면 전체 재판정이 돌고 바뀐 공고 수를 알린다.

## 6. 범위 밖

되살릴 때를 위해 한 줄씩만 남긴다.

**판별 과정 노출.** 요건별 대조 표, 미충족 사유 문구, 확인 필요 3분류, 판별 조건 칩. → [ADR-0003](adr/0003-판별-비노출.md)

**운영 도구.** 사람 검수 큐, 정답 세트 관리 화면, 정확도 지표 대시보드, 링크 유효성 검사, 사용 로그. 수집·파싱·추출·신뢰도 자체는 F0으로 들어왔다. 여기 남은 것은 **그 결과를 사람이 들여다보고 고치는 화면**이다.

**계정과 과금.** 회원가입, 로그인, 건당 결제, 이용 내역.

**알림 발송.** 마감 알림 이메일과 알림톡. 화면 내 배지까지만 만든다.

**문서 고급 기능.** HWPX 지정 양식 적용, 도식 자동 생성, 표 자동 생성.

**계획서 재활용.** 지난 계획서를 새 공고 양식에 맞춰 변환하는 기능. 반복 신청자에게 가치가 크다.

**기타.** 캘린더 뷰, 참고자료 업로드, 가점 판정, 변경 이력.
