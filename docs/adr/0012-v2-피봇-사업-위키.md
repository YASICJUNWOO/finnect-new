# ADR-0012: v2 피봇 — 사업 위키를 제품의 뿌리로

- 상태: 채택됨
- 날짜: 2026-08-16
- 대체: [ADR-0008](0008-제품-범위-확대.md) (기능 번호 체계에 한해)
- 근거: [2026-08-16 v2 기획 문서](evidence/2026-08-16-v2-기획문서/) — 특히 `01_제품정의.md`

## 맥락

v1의 제품은 "사업 정보를 폼으로 받아 신청 가능한 공고를 판정하고, 그 판정을 사업계획서 초안으로 잇는다"였다. 사용자가 판별용 6항목과 집필용 6항목을 직접 입력하고, 계획서는 분석 → 질문 → 작성 세 단계를 거쳤다.

멘토가 던진 질문이 이 설계를 흔들었다. **"Claude에 직접 넣는 것보다 뭐가 나은가."**

폼으로 받은 정보는 그 공고 하나에만 쓰인다. 다음 공고에서 또 묻는다. Claude에 공고를 붙여넣고 내 사업을 설명하는 것과 구조가 같다. 차별점이 없다.

그리고 폼이 콜드 스타트를 만든다. 열두 칸을 채우기 전까지 제품이 아무 일도 하지 않는다.

## 결정

**사업 위키를 제품의 뿌리로 삼는다.**

1. **입력을 파일 던지기로 바꾼다.** 사업계획서·IR·회사소개서·사업자등록증·재무제표·흩어진 메모, 무엇이든 형식 구분 없이 받아 구조를 만든다. 분류해서 올리라고 요구하지 않는다.
2. **위키가 쌓인다.** 문서 작성 중 사용자가 답한 내용이 위키로 돌아가고, 다음 공고에서는 그만큼 덜 묻는다. 쓸수록 좋아진다.
3. **3단계 질문 폼을 버린다.** 파일 업로드와 부족분 질문으로 대체한다.
4. **기능 번호를 v2 체계로 다시 배열한다.** F1 위키 · F2 공고 데이터 처리 · F3 판별과 적합도 · F4 추천 · F5 공고 상세 · F6 문서 자동 완성 · F7 제출 가이드 · F8 신청 현황.

번호 재배열은 [ADR-0008](0008-제품-범위-확대.md)이 "F1~F9를 건드리지 않는다"고 한 것을 뒤집는다. 그때 근거는 "화면 문서와 다이어그램이 전부 F1~F9로 참조한다"였는데, **이번에는 그 문서들도 같이 다시 쓰므로 근거가 사라졌다.**

## 결과

- **v1 명세 F0~F9가 전부 이동하거나 사라졌다.** `SPEC.md`를 재작성했다. 대응표를 만들지 않는다. 대응이 되지 않는 것이 이 결정의 내용이다.
- **F2-2 첨부 파싱이 여전히 제품의 전제다.** [ADR-0008](0008-제품-범위-확대.md)의 실질은 그대로 살아 있다. 번호만 F0-2 → F2-2로 바뀌었다.
- **이 레포의 수집 코드는 그대로 산다.** `src/finnect/ingest/`와 저장 모델 6종이 F2-1이 된다. `plan/06`으로 만든 것 중 버릴 것이 없다.
- 대가로 **콜드 스타트가 파싱 품질 문제로 바뀐다.** 파일을 못 읽으면 위키가 안 만들어지고 제품 전체가 서지 않는다. 첨부 텍스트 추출률 95%가 여기 걸린다.
- **위키 관리 부담이 새로 생긴다.** 파일에서 뽑은 정보는 서로 어긋나고 낡는다. F1-5 정리가 그래서 선택 기능이 아니다.
- 판별 엔진은 화면 주인공에서 물러나 추천의 근거가 된다. [ADR-0003](0003-판별-비노출.md)은 그대로 유효하다.
