## 지금 상태

**공고 수집이 돌아간다.** [06 슬라이스](06-목록-수집과-조회.md)의 코드가 들어갔고 `uv sync` → `docker compose up -d db` → `alembic upgrade head` → 화면까지 [`README.md`](../../README.md)만 보고 통과한다.

두 출처의 목록 API가 DB에 쌓이고, `/notices`에서 목록·상세를, `/ingest`에서 수집 실행을 본다. 첨부는 메타데이터만 담고 LLM은 아직 안 부른다.

**v2에서 이것은 F2-1 수집이다.** 번호만 바뀌었고 버릴 코드는 없다.

### v2가 요구하는 것 중 아직 없는 것

제품의 뿌리가 **사업 위키**로 바뀌었는데(F1) **이 레포에는 위키 쪽 코드가 한 줄도 없다.** 파일 업로드, 청크 분리, 노드 추출, 근거 매달기, 그래프 저장이 전부 새로 만들 것이다. 기존 코드는 공고 쪽(F2)만 덮는다.

| v2 기능 | 이 레포 상태 |
|---------|-------------|
| F1 사업 위키 | **없다.** 전부 새로 |
| F2-1 수집 | **있다.** `src/finnect/ingest/` |
| F2-2 첨부 수집 | 메타데이터만. 내려받지 않는다 |
| F2-3 ~ F2-10 정규화·추출 | 없다 |
| F3-1 자격 판별 | 없다 |
| F3-2 적합도 | 없다 |
| F4 ~ F8 화면 | 없다. `src/finnect/admin/`은 운영 도구이고 제품 화면이 아니다 |

기획이 만든 시연 코드(`demo_dark.html`, `redesign.html`)는 **이 레포에 없고 별개다.** 그쪽 상태는 [`04_구현현황.md`](../adr/evidence/2026-08-16-v2-기획문서/04_구현현황.md)에 있다.

### 막혀 있는 것

**배점 미결이 풀렸다.** [ADR-0010](../adr/0010-배점-전제-폐기.md)이 [ADR-0019](../adr/0019-집필의-축을-양식으로.md)로 대체됐다. 집필의 축은 양식 목차와 작성 지침이다. 배점 순 정렬과 배점 기반 분량 배분은 만들지 않는다.

**대신 새 미결이 여덟 생겼다.** 목록은 [`../SPEC.md`](../SPEC.md) §9에 있다. 그중 코드를 막는 것은 셋이다.

| 미결 | 무엇을 막나 |
|------|------------|
| **질문을 언제 하는가** (SPEC §9-1) | F6-7과 F1-7의 되먹임. 온보딩 설계 전체가 여기 걸린다 |
| **접수 기간 표현** (SPEC §9-5) | 공고 스키마. 기업마당의 57%가 날짜가 아니다 |
| **저장소·큐·파서 선정** (SPEC §9-7) | F1-1 전체. 아무것도 시작 못 한다 |

앞의 둘은 결정이고 코드가 필요 없다. 세 번째는 조사가 먼저다.

### 지금 할 수 있는 것 셋

**1. 실측 4건을 기획에 회신한다.** 코드가 필요 없고 상대 스키마를 바꾼다. [`../SPEC.md`](../SPEC.md) §8.1의 네 항목이다. 특히 배점과 마감일 두 건은 `03_데이터모델.md`의 `Section.score`와 `Program.deadline`을 고치게 만든다. **기획이 "HWP 파싱 가능성"을 아직 조사 과제로 두고 있는데 이미 실측됐다**(추출률 95%).

**2. [T-0009](06-목록-수집과-조회.md#t-0009-api-실측-기록) 실측 기록.** 계획 파일에 흩어진 실측값을 `adr/evidence/`로 옮긴다. **날짜 필터가 틀린 값을 준다는 사실은 잊으면 반드시 다시 밟는다.** 에러가 아니라 그럴듯한 숫자가 나오기 때문이다.

**3. SPEC §9의 미결 1·5를 정한다.** 질문 타이밍과 접수 기간 표현이다. 둘 다 결정이지 조사가 아니고, 정해지기 전에는 온보딩과 공고 스키마를 못 짠다.

**[T-0003](01-기반.md#t-0003-스택-확정)은 [ADR-0020](../adr/0020-스택-확정.md)으로 승격돼 끝났다.** 다만 v2가 오브젝트 스토리지·큐·워커·벡터 저장을 새로 요구한다. 그건 스택 확정에 안 들어간 부분이라 SPEC §9-7에서 따로 정한다.

## 순서를 이렇게 잡은 이유

마감은 있다. FIN:NECT 챌린지 본선이고 **MVP 완성도가 30점으로 가장 크다**([`../SPEC.md`](../SPEC.md) §1.5). 시연이 필수다.

그래서 v1의 원칙 하나가 바뀐다. v1은 "틀린 문서를 미리 쓰지 않는다"를 이유로 골격부터 정했다. **그 원칙은 유지하되, 무엇을 먼저 세울지는 시연 동선이 정한다.**

**위키가 맨 앞이다.** 다른 기능이 전부 여기서 나온다. 위키가 없으면 적합도도 집필도 입력이 없다.

**그다음이 첨부 파싱이다.** 자격 요건·양식 구조·작성 지침이 전부 첨부 안에 있다. 평가 정보는 공고 본문에 0%다. 추출률 95%가 이미 확인됐으므로 **기획이 생각하는 것보다 이 블로커는 얕다.**

**적합도는 위키와 취지 추출 둘 다 있어야 돈다.** 어느 하나가 없으면 상수를 박는 것 외에 할 게 없다.

**화면은 DESIGN.md 토큰 실값을 기다린다.** [`../../DESIGN.md`](../../DESIGN.md) §4가 색·타입·반경을 전부 "5.1에서 확정"으로 두고 있다. 방향만 있고 값이 없다.
