# ADR-0020: 스택을 Python · FastAPI · PostgreSQL로 확정한다

- 상태: 채택됨
- 날짜: 2026-08-16
- 승격: [plan/06 "정한 것"](../plan/06-목록-수집과-조회.md#정한-것) — 그 표를 결정으로 올린다
- 닫는 것: [T-0003 스택 확정](../plan/01-기반.md#t-0003-스택-확정)

## 맥락

**스택이 어디에도 결정으로 기록된 적이 없다.** `.gitignore`가 Python(`__pycache__`, `.ruff_cache`)과 Node(`node_modules`, `.next`)를 나란히 전제하고 있었지만, 그건 이전 저장소에서 딸려온 관성이지 결정이 아니다. [ADR-0001](0001-정본-문서-체계.md)이 정한 대로 **여기에 없는 것은 결정이 아니다.**

그사이 [plan/06](../plan/06-목록-수집과-조회.md)이 코드를 넣으면서 스택이 사실상 정해졌고 근거도 그 계획의 "정한 것" 표에 적혔다. 그런데 계획은 완료되면 `상태:`만 바뀌는 문서라 **결정의 정본이 될 수 없다.** T-0009가 실측값에 대해 지적하는 것과 같은 문제다.

스택은 나중에 바꾸면 전부 뜯어야 하는 축이다. 돌아가고 있다는 사실만으로 두지 않고 여기 옮긴다.

## 결정

| 항목 | 결정 | 이유 |
|------|------|------|
| 언어 | **Python 3.13** | HWP 파서가 이 선택을 강제한다. 스파이크 `hwp_text.py`가 OLE + raw deflate + 레코드 워크로 추출률 100%를 냈다. 3.14를 쓰지 않는 이유는 신규 의존성 휠이 아직 비어 있을 수 있어서다 |
| 패키지 | **uv** | 락파일과 파이썬 버전을 함께 고정한다. `.venv`가 시스템 인터프리터를 그대로 쓰던 상태를 끝낸다 |
| 웹 | **FastAPI** | 나중에 제품 프론트에 JSON을 주는 서버와 같은 프로세스다. 지금 관리 화면을 얹는 자리가 그때 API가 서는 자리와 같다 |
| 관리 화면 | **Jinja2 템플릿** | 운영 도구는 `SPEC.md` §6 범위 밖이다. 제품 프론트와 섞지 않고, **API 계약을 아직 안 정해도 된다** |
| DB | **PostgreSQL 18** (docker compose) | 원문 payload를 JSONB로 보존한다. 제품과 같은 DB를 쓴다 |
| ORM | **SQLAlchemy 2.0 + Alembic** | 추출 스키마는 코퍼스를 보고 정하므로([ADR-0009](0009-구-백엔드-재사용-보류.md)) 스키마가 계속 바뀐다. 마이그레이션이 필수다 |
| 수집 실행 | **CLI와 화면 버튼** | **공고 수집에 한정한 판단이다.** 목록 API를 받는 데 스케줄러·잡 큐는 과설계다([ADR-0011](0011-수집-실행-화면.md)). 파일 업로드 처리는 이 판단이 적용되는 대상이 아니다 |

**버전을 범위가 아니라 상한까지 묶는다.** `requires-python = ">=3.13,<3.14"`다. 파서가 언어 버전에 걸려 있으므로 상한이 열려 있으면 어느 날 조용히 3.14로 올라간다.

## 결과

- [T-0003](../plan/01-기반.md#t-0003-스택-확정)의 완료 조건 셋이 모두 찼다. 나머지 둘(`.env.example`에 DB 키, `README.md`만 보고 실행)은 [T-0010](../plan/06-목록-수집과-조회.md#t-0010-저장소-골격)이 이미 채웠고, 남아 있던 ADR 승격을 이 문서가 닫는다.
- [T-0004 지원 포맷 목록 정의](../plan/02-수집과-추출.md#t-0004-지원-포맷-목록-정의)의 선행이 풀린다. 파서 후보를 Python 생태계 안에서 고르면 된다.
- `.gitignore`의 Node 항목은 근거를 잃는다. **지우지는 않는다.** 제품 프론트를 정할 때 되살아날 수 있고, 지금 지워서 얻는 것이 없다.
- **포기한 것** — 언어를 바꿔 얻을 수 있었던 것들. 특히 동시성과 배포 크기다. 3만 건 적재가 병목이지 언어가 병목이 아니라서 지금은 대가가 보이지 않지만, 판정이 공고 수천 건 × 요건 수십 개로 늘면 다시 볼 수 있다.

## 안 정한 것

**제품 프론트 프레임워크를 지금 정하지 않는다.** [plan/01](../plan/01-기반.md)의 API 계약이 아직 없고 제품 화면도 서지 않았다. 관리 화면이 Jinja2로 이미 돌고 제품 프론트와 섞지 않기로 했으므로 **지금 정해서 얻는 것이 없다.** 정하지 않은 상태가 아무것도 막지 않는다.

**LLM 제공자를 지금 정하지 않는다.** 저장소는 아직 LLM을 한 번도 부르지 않았다. L1 추출은 strict schema를, L3 집필은 스트리밍을 요구하는데 **둘 다 무엇을 뽑을지가 정해지기 전이다.** 추출 스키마는 코퍼스를 보고 정한다([ADR-0009](0009-구-백엔드-재사용-보류.md)). 스키마 없이 제공자를 고르면 고른 근거가 없다.

**v2가 새로 요구하는 인프라는 이 문서의 범위가 아니다.** [ADR-0012](0012-v2-피봇-사업-위키.md)의 피봇으로 사업 위키(F1)가 제품의 뿌리가 되면서 오브젝트 스토리지, 큐와 워커, 벡터 저장이 필요해졌다. 이 문서가 확정한 것은 **지금 돌고 있는 공고 수집 스택**이고, 위키 쪽은 코드가 한 줄도 없어서 확정할 근거가 없다.

그 여덟 건은 `SPEC.md` §9-7에 미결로 서 있다([설계정리 §7](evidence/2026-08-16-v2-기획문서/설계정리_개발논의용.md) A~H).

| | 미결 | 이 문서와의 관계 |
|---|------|-----------------|
| A | 저장소 구성 · 벡터 저장 위치 | PostgreSQL은 정했다. **pgvector로 갈지 전용 벡터DB를 붙일지는 안 정했다** |
| B | 큐/워커 스택 | 위 표의 "수집 실행" 행이 **이 건에 대한 답이 아니다.** 파일별 상태머신은 성격이 다르다 |
| C | 파싱 도구 (HWP·OCR·표 추출) | 언어가 Python으로 정해져 후보가 좁혀졌을 뿐이다 → [T-0004](../plan/02-수집과-추출.md#t-0004-지원-포맷-목록-정의) |
| D~H | ETL 주기, 그래프 테이블링, RAG 시점, LLM 비용, 격리 정책 | 전부 범위 밖 |

**이 문서를 "스택이 다 정해졌다"로 읽지 않는다.** 정해진 것은 언어·패키지·웹·DB·ORM 다섯이다.

여기 적은 미결을 정할 때 이 문서를 고치지 않고 새 번호를 만든다.
