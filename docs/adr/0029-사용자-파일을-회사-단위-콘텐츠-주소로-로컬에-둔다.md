# ADR-0029: 사용자 파일을 회사 단위 콘텐츠 주소로 로컬에 두고, 격리를 경로에서 건다

- 상태: 채택됨
- 날짜: 2026-08-18
- 채우는 것: [ADR-0021](0021-인프라-선정을-미룬다.md)이 미룬 **A(저장소 구성)와 H(개인정보·격리)**. 그 ADR이 "나눠서 정할 수 없다"고 적은 그 둘이다
- 닫는 것: [plan/12](../plan/12-사업-위키-구축.md) T-0041
- 관련: [ADR-0022](0022-첨부-원본을-콘텐츠-주소로-로컬에-둔다.md) · [ADR-0026](0026-읽기-경로만-vercel에-올린다.md) · [ADR-0014](0014-통합-그래프와-근거-청크.md)

## 맥락

사용자가 파일을 던지는 것이 제품의 첫 동작이고([SPEC](../SPEC.md) F1-1-1), **어디에 둘지 정하기 전에는 받을 수가 없다.** 파싱부터 저장까지 모든 단계가 "파일이 여기 있다"를 전제한다.

[ADR-0022](0022-첨부-원본을-콘텐츠-주소로-로컬에-둔다.md)가 공고 첨부용으로 콘텐츠 주소 저장을 한 벌 깔아 뒀다(`data/attachments/<sha256[:2]>/<sha256>`, 3,354건 · 약 2GB). **그런데 그대로 쓸 수 없다.**

| | 공고 첨부 | 사용자 파일 |
|---|---|---|
| 공개성 | 누구나 내려받는 공개 파일 | **사업자등록증·재무제표.** 개인정보이고 영업비밀 |
| 격리 | 요구가 없다 | **필수다** — [SPEC](../SPEC.md) §2-3 "검색 대상은 오직 사용자 본인 문서다" |
| 삭제 | 지울 이유가 없다 | **탈퇴하면 지워야 한다** |

그리고 콘텐츠 주소 자체가 격리와 부딪힌다. 중복 업로드를 막으려면 `sha256`이 키여야 하는데, **두 회사가 같은 파일을 올리면 해시가 같다.** 정부 양식이나 표준 서식이면 실제로 그렇다. 원본 하나를 둘이 공유하게 되고 한쪽이 탈퇴하면 무엇을 지울지가 정해지지 않는다.

## 결정

### 1. 로컬 파일시스템에 둔다. 오브젝트 스토리지를 지금 쓰지 않는다

```
data/user-files/<company_id>/<sha256[:2]>/<sha256>
```

[ADR-0026](0026-읽기-경로만-vercel에-올린다.md)이 "올라가는 것은 읽기 경로뿐이고 수집·해독은 로컬에 남는다"고 정했다. **업로드는 배포본의 첫 쓰기 경로가 되는데, 그 문을 데이터가 하나도 없는 상태에서 열지 않는다.** 사업자등록증과 재무제표를 외부로 내보내는 결정이라 되돌리기 어렵다.

### 2. 저장 인터페이스를 한 겹 둔다. 그것이 되돌리는 장치다

```
put(company_id, fileobj, filename) -> sha256
open(company_id, sha256) -> IO
delete(company_id, sha256) -> None
purge(company_id) -> int          # 탈퇴
```

**모든 함수가 `company_id`를 필수 인자로 받는다.** `company_id` 없이 사용자 파일에 닿는 함수를 만들지 않는다. 이것이 격리를 코드에서 강제하는 지점이고 테스트할 수 있는 형태다.

구현은 로컬 하나로 시작한다. 클라우드로 갈 때 **구현 한 벌을 더하는 일**이 되고 호출부는 안 고친다.

### 3. 격리는 경로에서 건다. DB 행에서만 걸지 않는다

`company_id`가 경로의 첫 조각이다. **DB 조건절이 아니라 디렉터리가 1차 방어선이다.**

- 코드 버그로 남의 `sha256`을 조회해도 자기 회사 디렉터리 밖에 못 닿는다. `WHERE company_id = ?`를 빠뜨린 쿼리 하나가 유출이 되지 않는다
- 탈퇴 삭제가 디렉터리 하나를 지우는 일이 된다. DB만 격리하면 고아 파일을 찾아 돌아야 한다

### 4. 회사 단위로 해시를 매긴다. 회사 사이 중복 제거를 하지 않는다

**같은 파일을 두 회사가 올리면 두 벌 저장된다. 의도한 것이다.**

우리가 실제로 필요한 중복 제거는 **한 회사 안에서**다 — 같은 파일 재업로드와 두 파일에 같은 내용이 있는 경우([픽스처](../../tests/fixtures/wiki/README.md) 함정 1·3). 그건 회사 단위 콘텐츠 주소로 그대로 된다.

회사 사이 중복 제거가 사 오는 것은 **디스크 절약**이고, 치르는 것은 **공유 객체의 수명 관리**(참조 세기, 누가 지우나)와 **조용히 새는 격리 버그 한 종류**다. 저장 최적화와 정확성이 부딪히면 정확성이 이긴다.

### 5. 파일을 지워도 노드를 지우지 않는다

| 무엇을 지우나 | 무엇이 일어나나 |
|---|---|
| **파일 하나** (F1-4-7에서) | 그 파일에서 나온 청크를 지운다. **그 청크만 근거였던 노드는 지우지 않고 "근거 없음"으로 표시한다** |
| **회사 전체** (탈퇴) | `purge(company_id)` + DB의 그 회사 행 전부. 청크·노드·엣지가 CASCADE로 따라간다 |

노드를 같이 지우면 안 되는 이유가 둘이다. **사용자가 위키에서 직접 고쳤을 수 있고**(F1-4-5), **집필 중 답한 `user_stated` 값이 붙어 있을 수 있다**([ADR-0028](0028-초안을-먼저-완성하고-못-채운-자리에서-묻는다.md)). 문서 근거가 사라진 것과 값이 사라져야 하는 것은 다르다.

### 6. 벡터 저장은 여기서 정하지 않는다

[ADR-0021](0021-인프라-선정을-미룬다.md) A가 "벡터는 따로 본다"고 나눠 뒀고, [plan/12](../plan/12-사업-위키-구축.md)가 사용자 위키에 의미 검색을 붙이지 않기로 했다. **PostgreSQL로 되는지부터 확인하는 일이 남아 있고 그 시점은 집필(F6)이다.**

## 결과

- **배포본에서 업로드가 안 된다. 시연을 로컬에서 해야 한다.** 이 대가를 알고 받는다. [ADR-0026](0026-읽기-경로만-vercel에-올린다.md)이 이미 같은 분리를 받아들여 뒀다
- **되돌리는 조건: 시연을 배포 URL에서 하기로 정해지면** 그때 구현을 하나 더한다. 인터페이스가 있어 호출부는 안 바뀌고, 개인정보 이관 정책만 새로 쓴다
- **디스크가 회사 수에 비례한다.** 회사 사이 중복 제거를 안 하므로 정부 양식이 회사마다 한 벌씩 쌓인다. 첨부가 3,354건에 2GB였으니 회사 하나가 파일 열 개를 올리면 수십 MB 수준이다. **지금 규모에서는 문제가 아니고, 문제가 되면 그때 참조 세기를 도입한다**
- **`data/user-files/`를 `.gitignore`에 넣어야 한다.** `data/attachments/`와 같은 이유다
- **픽스처에 회사가 하나뿐이라 격리를 시험할 수 없다**([픽스처 README](../../tests/fixtures/wiki/README.md)). **둘째 회사를 만드는 것이 이 결정의 검증 조건이다** — A사 파일을 B사로 조회하면 못 찾아야 한다
- **포기한 것 — 저장소 구성 전체를 한 번에 못 본다.** [ADR-0021](0021-인프라-선정을-미룬다.md)이 B(큐·워커)를 여전히 미뤄 뒀고, "A와 B는 보통 같이 고르는 축이라 B를 나중에 정하면 A를 다시 볼 가능성이 있다"고 적었다. 인터페이스 한 겹이 그 위험을 줄이지만 없애지는 않는다
