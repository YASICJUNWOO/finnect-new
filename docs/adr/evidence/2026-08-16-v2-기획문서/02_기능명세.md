## 1. 한 줄 정의

가진 파일을 통째로 던지면 **내 사업 위키**가 만들어지고, 그 위키로 **맞는 공고를 골라주고**, 들어가면 **문서가 이미 써져 있다.**

v1과의 차이는 하나다. v1은 사용자가 정보를 입력하면 문서를 만들어 줬다. **v2는 사용자가 입력하기 전에 문서가 완성돼 있다.**

---

## 2. 이 제품을 왜 쓰는가

멘토가 던진 질문이다. "Claude에 직접 넣는 것보다 뭐가 나은가."

**답은 위키다.** Claude에 공고를 붙여넣으면 그 공고 하나에 대해서만 답한다. 매번 내 사업을 다시 설명해야 한다. 우리는 구조화된 사업 정보를 갖고 있어서 두 가지를 할 수 있다.

1. **수백 건을 한 번에 대조한다.** 사람이 공고를 하나씩 열어보지 않아도 된다.
2. **설명하지 않아도 문서가 써진다.** 이미 알고 있기 때문이다.

그리고 쓸수록 위키가 두꺼워져서 다음 공고는 더 잘 써진다.

## 3. 동작 순서

```
   [ 사용자가 가진 파일 뭉치 ]
     사업계획서·IR·소개서·재무제표·메모, 무엇이든
              │
              ▼
   F1  사업 위키 구축            ◀─────────────────┐
       파일을 읽어 항목으로 쪼개고 잇는다            │
              │                                    │
              ▼                                    │ 적립
   F3  자격 판별 + 적합도 판정                       │
       자격은 결정론, 적합도는 취지 대조              │
              │                                    │
              ▼                                    │
   F4  추천                                         │
       맞는 것 소수 + 왜 맞는지 한 줄                 │
              │                                    │
              ▼ 공고 선택                           │
   F5  공고 상세                                    │
              │                                    │
              ▼                                    │
   F6  문서 자동 완성  ◀── 위키에서 끌어와 이미 써짐  │
       못 채운 곳만 표시 ──── 사용자가 채운 답 ───────┘
              │
              ▼
   F7  문서 산출        F8  신청 현황
```

**오른쪽 화살표가 이 제품의 전부다.** 사용자가 채운 답이 위키로 돌아가 쌓인다. 다음 공고에서는 그만큼 덜 묻는다. 쓸수록 좋아지는 구조다.

F2(공고 데이터 처리)는 화면이 없어 그림에서 뺐다. F3의 입력이 된다.

## 4. 핵심 기능

### F1. 사업 위키

이 제품의 뿌리다. 다른 모든 기능이 여기서 나온다.

#### F1-1. 구축

| 기능 | 동작 |
|------|------|
| F1-1-1 파일 통째로 받기 | 사업 관련 파일을 형식 구분 없이 여러 개 한 번에 올린다. 분류해서 올리라고 요구하지 않는다 |
| F1-1-2 원본 보관 | 올린 파일은 그대로 둔다. 추출 결과와 분리해 보관한다 |
| F1-1-3 항목으로 쪼개기 | 파일을 읽어 사업 정보를 항목 단위로 나눈다. 항목 목록은 F1-2 |
| F1-1-4 출처 기록 | 각 항목이 어느 파일 어디에서 나왔는지 남긴다 |
| F1-1-5 항목 간 연결 | 관련 있는 항목을 서로 잇는다 |
| F1-1-6 충돌 표시 | 여러 파일에서 서로 다른 값이 나오면 어느 쪽을 쓸지 묻는다 |
| F1-1-7 구축 진행 표시 | 파일을 읽는 동안 무엇이 채워지고 있는지 보여준다 |

#### F1-2. 위키가 담는 것

두 묶음으로 나눈다. 쓰임이 달라서다.

| 묶음 | 항목 | 쓰임 |
|------|------|------|
| **사업체 정보** | 사업자 형태, 사업자등록일, 대표자 생년월일, 소재지, 업종, 상시 근로자, 수령 이력 | **자격 판별**(F3-1)의 입력. 정형 |
| **사업 내용** | 한 줄 정의, 문제 인식, 솔루션과 기술, 목표 고객과 시장, 경쟁과 차별점, 매출과 성과, 팀 구성, 자금 현황, 로드맵 | **적합도 판정**(F3-2)과 **문서 자동 완성**(F6)의 입력. 서술 |

#### F1-3. 노드 한 장의 생김새

위키는 항목 하나가 문서 한 장이다. 각 장은 본문과 머리말로 이뤄진다. 머리말이 있어야 기계가 고르고 사람이 출처를 확인할 수 있다.

```
─────────────────────────────────────────
 종류    솔루션
 제목    재고관리 자동화 소프트웨어
 상태    확정
 태그    기술, 개발단계
 갱신    2026-08-15
─────────────────────────────────────────
 본문
 바코드와 QR로 입출고 기록을 자동으로 남긴다.
 현재 1단계 모듈 프로토타입 개발을 마쳤다.

 근거 2                              ← 펼치면 원문 조각
 ▸ 2025_초기창업패키지_사업계획서.hwp  12쪽 · 기술 구현
 ▸ 회사소개서_v3.docx                 4쪽 · 제품

 관련  → 목표 고객   → 경쟁 제품   → 팀 구성
─────────────────────────────────────────
```

**출처는 문자열이 아니라 청크다.** 파일명과 쪽수만 적어 두면 사람이 원본을 다시 열어 봐야 확인이 된다. 노드가 자기 근거가 되는 원문 조각을 직접 매달고 있어서, 펼치면 그 자리에서 읽힌다. 스키마는 `03_데이터모델.md` 11장에 있다.

**모순(F1-5-1)이 잡힌 노드는 어긋난 근거를 펼쳐 놓는다.** 어느 쪽이 맞는지 고르는 일이라 둘을 나란히 봐야 한다. 팀 구성 노드가 그 예다. 회사소개서는 3인, IR 자료는 5인으로 적혀 있고 둘 다 원문이 열려 있다.

이 형태는 임의로 정한 것이 아니다. 마크다운 본문에 머리말을 얹고 문서끼리 링크로 잇는 구조는 옵시디언과 llm-wiki가 공통으로 쓰는 방식이고, 2026년 6월 구글이 **Open Knowledge Format**으로 표준화한 것과 같다. 이 사실이 심사 문구 "범용 모델 활용을 넘어선 기술적 접근"에 대한 답이 된다.

#### F1-4. 위키 관리 화면

**옵시디언에서 볼트를 다루는 감각으로 만든다.** 별도 화면이 필요하다.

| 기능 | 동작 |
|------|------|
| ~~F1-4-1 목차~~ | **폐기.** 2026-08-16. 노드가 열다섯이라 그래프 하나에 다 보인다. `05` 4.5 |
| F1-4-2 **연결 구조 보기** | 노드가 서로 어떻게 이어져 있는지 그림으로 본다. 참석자 2가 말한 "뇌 구조처럼" |
| F1-4-3 채움 상태 | 채워진 노드, 빈 노드, 손봐야 할 노드를 구분해 보여준다 |
| F1-4-4 노드 상세 | F1-3의 한 장을 연다 |
| F1-4-5 **역참조** | 이 노드를 가리키는 다른 노드를 보여준다 |
| F1-4-6 직접 수정 | 본문과 머리말을 그 자리에서 고친다 |
| F1-4-7 노드 추가 | 빈손으로 새 노드를 만든다 |
| F1-4-8 검색 | 내용과 태그로 찾는다 |
| F1-4-9 원본 파일 목록 | 올린 파일과 각 파일에서 나온 노드를 잇는다 |
| F1-4-10 파일 추가 | 나중에 파일을 더 올려 위키를 두껍게 한다 |
| F1-4-11 **변경 이력** | 언제 무엇이 어디서 들어왔는지 시간순으로 |

#### F1-5. 정리

**LLM이 위키를 훑어 손봐야 할 곳을 찾아준다.** 사용자가 관리 부담을 지지 않게 하는 기능이다. 이게 없으면 위키는 금세 지저분해지고 안 쓰이게 된다.

| 기능 | 동작 |
|------|------|
| F1-5-1 **모순 찾기** | 서로 어긋나는 내용을 짚어 준다. 파일마다 팀 규모가 다르게 적힌 경우 등 |
| F1-5-2 **오래된 내용 찾기** | 갱신일이 지난 노드를 짚어 준다. 매출·팀 구성처럼 자주 바뀌는 항목 우선 |
| F1-5-3 **끊긴 노드 찾기** | 아무 데도 연결되지 않은 노드를 짚어 준다 |
| F1-5-4 **빠진 연결 제안** | 이어야 할 것 같은데 안 이어진 노드 쌍을 제안한다 |
| F1-5-5 **중복 병합 제안** | 같은 내용이 여러 노드에 흩어져 있으면 합치자고 제안한다 |
| F1-5-6 **빈 곳 지목** | 지원사업 문서를 쓰려면 필요한데 위키에 없는 항목을 지목한다 |
| F1-5-7 제안 수락과 거절 | 정리는 제안까지만 한다. 자동으로 고치지 않는다 |

F1-5-7이 중요하다. llm-wiki 패턴의 규율이 "자동 갱신 금지, 사람이 시킬 때만"이다. 모르는 사이에 내 사업 정보가 바뀌어 있으면 신뢰를 잃는다.

#### F1-6. 밖으로 꺼내기

| 기능 | 동작 |
|------|------|
| F1-6-1 마크다운 내보내기 | 위키 전체를 표준 형식으로 내려받는다 |
| F1-6-2 옵시디언 호환 | 내려받은 폴더를 옵시디언에서 그대로 연다 |

우리 서비스를 떠나도 위키가 남는다는 뜻이다. 가둬 두지 않는다는 것이 오히려 쓸 이유가 된다.

#### F1-7. 자동 적립

| 기능 | 동작 |
|------|------|
| F1-7-1 답변 적립 | 문서 작성 중 사용자가 답한 내용이 위키 노드로 저장된다. 3장 그림의 오른쪽 화살표 |
| F1-7-2 적립 알림 | 무엇이 위키에 쌓였는지 그 자리에서 알린다 |

### F2. 공고 데이터 처리

화면이 없다. 결과가 F3의 입력이 된다. **멘토가 지목한 기술 차별점이 여기 있다.**

| 기능 | 동작 |
|------|------|
| F2-1 수집 | 공고를 가져온다. 대상 사이트 수는 추후 정한다 |
| F2-2 첨부 문서 수집 | 본문 외 HWP·DOCX·PDF 첨부를 함께 가져온다. 자격·배점·양식이 여기 들어 있다 |
| F2-3 이질 형태 정규화 | 인라인 HTML, HWP, DOCX, PDF를 하나의 구조로 맞춘다 |
| F2-4 자격 요건 구조화 | 요건명, 비교 기준, 값으로 쪼갠다 |
| F2-5 **공고 취지 추출** | 이 공고가 무엇을 하려는 사업인지 주제와 키워드를 뽑는다. **적합도 판정의 절반이다** |
| F2-6 지원 형태 구분 | 현금인지 시설·공간인지 멘토링인지 인력인지 |
| F2-7 제출 서류와 양식 추출 | 서류 목록, 지정 양식 여부, 양식의 항목 구조 |
| F2-8 배점 추출 | 심사 항목과 배점 |
| F2-9 항목별 작성 지침 추출 | 양식 각 칸에 적힌 "~를 기술" 문구 |
| F2-10 **제약사항 보존** | 자부담 비율, 지원 상한, 중복 제한처럼 놓치면 안 되는 조건을 잘라내지 않는다. 어디서 나왔는지 함께 남긴다 |

F2-10이 멘토가 말한 지점이다. "잘라내다가 반드시 중요한 제약사항을 놓칠 수도 있잖아요."

### F3. 자격 판별과 적합도

화면이 없다. 결과가 F4 추천이 된다. **두 층을 섞지 않는다.**

#### F3-1. 자격 판별 (결정론)

| 기능 | 동작 |
|------|------|
| F3-1-1 요건 대조 | 위키의 사업체 정보와 공고 요건을 대조한다 |
| F3-1-2 파생값 계산 | 등록일에서 업력, 생년월일에서 만 나이를 신청일 기준으로 계산한다 |
| F3-1-3 결정론 보장 | LLM을 거치지 않는다. 같은 입력에 같은 결과 |
| F3-1-4 미달 제외 | 자격이 안 되는 공고는 추천에서 뺀다 |

#### F3-2. 적합도 판정 (의미 판단)

| 기능 | 동작 |
|------|------|
| F3-2-1 취지 대조 | 공고 취지(F2-5)와 사업 내용(F1-2)을 대조한다 |
| F3-2-2 **이유 생성** | 왜 맞는지 한 줄로 만든다. 이유가 안 나오면 내보내지 않는다 |
| F3-2-3 순위 | 자격을 통과한 것들의 순서를 정한다 |
| F3-2-4 안 맞는 이유 | 낮게 나온 것에는 왜 낮은지 남긴다 |

**하지 않는 것.** 합격 확률을 예측하지 않는다. 점수 하나로 뭉뚱그리지 않는다. 화면에서 확률이라는 말을 쓰지 않는다.

### F4. 추천 (첫 화면)

### F6. 문서 자동 완성

**핵심 기능이다.** 목표 상태는 "내가 입력하지 않아도 문서가 완성돼 있다"이다.

| 기능 | 동작 |

| F6-2 위키 기반 생성 | 위키의 사업 내용에서 끌어와 쓴다. 사용자에게 다시 묻지 않는다 |

### F7. 제출 가이드 [구현하며 바뀜]

## 5. 화면 구성

LNB 3축이다. 채용 사이트 구조와 같다. 공고를 보고, 내 프로필을 관리하고, 지원 현황을 본다.

| 메뉴 | 담는 기능 | 성격 |
|------|-----------|------|
| **지원사업** | F4 추천, F5 공고 상세, F6 문서 작성, F7 제출 가이드 | 공고 중심 |
| **내 사업** | F1 위키 | 나 중심. **v1에서 시연 제외였던 화면이 핵심으로 올라온다** |
| **신청 현황** | F8 | 진행 중심 |

**온보딩과 제출 가이드는 LNB 축에 걸리지 않는다.** 흐름 안에서만 나온다. 온보딩은 첫 진입, 제출 가이드는 문서를 끝낸 뒤다.

### 5.1 내 사업 메뉴의 하위 화면 [구현 반영]

탭 넷으로 나뉜다. 노드 상세와 정리는 별도 탭이 아니라 궤도 위에 겹쳐 뜬다.

| 탭 | 담는 기능 | 무엇을 하는 곳인가 |
|----|-----------|--------------------|
| **궤도** | F1-4-2, F1-4-3 | 노드가 어떻게 이어져 있는지 본다. 기본 탭 |
| **원본 파일** | F1-4-9, F1-4-10 | 파일과 그 파일이 만든 노드 |
| **변경 이력** | F1-4-11 | 언제 무엇이 어디서 들어왔는지 |

**궤도 위에 겹치는 것 둘.** 우측 상단 **정리 패널**(F1-5)과 노드를 누르면 열리는 **노드 상세 패널**(F1-3, F1-4-4~6)이다. 별도 탭으로 두지 않은 이유는 둘 다 궤도에서 위치를 확인하며 보는 것이 자연스럽기 때문이다.

**검색(F1-4-8)은 아직 없다.** 노드가 열다섯이라 그래프 하나에 다 보인다. 100개를 넘으면 검색과 목록을 같이 다시 이야기해야 한다.

### 5.2 왜 위키 관리에 화면을 따로 주는가

세 가지 이유다.

1. **차별점이 눈에 보여야 한다.** 위키가 있다고 말로만 하면 심사에서 안 산다. 노드가 쌓이고 이어진 화면을 보여주는 것이 "범용 모델을 넘어선 접근"의 증거다.
2. **관리하지 않으면 썩는다.** 파일에서 뽑은 정보는 서로 어긋나고 낡는다. 사용자가 손볼 수 있어야 계속 쓴다.
3. **신뢰가 여기서 생긴다.** 문서가 자동으로 써지는 것이 마법처럼 보이면 오히려 못 믿는다. 어떤 정보를 근거로 썼는지 열어볼 수 있어야 한다.

## 7. 이번에 안 하는 것

되살릴 때를 위해 한 줄씩만 남긴다.

**제출 대행.** 규제 경계 확인 후 다시 판단한다. 목표는 문서 완성까지다.

**합격 확률 예측.** 근거 데이터가 없다. 적합도로 대체한다.

**운영 기능.** 수집 스케줄러, 추출 신뢰도 관리, 사람 검수, 정확도 대시보드, 링크 유효성 검사, 사용 로그.

**계정과 과금.** 회원가입, 로그인, 결제.

**알림 발송.** 마감 알림 이메일과 알림톡. 멘토가 언급했으나 화면 내 표시까지만.

**문서 고급 기능.** HWPX 양식 적용, 도식 자동 생성, 자금계획 표 자동 작성. 자금계획 표는 실물 양식에서 확인한 필수 요소라 다음 순위 후보다.

**시장 규모 산정.** 발표 자료 영역으로 분리했다. `../internal/01_회의록_피봇.md` 12장.
