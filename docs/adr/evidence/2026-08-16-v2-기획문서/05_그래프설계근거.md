# 05_그래프설계근거 — 위키 그래프가 헤어볼이 되는 문제

> "노드가 많아지면 정신이 없어질 것 같다"는 지적에서 출발했다. 실제로 널리 논의된 문제이고 이름도 붙어 있다.
> 조사일 2026-08-15.

---

## 1. 문제에는 이름이 있다: 헤어볼

네트워크 시각화에서 노드와 선이 뒤엉켜 읽을 수 없게 되는 현상을 **hairball problem**이라 부른다. 겹침과 혼잡 때문에 크거나 조밀한 네트워크에서는 node-link 방식 자체가 해석 불가능해진다.

### 1.1 옵시디언 그래프 뷰가 실제로 받는 평가

커뮤니티 논의를 그대로 옮기면 이렇다.

1. **200개를 넘으면 헤어볼이 된다.** 물리 시뮬레이션이 만들어내는 결과가 "시각적으로는 인상적이지만 길찾기에는 쓸모없는" 상태가 된다.
2. **50개 미만일 때만 값이 있다.** 노트가 50개 아래일 때는 주제별 뭉침이 보이지만, 커뮤니티가 일관되게 말하는 유효 구간이 딱 그 초기뿐이다.
3. **결정적 지적 두 가지.** "연결이 많은 허브 노트와 보통 노트를 **구분할 수 없다.** 그리고 특정 노드를 **이름으로 검색하지 않으면 찾을 수 없다.** 그러면 시각화를 하는 이유가 없어진다."
4. **"예쁘지만 거의 쓸모없다."** 레딧에 스크린샷 올리는 용도라는 냉소가 흔하다.

### 1.2 다만 옵시디언 잘못은 아니라는 반론

"옵시디언은 문서에 적힌 대로 **페이지 링크 그래프**를 보여줄 뿐이고 그건 잘 하고 있다. 착각은 사용자 쪽에 있다. **마크다운 에디터의 그래프 뷰**를 **데이터베이스 의미의 지식그래프**와 같다고 여긴 것이 문제다."

이 반론이 우리에게 중요하다. **우리는 후자를 만들 수 있는 위치에 있다.** 2장에서 다룬다.

---

## 2. 우리는 옵시디언과 조건이 다르다

옵시디언 그래프가 헤어볼이 되는 근본 이유는 **노드에 종류가 없기 때문**이다. 모든 노트가 동등하고 모든 링크가 같은 실선이다. 그러니 배치를 물리 법칙에 맡길 수밖에 없고, 물리는 구조를 만들지 못한다.

**우리 위키는 다르다.**

| | 옵시디언 | 우리 |
|---|---|---|
| 노드 종류 | 없음. 전부 노트 | **셋으로 정해져 있다.** 정체성·사업체 정보·사업 내용. 원본 파일은 4.1에서 노드가 아니게 됐다 |
| 링크 종류 | 없음. 전부 같은 링크 | 구분 가능. 하위·관련 |
| 노드 수 | 수천에서 수만 | **수십.** 한 사업의 정보량은 한정돼 있다 |
| 스키마 | 자유 | **정해져 있다.** 사업계획서가 요구하는 항목이 곧 스키마 |

즉 우리는 **스키마 있는 지식그래프**를 만드는 것이고, 배치를 물리에 맡길 이유가 없다.

## 3. 알려진 해법들

네트워크 시각화 연구와 옵시디언 커뮤니티에서 나온 것들이다.

| 해법 | 내용 | 우리에게 |
|------|------|----------|
| **군집 탐지와 접기** | Louvain·Leiden으로 묶고 매크로 노드로 접었다가 확대하면 펼친다 | 노드가 수십 개면 과하다. 대신 **스키마로 미리 묶는다** |
| **레이아웃 교체** | 힘 기반 대신 원형, 행렬, OpenOrd | **이미 궤도로 바꿨다.** 방향은 맞다 |
| **간선 다발 묶기** | 관련 선을 다발로 합쳐 혼잡을 줄인다 | 선이 40개 아래면 불필요 |
| **K-core 벗기기** | 연결 적은 노드를 재귀적으로 걷어내 핵심만 남긴다 | **기본 노출을 줄이는 근거로 쓴다** |
| **점진적 공개** | 20~50개만 먼저 보이고 상호작용으로 확장 | **채택** |
| **국소 그래프** | 전역 대신 현재 노드 주변만 | **채택** |
| ~~**MOC**~~ | 허브 노트로 수동 색인을 만든다. 그래프 없이도 길찾기가 된다 | **2026-08-16에 안 쓰기로 했다.** 4.5를 보라 |
| **타입 있는 링크** | Breadcrumbs 플러그인. 상(↑)·동(→)·하(↓) 방향을 붙여 **위계**를 만든다 | **채택. 지금 우리 선은 전부 무방향이다** |
| **관계 종류 고정** | ExcaliBrain. 부모·자식·형제·친구 다섯으로 고정해 구조화된 마인드맵을 만든다 | 참고 |

## 4. 그래서 무엇을 바꿀까

우선순위 순으로 다섯이다. **넷을 반영했고 하나가 부분이다.** 상태는 각 절 제목에 적었다.

| | 항목 | 상태 |
|---|------|------|
| 4.1 | 원본 파일 기본 숨김 | **완료** |
| 4.2 | 궤도를 구획으로 | **완료.** 사업 내용 4구획, 사업체 2구획 |
| 4.3 | 선에 종류 | **완료.** 하위·관련. 출처는 청크로 갔다 |
| 4.4 | 국소 뷰 | **부분.** 호버 시 이웃만 밝아진다. 별도 모드는 없다 |
| 4.5 | ~~목차 화면~~ | **폐기.** 2026-08-16 |

### 4.1 원본 파일을 그래프에서 기본으로 숨긴다 [완료 → 2026-08-16 더 나아감]

지금 바깥 궤도의 원본 파일 6개가 **선을 가장 많이 만든다.** 파일 하나가 노드 서너 개로 뻗는다. 실사용에서 파일이 30개가 되면 그것만으로 헤어볼이 된다.

파일은 그래프의 주인공이 아니다. **레일의 원본 파일 탭으로 빼고 그래프에서는 기본 꺼둔다.** 필요할 때만 켠다. 이것 하나로 선이 절반 이하로 준다.

> **2026-08-16. 숨기는 대신 아예 노드로 두지 않기로 했다.**
>
> `서비스_설계_개발논의용.md` 3장의 GraphRAG 구조로 간다. 원본 문서는 `Document → Chunk` 계층으로 따로 두고, **각 노드가 자기 근거가 되는 청크를 매단다.** 원본 파일이 노드가 아니게 되므로 숨길 것도 없다.
>
> 실제로 세어 보니 **노드 21 → 15, 연결 37 → 21로 43% 준다.** 이 절이 예측한 "절반 이하"에 가깝고, 껐다 켜는 상태를 관리할 필요도 사라진다.
>
> "필요할 때만 켠다"는 요구는 **노드 상세에서 근거 청크를 여는 것**으로 대신한다. 파일명과 쪽수만 글자로 보여 주던 것이 원문 조각으로 바뀌므로 오히려 낫다.
>
> 스키마는 `03_데이터모델.md` 11장에 있다.

### 4.2 궤도를 구획으로 나눈다 [완료]

지금 사업 내용 9개가 한 궤도에 임의 각도로 놓여 있다. 여기에 **주제 구획**을 준다.

```
사업 내용 궤도를 네 구획으로
  ┌─ 문제와 해결 ─┬─ 시장과 고객 ─┬─ 성과와 자금 ─┬─ 팀과 계획 ─┐
   문제 인식        목표 고객        매출과 성과      팀 구성
   솔루션과 기술    시장과 경쟁      자금 현황        로드맵
                    지역 연계

사업체 정보 궤도는 두 구획으로
  ┌─ 등록 정보 ────────────┬─ 대표와 이력 ─┐
   사업자 정보·소재지·업종    대표자·수령 이력
```

궤도 위에 구획 라벨을 얹으면 **각도가 의미를 갖는다.** 노드가 늘어도 어느 구획에 들어가는지 정해져 있어 뭉치지 않는다.

### 4.3 선에 종류를 준다 [완료]

지금 모든 선이 같다. 셋으로 나눈다.

| 종류 | 무엇 | 표현 |
|------|------|------|
| **하위** | 정체성에서 각 항목으로 | 실선. 안에서 밖으로 |
| **관련** | 사업 내용끼리 | 점선. 얇게 |
| ~~**출처**~~ | ~~원본 파일에서 노드로~~ | **2026-08-16에 없앴다.** 4.1을 보라 |

Breadcrumbs가 상·동·하로 나눈 것과 같은 발상이다. **방향이 생기면 위계가 보인다.**

출처가 빠져 **선은 둘이 됐다.** 하위 9개, 관련 12개다. 근거는 선이 아니라 노드에 매달린 청크로 간다.

### 4.4 국소 뷰를 기본 동작으로 [부분]

노드를 누르면 지금은 패널만 열린다. 여기에 더해 **그 노드와 1촌만 남기고 나머지를 크게 죽인다.** 지금도 흐려지긴 하는데 정도가 약하다. 국소 뷰로 들어갔다 나오는 동작을 분명히 만든다.

### 4.5 목차 화면 [폐기 → 2026-08-16]

> **안 만든다.** 그래프 아래에 깔던 구획별 목록을 시안에서도 걷어냈다.
>
> 원래 논지는 "그래프 없이도 일이 되어야 한다"였고 커뮤니티가 MOC로 돌아가는 사례를 근거로 들었다. 다만 그 사례는 노트가 수천 개인 볼트 이야기다. **우리는 노드가 열다섯이고 화면 하나에 다 들어간다.** 목록을 따로 두면 같은 열다섯 개를 두 번 그리는 것이 된다.
>
> 노드를 찾는 일은 그래프에서 직접 한다. 궤도와 구획(4.2)이 자리를 고정해 주고, 정리가 필요한 노드는 우측 패널이 목록으로 모아 준다.
>
> **다시 열어야 하는 조건.** 노드가 늘어 그래프에서 눈으로 못 찾게 되는 시점이다. `02_기능명세.md` 8장이 검색(F1-4-8)을 100개 기준으로 잡아 뒀는데, 목록도 같은 기준에서 다시 이야기하면 된다.

## 5. 더 근본적인 판단

**그래프를 주 화면으로 둘 것인가.**

옵시디언 커뮤니티의 결론이 "그래프는 아이캔디"라면 우리도 같은 함정에 빠질 수 있다. 다만 우리 조건은 2장에서 본 대로 다르고, 발표에서 그래프의 인상은 크다.

**절충한다.**

1. **그래프는 구조를 보여주는 개요**로 둔다. 시연에서 "우리가 파일을 이렇게 구조로 바꿨다"를 보여주는 자리다.
2. ~~**작업은 목차에서** 한다~~ → **작업도 그래프에서** 한다. 노드를 눌러 패널에서 고친다. 목차 화면은 4.5에서 폐기했다.
3. 레일에서 둘을 나란히 두고 사용자가 고르게 한다. 지금 탭 구조가 이미 그 모양이다.

이렇게 하면 그래프가 예쁘기만 한 것이 아니라 **"보여주는 용도"라는 분명한 역할**을 갖는다. 역할이 정해지면 아이캔디라는 비판이 성립하지 않는다.
