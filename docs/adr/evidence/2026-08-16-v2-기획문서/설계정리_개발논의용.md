# 정부지원 공고 매칭 + 사업계획서 작성 서비스 — 설계 정리 (개발 논의용)

> 대상 독자: 백엔드/프론트 개발자
> 목적: 서비스 전체 흐름과 뒷단 로직을 공유하고, 아키텍처·데이터 모델·미결정 사항을 함께 확정하기 위한 논의 기반 문서
> 상태: 설계안 (v0.1) — 확정 아님, 논의 대상

---

## 1. 서비스 개요

사업자가 자기 사업 관련 문서를 올리면,

1. 문서를 구조화해 **사업자 프로필**로 만들고,
2. 자격에 맞는 **정부지원 공고를 추천**하고,
3. 선택한 공고용 **사업계획서 초안을 자동 작성**해주는 서비스.

경쟁 서비스(웰로 등)가 "탐색·추천"에 머무는 데 비해, 본 서비스는 **사업자 문서에 근거한 계획서 자동 작성**까지 간다는 점이 차별점이다.

---

## 2. 관통하는 설계 원칙 3가지

이 세 가지가 전체 아키텍처를 묶는 뼈대다.

| 원칙 | 내용 | 왜 중요한가 |
|---|---|---|
| **① 통합 그래프가 허브** | 문서에서 추출한 구조화 그래프 하나가 시각화·매칭·작성 세 기능의 공통 소스 | 소스가 갈라지면 동기화 비용과 불일치 위험 발생 |
| **② 모든 값에 출처(provenance) 태깅** | 추출된 모든 값에 "어느 파일 몇 페이지" 근거를 매단다 | brain 원문 보기, 계획서 근거 표시, 환각 방지를 한 번에 해결. 나중에 붙이면 불가능 |
| **③ RAG는 작성 단계에서만** | 추출·매칭·시각화는 RAG가 아님. 검색 대상은 오직 유저 본인 문서 | 매칭은 필드 판정, 작성은 원문 근거 서술 — 성격이 다름 |

## 3. 핵심 데이터 모델: 통합 그래프

"brain 시각화 = RAG 인덱스 = 매칭 소스"를 하나의 구조로 통일한다.
**중요: 진짜 그래프DB(Neo4j)가 아니라, 관계형/문서 저장 + "노드로 청크를 필터링해 꺼내는" GraphRAG 로직만 채택한다.** 그래프DB는 다중 홉 추론이 필요할 때나 가는 것으로, MVP엔 오버스펙.

```
Document (raw 업로드 파일)
  └─ Chunk (전처리된 원문 조각 + 위치정보: 파일/페이지/표좌표)

Node (구조화 엔티티: 사업체 · 대표자 · 매출 · 특허 · 기술 · 팀 …)
  ├─ value          (구조화된 값)
  ├─ confidence     (추출 신뢰도, 0~1)
  ├─ status         (unverified / estimated / confirmed)
  ├─ source_type    (document / user_stated)  ← 근거 등급
  └─ evidence ──▶   자기 근거가 되는 Chunk[]

Edge (노드 간 관계)
```

- `Node.value` → **매칭·시각화**가 사용
- `Node.evidence`(청크) → **사업계획서 작성**이 사용
- `confidence` + `status` → **어디를 유저에게 물어볼지**를 결정하는 핵심 필드
- `source_type` → 문서 근거(`document`)와 자기진술(`user_stated`)을 구분해 신뢰도·검수 우선순위에 반영

### 노드 예시 (프로필 JSON 개념도)

```json
{
  "business":  { "업종": "...", "창업연차": 2, "지역": "...", "단계": "초기" },
  "대표자":     { "나이": 34, "청년여부": true },
  "financials": { "매출_2024": { "value": 500000000, "source": "재무제표.pdf#3", "status": "confirmed" } },
  "assets":     { "특허": [ { "value": "...", "status": "출원", "source": "user_stated" } ] },
  "history":    { "기존_수혜": [ ... ] }
}
```

## 4. 유저 플로우 × 뒷단 로직

```
[0] 온보딩(seed 폼) ─────────────────▶ 문서 없이도 매칭 가능
        +
[1] 문서 업로드 → [2] 적재(async) → [3] 파싱 → [4] 구조화(추출·병합)
        ↓
[5] gap/status 스캔 → status 인터뷰(온보딩에서 몰아서 질문)
        ↓
   [통합 그래프 = brain = 매칭소스 = RAG인덱스]  ← 여기서 유저 준비 완료
        ↓
[6] brain 렌더 → [7] 공고 매칭 → 공고 선택 → [8] 사업계획서 무인 작성 → 내보내기
```

### [0] 온보딩 — 문서 업로드 *전* 최소 정보(seed 프로필)

문서만으론 초기창업자의 매칭 필드가 안 채워진다. 업로드 전에 폼으로 최소 정보를 받는다.

- 수집: 업종 / 창업일(→창업연차 자동계산) / 대표자 생년(→청년 판정) / 소재지 / 현재 단계(예비·초기·도약)
- **효과: 이 5~6개만으로 매칭은 즉시 가능.** 문서는 "매칭용"이 아니라 "계획서 근거용"으로 역할 분리 → 문서 미업로드 유저도 추천을 받아 이탈 감소

### [1]~[2] 업로드 → 적재 → 비동기 처리

- 업로드 순간엔 처리하지 않음. raw 파일은 오브젝트 스토리지, 메타만 DB
- 파일마다 처리 잡을 **큐에 넣고 파일 단위 독립 상태머신**으로 진행

```
uploaded → parsing → extracting → linking → needs_review / done / failed
```

- **파일별 상태 독립이 핵심.** 5개 중 hwp 1개가 `failed`여도 나머지 4개는 진행. 유저에겐 "4개 완료, 1개 실패(재업로드)"로 노출
- 전체를 한 트랜잭션으로 묶지 말 것 (하나 터지면 전부 무너짐)
- 실패 유형 분기: 일시 오류(OCR 타임아웃 등) → 재시도 큐 / 파서가 못 읽는 파일 → 유저 반송
- 프론트는 상태 폴링으로 "3개 중 2개 완료" 진행률 표시

### [3] 전처리(파싱) — 파일 타입별 완전 분기

조용히 가장 많이 실패하는 구간. 타입별로 완전히 다른 처리:

| 타입 | 처리 |
|---|---|
| 텍스트 PDF (IR·소개서) | 텍스트 레이어 추출 |
| 스캔 PDF·이미지 (사업자등록증 등) | **OCR 필수** (등록증은 거의 사진) |
| **hwp / hwpx** | **전용 파서 필수** — 정부·창업판 문서는 hwp가 지배적. 빠지면 서비스가 반쪽 |
| xlsx (재무제표) | **표 구조·셀 좌표 보존** — 뭉개면 연도-항목-값 대응이 깨짐 |
| docx / pptx | 텍스트 + 표 |

- 산출물: 위치정보(파일·페이지·표좌표)를 품은 **청크 세트**. 이 위치가 나중에 provenance로 회수됨
- 레이아웃 보존이 다음 단계 추출 정확도를 좌우

### [4] 구조화 — 다단계 + 신뢰도

한 번의 LLM 호출로 끝내지 않고 3패스:

1. **문서 종류 분류** — 등록증/재무제표/IR/특허 판별 → 종류별 맞춤 추출 프롬프트 선택
2. **종류별 필드 추출** — `값 + evidence 청크 + confidence` 동반 추출. 애매하면 낮은 confidence로 정직하게
3. **병합(entity resolution)** — 가장 어려운 부분:
   - 회사명·주소 표기 차이 → 정규화 후 매칭
   - **값 충돌**(소개서 매출 ≠ 재무제표 매출) → 둘 다 보관, 우선순위 룰(공식문서 > 자기작성)로 기본값 + `conflict` 플래그 → 유저 확인 대상으로 승격
   - **시점 문제** → 값에 연도를 붙여 저장

### [5] gap/status 스캔 + 인터뷰 (질문을 온보딩으로 앞당김)

> **설계 결정:** 질문 타이밍을 "작성 중"이 아니라 **"문서 업로드 직후(온보딩)"**로 옮긴다.
> 단, 이 시점엔 아직 공고를 안 골랐으므로, gap 기준을 **특정 공고가 아니라 "공통 사업계획서 정보모델(PSST)"**에 대고 검사한다.

**공통 슬롯 (PSST 표준):**

| 대분류 | 필요한 정보(슬롯) |
|---|---|
| 문제인식 (Problem) | 타겟 고객, 시장 문제, 시장 규모 |
| 실현가능성 (Solution) | 제품/기술 단계, 개발 현황, 검증(POC) 여부 |
| 성장전략 (Scale-up) | 비즈니스 모델, 매출 계획, 자금 계획 |
| 팀 (Team) | 대표 이력, 팀 구성, 핵심 인력 |

- 스캔: 공통 슬롯 중 **비었거나 confidence 낮은 노드만** 추림
- 인터뷰: 추려진 것만 **"지금 어떤 상태예요?"**로 질문 → 열린 질문 대신 **status enum 객관식**으로:

| 노드 | 상태 enum |
|---|---|
| 제품 | 아이디어 / 기획 / 프로토타입 / MVP출시 / 매출발생 |
| 특허 | 없음 / 준비중 / 출원 / 등록 |
| 매출 | 없음 / 발생(→재무제표 자동, 없으면 예상치 입력) |
| 팀 | 대표 혼자 / 구인중 / 핵심인력 확보 |
| 검증(POC) | 없음 / 진행중 / 완료(→수치 입력) |

- 객관식이라 유저 부담↓, 답이 그대로 구조화 노드로 편입되어 병합 깔끔
- 이렇게 받은 값은 `source_type: user_stated`로 태깅 (문서 근거보다 약한 등급)
- **효과: 공통 슬롯을 온보딩에서 채워두면 어떤 공고를 고르든 본문 90% 커버 → 작성이 무인으로 가능**

### [6] brain 렌더

- 확정 그래프를 노드·엣지로 프론트 렌더 (react-flow / Cytoscape)
- **배치는 궤도 + 구획.** 자동 배치(force-directed) 안 씀. 안쪽 원은 사업체 정보, 바깥 원은 사업 내용이고 바깥 원은 네 구획으로 나눈다. 노드 자리가 고정돼야 두 번째 볼 때 찾는다 (`05_그래프설계근거.md` 4.2)
- **엣지는 하위·관련 둘.** 중심에서 뻗는 하위는 실선, 항목끼리 잇는 관련은 얇은 점선 (`05` 4.3). 출처 엣지는 없앴다. 근거는 노드에 매달린 청크다 (`03_데이터모델.md` 11장)
- ~~confidence·status를 색으로 구분 (확정=진하게, 추정=흐리게, 미확인=점선)~~ → **색은 노드 종류만 말한다.** 상태는 배지 점과 점선 테두리, 그리고 패널의 글자로 표시한다 (`DESIGN.md` 4.1)
- 노드 클릭 → 매달린 evidence 청크 원문 표시
- **형식 온톨로지·그래프DB 미사용** — JSON/관계형 저장 + 프론트 시각화로 충분
- 매칭 후엔 "이 공고가 왜 추천됐는지"를 속성 노드↔공고 요건 엣지로 표시 → 설명가능성(차별점)

### [7] 공고 매칭 — 현실 반영

공고 DB는 미리 ETL로 수집·구조화하되, **"구조화가 안 되는 공고가 태반"**이라는 전제로 설계:

1. **하드 필터(결정론)** — 구조화된 요건(창업연차·나이·지역·업종)으로 부적격 먼저 제거
2. **소프트 랭킹** — 남은 것 중 "사업 방향 ↔ 공고 취지" 적합도를 임베딩으로 순위
3. **LLM 판정 폴백** — 자격요건이 텍스트로만 있는 공고는 LLM이 프로필 대비 적격성 판단하되 **"확인 필요"로 표시**(확정 아님)

**한국 정책판 특유의 함정 (반드시 반영):**

- **청년 정의가 부처마다 다름** (만 34세 vs 39세) → 나이 필터를 공고별 기준으로 개별 적용
- **중복수급 제한** → 프로필의 `기존_수혜이력` 노드와 대조해 배제
- **예산 소진·접수기간** → 만료/마감 공고 강등 (실시간성 데이터 → ETL 주기 중요)

### [8] 사업계획서 작성 — **무인(無人)**

> **설계 결정:** 작성 중엔 유저에게 묻지 않는다. 끝까지 자동 생성. (질문은 [5] 온보딩에서 이미 완료)

1. **목차 확정** — 공고 양식 파싱(있으면), 없으면 PSST 표준
2. **슬롯 정의** — 항목별 필요한 정보 조각 명시
3. **항목별 생성(RAG)** — 해당 노드에 매달린 evidence 청크만 retrieve(**per-user 격리 필수**) + 공고 평가기준 주입 → 초안 생성
   - **숫자·고유명사는 retrieve된 값만 사용.** 근거 없으면 지어내지 말고 `[확인 필요: OOO]` 플레이스홀더로 본문에 박음
   - 문단별 근거 표시(③의 provenance 회수)
4. **residual gap 처리** — 공고 특화 항목이라 온보딩에서 못 걷은 gap은 **작성을 멈추지 않고** `[확인 필요]`로 마킹만
5. 완성본 상단에 "보완 필요 N곳" 요약 → 유저가 검토 화면에서 그 자리만 채움
6. 확정 → 공고 양식(hwp/docx)으로 조립·내보내기

> **핵심:** 인터럽트(작성 중 질문)가 아니라 **결과물 위의 마킹**으로 처리. 무인 생성 + 사후 보완.

## 5. RAG 적용 범위 (혼동 방지)

| 항목 | 내용 |
|---|---|
| **RAG 대상** | **오직 유저 본인이 업로드한 문서** (per-user 격리) |
| 공고 DB | 매칭에서 소비(룰 필터). 작성 시엔 공고 1개라 통째로 컨텍스트 주입 → 검색 불필요 |
| 왜 유저 문서인가 | 프로필은 손실 압축이라, 원문에만 남은 서술·수치를 항목별로 꺼내야 함 |
| MVP 단순화 | 유저 문서가 짧으면 RAG 없이 추출 텍스트 통째 주입(long-context)으로 시작. 문서량↑·근거추적 필요 시 RAG로 승격 |
| (선택) 별도 corpus | 과거 선정 우수 계획서 샘플 = 문체·구성 참고용 few-shot. 유저 문서와 완전 분리. 확보 난이도로 MVP 제외 가능 |

## 6. "복잡한 서비스"의 실제 무게가 실리는 곳

초기 해피패스 설계 대비 실제로 어려운 지점들 — 개발 공수는 여기에 몰린다.

1. **문서 파싱의 현실** — hwp 파서, OCR 품질, 재무제표 표 구조 보존
2. **추출 신뢰도 + 사람 검수 루프** — confidence 낮거나 conflict 있는 노드만 골라 유저 확인
3. **entity resolution(병합)** — 여러 문서의 값 충돌·시점·표기 차이 정리
4. **공고 데이터 정규화** — 부처마다 제각각인 자격요건을 같은 스키마로. **이게 진짜 해자이자 제일 아픈 부분**
5. **정보 부족 대응** — 초기창업자는 문서가 얇음 → status 인터뷰로 그래프를 성장시키는 게 실질 기능

## 7. 함께 확정할 미결정 사항 (개발 논의 안건)

| B | **큐/워커 스택** | 비동기 처리 인프라 (예: 메시지 큐 + 워커). 파일별 상태머신 관리 방식 |
