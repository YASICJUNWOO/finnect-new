# ADR-0056: 위키를 동적 노드 트리로 바꾸고, 매칭 정보를 따로 뽑는다

## 맥락

[ADR-0052](0052-위키-자리를-기획-트리로-바꾸고-구획을-폴더로-세운다.md) 가 화면의 단위를 기획 트리 **자리 47 고정**으로 바꿨다. 그날 저녁에 그 결정이 두 군데서 무너졌다.

**① 표가 사업을 못 따라간다.** 자리 47 중 **21이 빈다.** 빈 이유가 「아직 안 올렸다」가 아니라 **「우리 topic 표에 그 자리가 없다」**다 — `Plan/KPI` · `마케팅` · `채용` · `Market/산출식-TAM` 은 사업계획서에 실재하는 항목인데 표에 없다. 표를 늘려도 다음 업종에서 또 빈다. 기획 문서 자신이 §6 마지막 줄에 「topic 온톨로지도 늘려야 한다」고 적어 뒀고, 그건 이 구조가 계속 손을 요구한다는 뜻이다.

**② 값의 이름이 사전이 되어 간다.** `VALUE_ALIASES` 43개가 picture 코퍼스 7건에서 나온 것이다. `직원수`·`팀 규모`·`인력 현황` 이 오면 `uncategorized` 로 떨어지고, 그건 자격 판별 입력이라 **그 회사가 규모 조건 공고에서 조용히 빠진다.**

셋째로, 자리 47 안에서 **값과 문장이 배타적이었다.** `place_kind` 가 `value|event|uncategorized` 셋 중 하나라 한 사실이 둘 다일 수 없었고, 「어느 값이 어느 자리에 뜨나」를 우리가 `TREE.values=(...)` 로 손수 적어야 했다.

## 결정

### 1. 트랙을 둘로 가른다

**같은 문서를 읽지만 찾는 것이 다르고, 화면도 다르다.**

| | **트랙 A — 노드 추출** | **트랙 B — 매칭 정보 추출** |
|---|---|---|
| 묻는 것 | 「이 문서가 우리 사업에 대해 뭐라고 말하나」 | 「소재지·직원 수·업종은 얼마인가」 |
| 질문 수 | **모른다.** 문서가 정한다 | **14개 고정** |
| 화면 | `/wiki` 그래프 | `/company` 회사 정보 표 |
| 쓰는 곳 | 사람이 읽는다 · 집필(G) | 자격 판별(M1) · 적합도(M2) |
| 잘한 기준 | 풍부한가 | **14칸 중 몇 칸** |
| 실패하면 | 위키가 얇다 | **공고가 목록에서 사라진다** |

**호출을 나눈다.** 튜닝 방향이 반대다 — A 는 넓게 뽑아야 하고 B 는 빠뜨리면 안 된다. 한 프롬프트에 섞으면 둘 다 어중간해진다. 그리고 **B 만 정확도를 잴 수 있다**(14칸 중 몇 칸) — A 는 정답지가 없다.

### 2. 트랙 A 는 세 층이고 고정은 맨 위 하나뿐이다

```
category   Company · Custom/특허            최상위 10 고정 · 하위는 동적
  node     팀 · 등록-10-2025-0114882        .md 한 장 · 그래프 점 하나 · 동적
    key    직원 수 · 팀 구성                  VALUE 또는 EVENT · 동적
```

최상위 카테고리 열은 기획 문서 §2 의 것이다.

```
Company · Product · Market · Competitor · Customer
BusinessModel · Financial · Plan · Events · Custom
```

**`Custom` 이 탈출구다.** 아홉에 안 맞는 것은 전부 여기로 온다 — 그래서 **어떤 사실도 갈 곳이 있고, `uncategorized` 가 없어진다.**

하위 카테고리 · 노드 이름 · 깊이 · key 이름 · 한정어는 **전부 LLM 이 만든다.**

### 3. `key` 하나가 라벨이자 병합 키다

`fact_key` 라고 부르지 않는다. **VALUE 쪽에서 거짓말이 되기 때문이다** — `직원 수` 는 행 넷(7·8·10·15명)이 공유하므로 그것만으로 사실이 정해지지 않는다. `key` 는 「이 자리의 이름」이라 양쪽에 다 맞고, 병합 규칙은 타입이 따로 정한다.

**EVENT 의 key 도 사람이 읽는 말이다.** 지금은 `pilot_retention_34_51` 같은 내부 id 라 화면에 못 냈다. `재구매율 상승` 으로 바꾸면 **라벨과 열쇠가 한 문자열**이 되고 화면·마크다운·병합이 같은 것을 쓴다.

| | 정체성 | 병합 |
|---|---|---|
| category | 경로 | 같은 경로면 같은 것 |
| node | 경로 | 같은 경로면 같은 것 |
| key · VALUE | `(key, 한정어, 시점, 값)` | 시점 다름 → 시계열 · 시점 같고 값 다름 → **충돌** |
| key · EVENT | `(node, key)` | 같으면 근거만 더한다 |

### 4. `.md` 는 사실이 붙은 노드다. 자식이 있든 없든

```
사실이 붙은 노드는 전부 .md 다. 안 붙은 노드는 뼈대일 뿐이다.
```

「잎만 `.md`」로 하면 **지금 잎인 노드에 자식이 생기는 날 그 내용이 갈 곳을 잃는다.** 사용자가 보고 있던 자리가 사라지는 일이라 안 한다. 옵시디언의 폴더 노트와 같은 모양이다.

**그래프는 `.md` 가 아닌 노드도 점으로 그린다.** 카테고리 열은 비어도 뜬다 — 무엇이 없는지 보여야 한다(`DESIGN.md` §7-5).

### 5. 트랙 B 는 평평하다. 고정 14 + `dated`

```
상호 · 사업자등록번호 · 법인등록번호 · 개업연월일 · 대표자 · 대표자 생년월일
소재지 · 업종(업태) · 업종(종목) · 직원 수 · 자본금 · 매출액 · 조달액 · 수혜 이력
```

category 도 node 도 없다. **그래프에 안 뜬다.** 회사 정보 표 한 장이다.

`dated` 플래그가 남는 이유는 **병합 규칙이기 때문이다.** 사업자등록번호에 문서 날짜가 붙으면 같은 번호가 문서 수만큼 행이 된다 — 시점을 떼야 하나로 모인다. 이건 문서를 읽어서 아는 게 아니라 그 값의 정의라서 LLM 에 맡기면 회차마다 흔들린다.

`ValueSpec.qualified` 는 **읽는 코드가 하나도 없다. 지운다.** `eligibility` 는 값의 성질이 아니라 「우리가 자격 판정에 쓰기로 한 목록」이라 `match/` 로 옮긴다.

### 6. 갈라짐은 프롬프트에 현재 상태를 주고 번호로 답하게 해서 막는다

동적 이름의 유일한 위험은 **같은 얘기가 여러 노드로 흩어지는 것**이다(`기능` · `주요기능` · `핵심 기능`).

**경로를 다시 쓰게 하지 않는다.** 자유 문자열로 받으면 `Product/기능`·`기능`·`Product/ 기능` 이 전부 새 노드가 된다. 번호로 답하게 한다.

```
## 지금 있는 노드
[1] Company/기본정보   [2] Company/팀   [3] Product/다시로/기능

## 답하는 법
있으면  {"node_ref": 3}
없으면  {"node_new": {"category": "Market", "path": "시장규모"}}
```

key 와 한정어도 같은 장치를 쓴다. 그리고 **코드가 마지막 그물이다** — `node_new` 가 와도 정규화(공백·구두점 제거) 후 기존과 정확히 같으면 조용히 기존으로 돌린다. **유사도는 안 쓴다** — 쓰면 다시 비결정론이다.

**한 호출 안에서도 갈릴 수 있다.** 프롬프트에 있는 건 이전 상태라, 한 파일에서 `기능` 과 `주요기능` 을 둘 다 만들 수 있다. 그래서 같은 호출 결과 안에서도 정규화 일치를 한 번 돌린다.

### 7. 저장

```
wiki_node                          wiki_fact
  company_id                         node_id     → wiki_node.  항상 있다
  path      "Company/팀"             key         "직원 수" · "팀 구성"
  category  "Company"  ← 고정 10     kind        value | event
  name      "팀"                     value · as_of · qualifier   value 일 때만
  parent    "Company"                text                        event 일 때만
                                     dedupe_key

company_value                      wiki_evidence
  company_id                         fact_id · chunk_id · quote
  key       headcount ← enum 14      **둘 다 여기로 근거를 맨다**
  value · as_of · qualifier
  status    current | superseded | conflict
```

`place` · `place_kind` · `topic` · `slot_key` 가 없어지고 `node_id` · `key` · `kind` 가 들어온다. **마이그레이션이 붙는다.**

**옛 데이터를 버리지 않는다.** `export.TREE` 가 topic → 경로 표를 이미 들고 있어서 기계적으로 옮길 수 있다 — 그 고정 표가 **동적 트리의 씨앗**이 된다.

## 결과

- **어휘가 다섯에서 셋으로 준다.** `sector`·`orbit`·`topic`·`place`·`place_kind` 가 없어지고 `category`·`node`·`key` 가 된다.
- **빈 자리 21이 없어진다.** 자리를 미리 안 세우니 「채울 topic 이 없다」는 상태 자체가 사라진다.
- **`uncategorized` 가 없어진다.** 카테고리는 enum 10 이라 LLM 이 항상 하나를 고른다.
- **표 하나가 없어진다.** 「어느 값이 어느 자리에 뜨나」(`TREE.values`)를 우리가 안 적는다.
- **자격 판별이 트리를 안 본다.** 트랙 B 가 이름으로 찾으므로 그래프가 어떻게 자라도 안 흔들린다([ADR-0013](0013-판정-두-층.md) 이 요구한 결정론이 여기서 지켜진다).
- **포기하는 것 ①** — **재현성이 약해진다.** 파일을 올린 순서가 노드 이름을 정한다. 사업계획서를 먼저 올리면 `기능`, 피치덱을 먼저 올리면 `주요 기능` 이 된다. **진짜 위험은 「이름이 뭐냐」가 아니라 「하나로 안 모이냐」**이고, 이름 자체는 어느 쪽이든 사용자가 읽고 이해한다.
- **포기하는 것 ②** — **같은 값이 두 트랙에 따로 뽑힌다.** 트랙 A 의 `Company/팀` 에 「직원 수 15명」이 있고 트랙 B 에도 `headcount=15` 가 있을 수 있다. 호출이 둘이라 **한쪽이 15, 한쪽이 10 이 될 수 있고 아무도 안 잡는다.** 줄이려면 B 를 먼저 돌려 그 결과를 A 프롬프트에 넣어 「이미 뽑았으니 다시 내지 마라」로 하면 되고, 그건 나중에 붙일 수 있다.
- **그래프가 방사 트리(마인드맵)가 된다.** 중심(회사) → 카테고리 열 → 노드 → 하위 노드로 **간선이 뻗는다.** 궤도·링·구획 호를 안 쓴다 — 저것들은 깊이가 둘로 고정일 때만 성립하고, 동적 트리는 깊이가 정해져 있지 않다. 카테고리마다 각도 구간을 갖고 **그 폭은 제 아래 잎 수에 비례한다.** 각도가 뜻을 갖는다는 [ADR-0017](0017-위키-그래프-궤도-배치.md) 의 성질은 그대로다.
- **점마다 이름이 붙는다.** 방사 트리는 가지를 따라 라벨이 퍼져서 47개도 들어간다 — 한 링에 몰아넣을 때 26px 간격이라 라벨을 못 붙이던 문제가 여기서 없어진다.
- **포기하는 것 ③** — **헤어볼 상한이 없어진다.** [ADR-0017](0017-위키-그래프-궤도-배치.md) 이 「50개 넘으면 길찾기에 쓸모없다」고 적었는데 동적이면 제한이 없다. 방사 트리가 가지로 갈라 주어 궤도보다는 오래 버티지만 **상한이 사라진 것은 사실이고, 그 수를 넘는 날 다시 봐야 한다.** 그때 쓸 것은 [ADR-0017](0017-위키-그래프-궤도-배치.md) 결정 4 의 국소 뷰다.
- **포기하는 것 ④** — **잘못 병합하면 되돌릴 도구가 필요하다.** 근거가 사실마다 붙어 있어 나누는 것은 가능하지만 화면 작업이 하나 는다.
- **계측을 반드시 붙인다.** **한 파일이 만든 신규 노드 수를 센다.** 갑자기 늘면 이름이 갈리는 중이고, 그것 말고는 위키가 갈라지는 것을 볼 방법이 없다 — 사용자는 노드가 셋인 게 정상인지 모른다.
