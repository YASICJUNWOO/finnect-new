# hwp 되쓰기 실측 — 글자모양과 줄정보 (2026-08-26)

[ADR-0073](../0073-hwp-를-갈-때-글자모양과-줄정보를-같이-간다.md)의 근거.

## 모수

| | |
|---|---|
| 파일 | **HWP5 20건** — `data/attachments` 9 · `spike/data/files` 11 |
| 칸 | 4,336 |
| 문단 | 8,910 (`PARA_TEXT` 가 있는 것 6,898 · 빈 문단 2,012) |
| **한/글 육안** | **0건** — 이 서버에 Java·LibreOffice·한/글이 다 없다 |

**규모가 작고 한/글로 열어 본 것이 없다.** 이 숫자로 「hwplib 폴백을 지운다」를 확정하지 않는다 — ADR-0060 결정 3 이 요구하는 규모(양식 20건 · 육안)에서 육안 쪽이 비어 있다.

## 1. 안 틀린 것 — 좌표

빈 칸 821개를 채워 저장하고 **다시 파싱해 대조**했다.

```
재파싱 성공                20 / 20
격자가 원본과 같다          20 / 20
엉뚱한 칸에 들어간 것            0
안 건드린 칸이 바뀐 것           0
같은 크기 포장 실패              0
```

`PARA_HEADER.nChars` 규칙도 맞았다 — **원본 6,898문단에서 `PARA_TEXT` 의 WCHAR 수와 100% 일치**(플래그 마스킹 후). `edit()` 이 쓰는 `len(text) + 1` 이 그 값이다.

즉 「밀려서 씀」·「잘못된 칸」의 뿌리가 **쓰는 층이 아니다.**

## 2. 문단에 매달린 레코드의 순서

```
문단 뒤에 붙는 것        TEXT/CS/LS   6,887
                        CS/LS        2,012
                        TEXT/CS         11
`PARA_RANGE_TAG`             0 / 8,910
줄정보가 아예 없는 문단        11 / 8,910   ← nLineSegs = 0. 규격 안의 상태다
빈 문단의 글자모양 쌍         전부 1쌍 (2,012 / 2,012)
빈 문단의 줄정보              전부 1개 (2,012 / 2,012)
```

빈 문단이 전부 한 쌍이라 **조각 접기는 빈 칸에서 아무 일도 안 한다.**

## 3. 틀린 것 — 옛 방식 대 새 방식

채운 문단 5,082개(칸 전부 + 표 밖 빈 문단)에서 잰 것이다. 「옛 방식」은 `nChars` 와 `PARA_TEXT` 만 고치던 ADR-0070 판본이다.

| 채운 문단에서 | 옛 방식 | 새 방식 |
|---|---:|---:|
| 글자모양 조각이 둘 이상 → **값이 잘린다** | 361 | **0** |
| 조각이 새 글자 수 밖을 가리킴 → **규격 위반** | 69 | **0** |
| 줄정보가 둘 이상 → **글자가 겹친다** | 382 | **0** |
| 줄정보가 새 글자 수 밖을 가리킴 | 94 | **0** |
| 줄정보를 버려서 한/글이 다시 계산한다 | 0 | 4,266 |
| 머릿수(`nCharShapes`·`nLineSegs`)가 레코드와 어긋남 | 0 | **0** |

머릿수가 옛 방식에서도 0 인 이유는 **레코드와 개수를 둘 다 안 건드려서 서로는 맞았기** 때문이다 — 둘이 같이 낡았다.

버린 줄정보가 5,082 중 4,266 이고 나머지 816 이 **비어 있던 표 칸**이다(거기서는 안 버린다).

나머지 둘도 같은 모양이고 하나는 `#0000ff` 였다. **글꼴과 크기는 같고 색이 갈렸다** — 조각을 가르는 것이 글꼴만이 아니다.

## 5. 값 칸이 물고 있는 서식

빈 값 칸 892개에서, 그 자리를 부른 행 라벨의 글자모양과 비교했다.

```
라벨 서식을 찾을 수 있다      408 (45.7%)
  같다                      180 (20.2%)
  다르다                    228 (25.6%)
    굵기가 다르다            160 (17.9%)
    크기가 다르다             91 (10.2%)
    글자색이 다르다            54 ( 6.1%)
    글꼴이 다르다             36 ( 4.0%)

빈 칸이 물고 있는 크기(pt)   11.0:324 · 10.0:284 · 12.0:74 · 8.0:54 · 9.0:37
                            2.0:27 · 6.0:25 · 1.0:16 · 15.0:13 · 18.0:11
빈 칸이 물고 있는 글꼴        맑은 고딕 279 · 휴먼명조 193 · HY신명조 131
                            함초롬바탕 92 · 한양중고딕 70 · 굴림 29
```

**굵기 차이는 고칠 것이 아니다** — 라벨이 굵고 값이 보통인 것이 정상이다. 색과 크기가 남는 문제이고, ADR-0073 은 그것을 **안 고쳤다**(정하지 않은 것 1).

## 6. 이름 층 — 단위와 안내문

`label_paths` 가 이름을 붙인 자리에서, 이름에 단위 단독 칸이나 통째로 괄호에 싸인 안내문이 섞인 비율이다.

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 이름 붙은 자리 | 842 | 791 |
| 이름이 유일 → 채울 수 있다 | 243 | **245** |
| 머리가 단위 | 4 | **0** |
| 머리가 안내문 | 8 | **0** |
| 라벨에 단위 | 2 | **0** |
| 이름 없음 → 목록에 안 온다 | 50 | 101 |

**이름 붙은 자리가 51개 줄고 유일한 이름은 2개 늘었다.** 줄어든 51개는 단위 칸이나 안내문이 이름을 대던 자리다.

남은 「라벨에 안내문 16」은 **측정 쪽의 오탐이다** — `(공정거래위원회) 공정거래법 … 위반 사실이 없음을 확인합니다.` 처럼 괄호로 *시작하는* 진짜 이름이고, 코드는 **통째로 싸인 것만** 본다.

### 육안 — 표 하나 75칸 (병합 70)

| 자리 | 고치기 전 | 고친 뒤 |
|---|---|---|
| (6,11) | `초기창업 현황 › 기업명 › (기업의 경우만 작성) › 대표자명 E-mail × 명` | `대표자명 E-mail` |
| (7,3) | `초기창업 현황 › 사업자등록번호 × (기업의 경우만 작성)` | `초기창업 현황 › 사업자등록번호` |
| (7,11) | `법인등록번호 × 명` | `법인등록번호` |
| (8,11) | `초기창업 현황 › 전년도매출액 › 백만원 › 업종/업태 × 명` | `업종/업태` |
| (11,3) | `아이템명 × 사무직` | `아이템명` |

나머지 다섯은 전후가 같았고 둘 다 맞았다. **10/10 이 제 이름이다.**

`× 사무직` 은 `종업원수 | 사무직 | 00 명 | 기술직 | 00 명 | …` 행이 「라벨 셋 이상」을 통과해 머리 행으로 인정된 것이다. 그 행은 머리가 아니라 **자기 값을 든 데이터 행**이다.

## 7. 안 고친 것 — 같은 크기 포장

값 길이별로, 채울 수 있는 자리를 전부 채운 뒤 원본 스트림 크기에 맞춰 포장한 성공률이다.

| 값 길이 | 10자 | 50자 | 200자 | 800자 | 2,000자 |
|---|---:|---:|---:|---:|---:|
| 성공 | 95% | 95% | 85~90% | 85~90% | **70%** |

**Java 가 이 서버에 없어서 실패는 `FormsUnavailable` 이다** — 그 파일은 아예 안 나온다. 줄정보를 버려서 스트림이 줄었지만 **이 숫자는 안 움직였다**(측정 오차 안). 뿌리는 `olefile` 이 CFB 를 새로 못 만드는 것이고, ADR-0070 이 「정하지 않은 것」으로 남긴 자리 그대로다.

## 재현

`data/attachments` 와 `spike/data/files` 의 HWP5 를 모아 `edit()` 을 돌리고 되읽는 스크립트로 쟀다. 레포에 안 남겼다 — 층 ①②(레코드 불변식 · 왕복 대조)는 `tests/test_forms_hwp5.py` 의 `Test글자모양과_줄정보` 가 손으로 만든 레코드로 같은 것을 잠근다.

**층 ③(실물 렌더 대조)이 비어 있다.** LibreOffice + [H2Orestart](https://github.com/ebandal/H2Orestart) 면 `soffice --headless --convert-to pdf` 로 hwp 를 직접 구울 수 있고, 그러면 원본 PDF 와 채운 PDF 를 쪽수·픽셀로 비교해 밀림을 자동으로 잡는다. **이 서버에 안 깔려 있고 `sudo` 가 대화형 인증을 요구해서 못 깔았다.**
