# 2026-08-18 올리기 경로 자원 실측 — OCR 이 얼마를 먹나

[ADR-0035](../0035-api와-워커를-자체-서버로-내리고-vercel은-화면만-맡는다.md)의 근거.
"올리기를 Vercel 에 둘 수 있나"를 묻기 위해 **가장 무거운 구간인 OCR** 한 쪽을 쟀다.

**표본이 1건이다.** 사업자등록증 스캔 픽스처 한 장이고, 여러 쪽 문서도 다른 회사 파일도
안 돌렸다. [ADR-0030 실측](2026-08-18-OCR-엔진-실측.md)이 시간을 이미 쟀으므로 여기서
새로 재는 것은 **메모리** 하나다.

## 잰 것

| | |
|---|---|
| 대상 | `tests/fixtures/wiki/사업자등록증_스캔.pdf` 1쪽 |
| 경로 | `finnect.attach.ocr.pages_from_pdf()` — 제품이 실제로 부르는 함수 |
| 설정 | PP-OCRv5 `server` 검출 · 300dpi ([ADR-0030](../0030-OCR은-rapidocr-로컬로-하고-검출은-server-를-쓴다.md)) |
| 기계 | 2코어 · 7.9GB · OpenStack VM |
| 방법 | 별도 스레드가 5ms 마다 `/proc/self/status` 의 `VmRSS` 를 읽고, `/usr/bin/time -v` 로 대조 |

## 결과

```
구간            끝 RSS    구간 최대
파이썬만          13 MB       —
임포트            15 MB      14 MB
엔진 적재        334 MB     333 MB
OCR 1쪽         419 MB   1,863 MB
                          프로세스 최대 RSS 1,908 MB
```

| | |
|---|---|
| wall | 8.5초 |
| CPU | 13.9초 — **1.5코어** |
| 글자 | 281자 |

### 1. 스파이크는 추론에서 난다. 모델 적재가 아니다

모델 셋을 올리는 데 334MB 이고 거기서 끝나지 않는다. **1,863MB 가 OCR 구간에서 났고
끝나면 419MB 로 내려온다.** 한 번 치르고 마는 비용이 아니라 **쪽마다 반복된다.**

원인은 300dpi 렌더(2339×1653)를 `server` 검출 모델에 넣을 때의 중간 텐서다.

### 2. 체크포인트만 보면 4배를 놓친다

구간 경계에서만 RSS 를 찍으면 **442MB** 로 보인다. 실제 최대는 1,863MB 다.
**5ms 표본이 없었으면 "메모리는 문제없다"고 잘못 보고했을 값이다.**

### 3. 쪽수가 늘어도 최대 RSS 는 안 늘어난다

`pages_from_pdf` 가 쪽을 하나씩 렌더하고 텍스트만 쌓는다. 20쪽짜리도 최대는 그대로 1.8GB 이고
**늘어나는 것은 시간뿐이다** — 8.5초 × 20 ≈ 170초.

*이건 코드를 읽고 한 추론이다. 여러 쪽 문서로 확인하지 않았다.*

## 그래서 Vercel 한도와 어떻게 되나

| 사양 | 한도 | 실측 | |
|---|---|---|---|
| 메모리 | 3,009 MB | 1,820 MB | **통과** |
| 패키지 | 5 GB | 약 450 MB | **통과** |
| 실행 시간 | 300초 | 8.5초/쪽 | 35쪽 넘으면 초과 |

**셋 다 "못 한다"의 이유가 아니다.** ADR-0035 가 Vercel 을 접은 이유는 자원이 아니라
읽기 전용 파일시스템과 응답 뒤 작업이다.

### 패키지 450MB 의 내역

```
rapidocr        129 MB   (모델 128 MB 포함)
opencv          116 MB
cv2              72 MB
onnxruntime      61 MB
numpy            60 MB
pillow           14 MB
```

**예전 250MB 한도였으면 여기서 끝났다.** 5GB 로 늘어서 통과한다.

## 이 서버에서의 동시성

RAM 이 아니라 **코어가 상한을 정한다.**

| 동시 | RAM (available 5.7GB) | CPU (2코어) |
|---|---|---|
| 1 | 1.8 GB | 1.5 — 여유 |
| 2 | 3.7 GB | **3.0 — 막힌다** |
| 3 | 5.6 GB — 붙는다 | 4.5 |

**둘이 겹치면 8.5초가 15초 넘게 늘어난다.** `jobs` 락이 회사별(`wiki:{company_id}`)이라
회사가 다르면 실제로 겹칠 수 있다.

## 재현

```bash
uv sync --group ocr
uv run python - <<'PY'
import sys, time, threading; sys.path.insert(0, "src")
peak = {"v": 0.0}
def rss():
    for line in open("/proc/self/status"):
        if line.startswith("VmRSS:"): return int(line.split()[1]) / 1024
stop = False
def sample():
    while not stop:
        peak["v"] = max(peak["v"], rss()); time.sleep(0.005)
threading.Thread(target=sample, daemon=True).start()
from pathlib import Path
from finnect.attach import ocr
t = time.perf_counter()
pages = ocr.pages_from_pdf(Path("tests/fixtures/wiki/사업자등록증_스캔.pdf"))
print(f"{time.perf_counter()-t:.1f}초 · 최대 {peak['v']:.0f} MB · {sum(map(len, pages))}자")
PY
```

## 안 잰 것

- **여러 쪽 문서.** 3번은 코드를 읽은 추론이다
- **HWP·DOCX·XLSX 파싱의 메모리.** OCR 보다 훨씬 가벼울 것이나 재지 않았다
- **동시 실행.** 표의 2·3행은 1건 실측을 곱한 값이지 측정값이 아니다
- **LLM 추출기가 붙은 뒤.** 아직 스텁이다([ADR-0031](../0031-사실-추출을-포트-뒤로-미루고-스텁으로-배관을-먼저-세운다.md))
