# plan/ — 구현 계획과 진행 상태

무엇을 만들지는 [`../SPEC.md`](../SPEC.md)에, 왜 그렇게 정했는지는 [`../adr/`](../adr/)에 있다. 여기는 **어떤 순서로 만들지, 그리고 지금 무엇이 막혀 있는지**를 다룬다.

> **진행 상태는 이 문서가 정본이다.** 다른 문서는 여기로 링크만 건다. 상태가 바뀌면 여기와 해당 계획 파일의 `상태:` 줄만 고친다.

---

## 지금 상태

**저장소가 실행 가능하다.** [06 슬라이스](06-목록-수집과-조회.md)의 코드가 들어갔다. `uv sync` → `docker compose up -d db` → `alembic upgrade head` → 화면까지 [`README.md`](../../README.md)만 보고 통과한다.

두 출처의 목록 API가 DB에 쌓이고, `/notices`에서 목록·상세를, `/ingest`에서 수집 실행을 본다. 첨부는 메타데이터만 담고 LLM은 아직 안 부른다.

스파이크 코드(`spike/`)는 여전히 버리는 코드다.

### 아직 안 한 것

**실측 기록이 계획 파일 안에 있다.** [T-0009](06-목록-수집과-조회.md#t-0009-api-실측-기록)가 그걸 `adr/evidence/`로 옮기는 일이다. 계획은 완료되면 상태만 바뀌는 문서라 실측값의 정본이 될 수 없다. **06에서 유일하게 남은 태스크다.**

**L1 추출 스키마는 아직 안 정했다.** 코퍼스를 눈으로 보고 정한다.

**상세 화면이 원문 payload를 안 편다.** [T-0013](06-목록-수집과-조회.md#t-0013-조회-화면)의 검증 항목 하나가 미충족이다. 컬럼과 `raw_fetch_id`까지만 보여준다.

### 막혀 있는 것 하나

[ADR-0010 배점 전제 폐기](../adr/0010-배점-전제-폐기.md)가 **미결**이다. 실측 결과 초기창업패키지·창업도약패키지가 **항목별 배점을 공개하지 않는다.** 창업 분야 전체로도 명시율 25%다. 승부처 화면(S3)이 배점 순 정렬을 전제했으므로 축을 다시 잡아야 한다.

이것이 [04 화면](04-화면.md)의 S3·S4와 [05 집필](05-집필.md)을 막고 있다. [00 미결 해소](00-미결-해소.md)에서 푼다.

**막히지 않은 것**: [01 기반](01-기반.md), [02 수집과 추출](02-수집과-추출.md), [03 자격 판별](03-자격-판별.md)은 병행 가능하다.

## 순서를 이렇게 잡은 이유

마감은 없다. 그래서 **틀린 문서를 미리 쓰지 않는 것**이 이 계획의 원칙이다. 골격(계층 경계, 데이터 모델, API 계약)은 나중에 바꾸면 전부 뜯어야 하므로 먼저 정하고, 계층별 상세 사양(추출 스키마, 요건 표현식, 집필 프롬프트)은 **코퍼스를 보고 나서** 정한다.

근거: 이전 제품의 추출 스키마가 자립준비청년 특화 필드로 짜여 있어 타깃이 바뀌자 통째로 갈아야 했다([ADR-0009](../adr/0009-구-백엔드-재사용-보류.md)). **스키마 모양은 코퍼스가 결정한다.**

**판별이 집필보다 먼저다.** 집필은 판별 결과 위에서 도는데(`SPEC.md` §3), 판별 없이 집필만 만들면 어차피 나중에 배선을 다시 해야 한다.

**화면이 집필보다 먼저다.** F3·F4·F9는 L2 출력만 있으면 완성된다. 여기까지만 해도 "신청 가능한 공고를 찾아준다"는 절반의 제품이 선다. 집필은 그 위에 얹는다.

**수집이 맨 앞이다.** 실측에서 확인했듯 평가 정보는 공고 본문에 0%다. 첨부를 열지 않으면 아무것도 못 한다([ADR-0008](../adr/0008-제품-범위-확대.md)).

## 각 단계에서 쓸 문서

단계에 들어갈 때 그 단계의 사양을 쓴다. 미리 쓰지 않는다.

| 단계 | 그때 쓸 문서 |
|------|-------------|
| 01 | `architecture.md`, `data-model.md`, `api-contract.md` |
| 02 | `spec-ingest.md`, `spec-extract.md` |
| 03 | `spec-eligibility.md` (요건 표현식 포함) |
| 05 | `spec-drafting.md` (프롬프트·가드 포함) |
| 전 단계 | `testing.md` — 판정 정확도를 무엇으로 재는지 |

위치는 `plan/` 옆이 아니라 별도로 정한다. 사양이 SPEC의 하위인지 독립인지는 01에서 결정한다.

```
# plan/NN — 제목

> 상태: 계획중 | 진행중 | 완료 | 폐기
> 선행: NN 또는 —

## 목표        무엇이 되면 이 단계가 끝인가
## 할 것       SPEC의 어느 기능을 구현하는가
## 태스크      T-NNNN. 각각 완료 조건과 건드리는 파일을 단다
## 검증        실행 가능한 pass/fail. 없으면 TODO로 남긴다
## 나오는 것    산출물
```

완료한 계획은 삭제하지 않고 `상태:`만 바꾼다.
