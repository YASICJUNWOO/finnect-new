**항목이 서로 독립이다.** 병렬로 돌고, 하나가 실패해도 나머지가 남고([ADR-0015](../adr/0015-무인-생성.md) 결과 절), 하나만 다시 쓴다([ADR-0028](../adr/0028-초안을-먼저-완성하고-못-채운-자리에서-묻는다.md) 3번). **문서 전체를 들고 도는 루프로 만들지 않는다** — 그러면 셋 다 안 된다.

**자율 루프가 아닌 이유가 하나 더 있다.** 항목이 최대 102개다([11](11-작성-항목-추출과-표시.md) 실측 · 독자 AI 사업수행계획서). 항목마다 종료를 모델이 정하면 한 초안에 호출이 곱해지는데, F6-1 이 "진입하면 이미 써져 있다"라 **언제 끝나는지 모르는 것을 그 자리에 둘 수 없다.**

- **항목 단위 함수가 아니다.** 항목 제목만 보고 정할 수 없다. 포항시 양식이 그 증거다 — `2-1 사업수행 배경 및 목적`과 `2-2 지원필요성`의 지시문에 **"필요성"이 둘 다 있다.** 항목들 사이 관계를 봐야 한다

- **회사와 무관하다.** `document` 가 콘텐츠 주소라(sha256) 한 번 계산하면 **그 양식을 쓰는 모든 공고·모든 회사가 쓴다.** 저장은 `document_item` 쪽에 붙이고 `decided_by` 를 남긴다 — `document.decided_by` 와 같은 규율이다
- **PSST 를 하드코딩하지 않는다**([11](11-작성-항목-추출과-표시.md) · 문제인식·실현가능성·성장전략이 다 있는 첨부는 2,827건 중 **9건**이다)
- 정확도를 **손 라벨과 대조해 잰다.** 여기가 결정론으로 안 풀리면 사용자 청크 벡터 검색을 그때 얘기한다(`SPEC.md` §9-7). **재기 전에는 고르지 않는다**

#### 세션을 스레드가 만나지 않게 3단으로 가른다

앞의 구조는 `Session` 을 LLM 호출 내내 붙잡고 있어서 스레드를 못 얹었다. 못 얹는
이유가 셋이었다.

1. **`Session` 은 스레드 안전하지 않다.** 항목 67개면 트랜잭션이 몇 분간 열려 있다
2. **`s.flush()` 로 id 를 받아 쓴다.** 동시에 flush 하면 세션 상태가 깨진다
3. **`Usage.calls += 1` 이 원자적이 아니다.** 하나를 공유하면 **토큰 수가 어긋난다** —
   "지어내지 않고 센다" 던 값이다

```
① 조립   세션 안 · 읽기만.  _FormPlan · _ItemPlan 으로 뽑는다 — ORM 객체를 밖으로 안 낸다
② 호출   세션 밖 · ThreadPoolExecutor.  집필기를 워커마다 새로 만든다
③ 저장   세션 안 · ordinal 순
```

- **집필기를 워커마다 새로 만든다.** `build_draft(writers=...)` 가 **인스턴스가 아니라
  만드는 함수**를 받는 이유다. 그러면 `unverified` · `dropped` · `Usage` 가 워커별로
  쌓이고 ③에서 합친다 — **lock 을 안 쓴다**
- **예외를 ②에서 잡아 문자열로 바꾼다.** ③에서 다시 던지면 트랜잭션이 통째로 죽어
  만든 항목까지 날아간다(ADR-0015 는 그 반대를 요구한다)
- **저장을 `ordinal` 순으로 못 박는다.** 같은 입력에서 같은 초안이 나와야 `--redo` 로
  무엇이 바뀌었는지 바이트로 본다 — 위키 마크다운에 시각을 안 넣은 것과 같은 이유다.
  `test_병렬과_순차의_결과가_같다` 가 이것을 막는다
- **스레드다. asyncio 가 아니다.** `llm.py` 가 호출마다 `httpx.Client` 를 열고 닫는
  동기 코드라 그대로 얹힌다. asyncio 로 가면 그 파일을 통째로 다시 써야 하고 얻는 것이 없다
- 동시 개수는 `DRAFT_WORKERS` (기본 8). **상한은 rate limit 이다** — 크게 잡으면 429
  재시도가 늘어 오히려 느려진다

**재작성이 같은 코드가 된다.** ①에서 그 항목만 조립하고 ②에서 워커 1개, ③에서 그 행만
갈아치우면 [ADR-0028](../adr/0028-초안을-먼저-완성하고-못-채운-자리에서-묻는다.md) 3번이다.

#### 구멍 1 — 공고 데이터를 제목 하나만 넘기고 있었다

`notice=(("공고", doc.title),)` 이었다. **F6-12 가 "금액·자격·마감일·고유명사는 공고
데이터와 근거 청크에서 온 것만" 이라고 허용한 자리인데 공고 데이터를 안 넘겨서
`verify()` 가 지원금액과 마감일을 지웠다** — 지키려다 허용한 것을 막고 있었다.

- `notice` 뷰만 읽는다. 출처별 표를 직접 읽으면 매핑이 둘이 되고 정본은 `views.py` 다
- 넘기는 것은 여섯 — 사업명 · 수행기관 · 주관기관 · 분야 · 접수기간 · **공고 내용**
- **공고 내용을 3,000자까지 넣는다.** 지원금액이 값으로 오는 필드가 없어서 본문에서만
  나온다(`bsnsSumryCn` · `pbanc_ctnt`). 짧게 자르면 금액이 잘리고 길면 프롬프트가 커진다
- **공고가 DB 에 없어도 돈다.** 재료가 얇을 뿐이다

#### 구멍 2 — 분량을 주기만 하고 안 재고 있었다

`draft/limits.py` 가 `limit_text` 를 읽어 잰다. **못 재는 것을 못 잰다고 말한다.**

| | |
|---|---|
| `500자 이내` | **잰다.** 넘으면 `over` |
| `10줄 이내` | 잰다 |
| `50페이지 내외` · `A4 2매 이하` | **`unmeasurable`.** 쪽 수를 글자로 환산하지 않는다 |
| `500자 내외` | `unmeasurable`. `내외` 는 초과 판정을 못 한다 |

- **환산율의 근거가 없다.** A4 한 장에 한글 몇 자인지는 서체·여백·줄간격이 정한다.
  관례로 1,800자를 쓰지만 관례는 근거가 아니다. **틀린 숫자를 내는 것보다 못 잰다고
  말하는 것이 낫다**
- **저장하지 않는다.** `limit_text` 와 `body` 로 계산되는 값이라 읽을 때마다 만든다 —
  들고 있으면 둘 중 하나가 먼저 낡는다(위키 마크다운과 같은 규율)
- **넘어도 다시 쓰지 않는다.** F1-5-5 가 자동 수정을 금지했다. 세어서 보고한다

#### 만들면서 하나 고쳤다

`draft_item.missing` 을 **배분 결과에서 다시 계산하고 있었다.** F6-6 은 "위키에 정보가
없어 못 쓴 자리" 인데, 그렇게 세면 **다른 항목이 그 사실을 맡은 경우까지 못 채움으로
잡힌다.** 위키에는 있는 것이라 물어볼 자리가 아니다. `allot` 이 계산한 것을 그대로 쓴다.

## 안 만든 것과 이유

- **집필 화면.** `SPEC.md` §5.2 는 S4 를 문서(F6)로 두는데 [09](09-사용자-앱-분리.md)와 CLAUDE.md 는 S4·S5 를 공고 목록·상세로 부른다. **화면 번호가 문서끼리 어긋나 있어서** 슬라이스를 열 때 먼저 정한다
- **질문과 답변 받기 (F6-7 ~ F6-9).** 못 채운 자리를 **표시하는 데까지**가 이 계획이다. 답을 받아 위키에 적립하는 것은 화면과 같이 온다
- **완성도 (F6-5)와 분량 (F6-14).** 초안이 서기 전에는 셀 것이 없다
- **적합도 (F3-2).** 집필의 선행이 아니다. 공고를 손으로 골라도 초안은 돈다
