## 0. v3에서 바뀐 것

| 항목 | v3 | v4 |
|------|-----|-----|
| 자격 판별의 위치 | 공고 상세에서 4열 대조표로 노출 | **화면 없음.** 엔진이 뒤에서 판정하고 결과가 목록이 된다 |
| 공고 상세 | 판정 표 + 근거 확인 | **요강 정리본.** 공고가 요구하는 것을 항목으로 나눠 보여준다 |
| 판정 3분류 | 충족·미충족·확인 불가를 화면에 노출 | 화면에서 사라짐. 신청 가능한 공고만 목록에 오른다 |
| 확인 불가 보완 | 표 안 인라인 입력 후 재판정 | 삭제 |
| 중복 수령 | 자격 표 한 행 + 신청 현황 경고 | 판별 엔진 안 요건의 한 종류로만. 화면 표시 없음 |
| 판별 조건 칩 | 목록 상단에 노출 | 삭제 |
| 내 정보 두 묶음 | 구분 표시를 기능으로 정의 | 탭으로 처리 |
| 디자인 기준 | 없음 | 1.4에 방침 추가 |

### 설계 원칙이 바뀐 지점

v3까지는 **판정 근거를 사용자에게 보여주는 것**이 신뢰를 만든다고 봤다. v4는 반대로 간다. **판정은 뒤에서 정확하게 하고 화면은 결과만 준다.**

사용자는 우리 판정을 검산하러 온 것이 아니다. 되는 공고를 알고 계획서를 쓰러 왔다. 검산 도구를 화면에 놓으면 사용자에게 우리 일을 떠넘기는 것이 된다.

## 1. 설계 기준선

### 1.1 확정 사항

아래 표는 원래 `PRD.md` 12장의 D1~D18 중 화면을 규정하는 것만 옮겨 적은 것이다. **그 `PRD.md`가 존재하지 않으므로 이 표가 D 결정의 유일한 기록이다.** 여기 없는 D3, D6~D10 여섯 개는 내용을 알 수 없다. 필요해지면 복원이 아니라 새로 결정한다.

### 1.2 화면 설계 원칙 여섯

1. **판별은 안 보인다.** 판정 과정과 근거를 화면에 늘어놓지 않는다. 목록에 오른 것 자체가 판정 결과다.
2. **공고는 구조로 보여준다.** 원문을 옮기지 않고 항목으로 나눈다. 원문 확인은 링크로 넘긴다.
3. **결론 먼저, 근거는 접는다.** 분석 화면에서 특히 지킨다.
4. **집필은 세 번에 나눠 한다.** 분석하고, 묻고, 쓴다.
5. **밀도는 높이되 구조를 준다.** 작업 도구라 스크롤보다 한 화면을 택한다. 그리드와 정렬을 지켜 밀도가 혼잡이 되지 않게 한다.
6. **확정 어투를 쓰지 않는다.** 최종 확인과 제출은 사용자 몫이다.

### 1.3 정보 밀도 규칙

정보 밀도 원칙을 화면 규칙으로 옮긴 것이다. 아래 여섯이 규칙 전부다.

1. 한 화면의 주요 정보 덩어리는 다섯에서 일곱이다. 넘으면 접는다.
2. 금액과 남은 일수는 우측 정렬한다.
3. 구분은 옅은 선과 여백으로 한다. 굵은 테두리 상자를 쌓지 않는다.
4. 채도 높은 색은 마감 임박과 경고에만 쓴다. 나머지는 무채색이다.
5. 긴 표는 헤더를 고정한다.
6. 목록은 카드보다 행에 가깝게 짠다. 카드 사이 여백이 크면 한 화면에 세 건밖에 안 들어간다.

### 1.4 디자인 방침

**어떤 디자인 시스템도 통째로 채택하지 않는다.** 우리 토큰을 쓰고 층별로 규칙만 빌린다.

| 층 | 기준 |
|----|------|
| 서체 | Pretendard. 없으면 시스템 한글 서체로 폴백 |
| 색 팔레트 | **GitHub Primer.** 목록과 표가 빽빽한 작업 도구를 위해 만들어진 팔레트라 우리 화면과 맞는다 |
| 색 사용 | 상태와 경고에만 색을 쓴다. 나머지는 무채색이다 |
| 접근성 | 색만으로 상태를 구분하지 않는다. 기호와 텍스트를 함께 쓴다 |
| 카피 | Polaris 방식. 사용자 행동 중심으로 쓴다 |
| 밀도 | Carbon 방식. 행 높이와 여백을 줄인다 |
| 목록 패턴 | Atlassian 방식. 상태별 그룹과 다음 행동 |
| 검사 | Vercel Web Interface Guidelines. 지킬 항목은 9.4에 옮겨 적었다 |

**KRDS는 쓰지 않는다.** 정부 사이트로 읽히면 안 된다. 사용자가 겪는 불편이 바로 공공 포털의 화면이라 그 언어를 옮기면 문제를 재현하는 것이 된다. 서체만 가져온다.

토큰은 9장에 정의했다.

| A1 | 로그인 없이 세션 단위로 동작한다 |

## 4. 화면별 흐름

### 4.1 S1 지원사업 리스트

1. **진입.** LNB 지원사업. 서비스 기본 화면이다.
2. **목표.** 신청할 수 있는 공고를 훑고 하나를 고른다.
3. **흐름.**
   1. 상단에 결과 한 줄을 둔다. 문구는 "신청할 수 있는 공고 7건"이다.
   2. 판별 엔진이 가능으로 판정한 공고만 행으로 나열한다.
   3. 각 행에 사업명, 주관기관, 출처 구분, 지원 규모, 마감까지 남은 일수를 둔다.
   4. 정렬 기본값은 마감 임박 순이다. D-7 이내는 색으로 강조한다.
   5. 출처 필터를 둔다. 전체, 중앙부처, 지자체.
   6. 행 우측에 준비 시작 버튼을 둔다. 누르면 신청 현황에 검토 중으로 들어간다.
   7. 행 본문 클릭 시 S2로 간다.
4. **설계 판단.**
   1. 카드가 아니라 행으로 짠 이유는 밀도다. 카드로 하면 한 화면에 세 건이 들어가는데 행으로 하면 여덟 건이 들어간다. 사용자는 목록을 비교하러 오므로 한눈에 많이 보이는 편이 낫다.
   2. 상단 문구에서 전체 공고 수를 뺐다. 42건 중 7건이라는 표현은 42가 사용자에게 의미 없는 숫자였다.
   3. 판별 조건을 화면에 노출하지 않는다. 조건이 궁금하면 내 정보에서 본다.
5. **빈 상태.** 0건이면 내 정보를 채우면 판단할 수 있는 공고가 늘어난다는 안내와 그 페이지로 가는 링크를 준다.

### 4.2 S2 공고 상세

1. **진입.** S1 행 클릭, 또는 S7 행 클릭.
2. **목표.** 이 공고가 무엇을 요구하는지 한 화면에서 파악하고 집필로 넘어간다.
3. **구성.** 위에서 아래로 여섯 블록이다.
   1. **개요.** 사업명, 주관기관, 출처, 접수 기간, 마감까지 남은 일수, 지원 규모, 접수 방법, 원본 공고 링크, 준비 시작 버튼.
   2. **지원 내용.** 무엇을 얼마나 어떤 기간에 주는지. LLM 정제를 허용하는 유일한 블록이다.
   3. **신청 자격.** 공고가 요구하는 요건 목록. 항목과 기준을 나눠 정리한다.
   4. **제출 서류.** 서류명, 지정 양식 여부, 비고. 양식 미준수 탈락 조건은 강조한다.
   5. **심사 방식과 배점.** 평가 단계와 항목별 배점을 표와 막대로. 초기창업패키지는 서류평가, 심층인터뷰, 발표평가 3단계다. ⚠️ **미확인.** 확인했다던 근거 문서가 존재하지 않는다. §11.2 참조.
   6. **유의사항.** 제출 후 수정 불가처럼 탈락으로 이어지는 조항.
4. **설계 판단.**
   1. 신청 자격 블록에 내 값이나 판정을 넣지 않는다. 이 화면은 공고를 설명하는 화면이지 나를 심사하는 화면이 아니다. 판정은 이미 목록 단계에서 끝났다.
   2. 제출 서류와 유의사항을 넣은 이유는 **지정 양식 미준수 탈락과 제출 후 수정 불가가 실제 탈락 사유이기 때문**이다. ⚠️ **미확인.** 근거 문서가 존재하지 않는다. §11.2 참조.
   3. 원본 공고 링크는 개요에 한 번만 둔다.
5. **하단.** 사업계획서 쓰기 버튼을 고정한다.

### 4.3 S3 계획서 공고 분석

승부처다. 배점과 판별이 만나야 나오는 화면이다.

1. **진입.** S2 하단 버튼, 또는 LNB 사업계획서에서 진행 중 문서 선택.
2. **목표.** 쓰기 전에 무엇을 어떻게 쓸지 합의한다.
3. **구성.**
   1. **결론 3줄.** 분석 결과를 세 줄로 먼저 말한다.
   2. **심사 항목과 배점.** 배점 높은 순. PSST 항목명을 쓴다.
   3. **목차 구조.** PSST인지 자체 양식인지, 항목이 몇 개인지, 분량 제한이 얼마인지.
   4. **강조할 지점.** 배점 큰 항목과 내 강점이 겹치는 곳.
   5. **아직 모르는 것.** 초안을 쓰려면 필요한데 없는 정보. 각 줄에 심사 항목과 배점을 붙인다.
4. **흐름.** 진입 즉시 분석이 돈다. 결론 3줄을 먼저 띄우고 나머지 블록은 접힌 상태로 둔다. 사용자는 읽고 다음을 누른다.
5. **설계 판단.**
   1. 결론을 먼저 두는 이유는 사용자가 리포트를 읽으러 온 것이 아니기 때문이다. 근거는 필요할 때만 편다.
   2. 5번 블록이 다음 화면의 질문이 된다. 질문이 어디서 나왔는지 보고 나서 답하게 만든다.
   3. 이 화면이 이 서비스의 주장 전부다. 배점만 아는 도구도, 자격만 아는 도구도 이 출력을 못 만든다.

### 4.4 S4 계획서 내용 채우기

1. **진입.** S3 다음 버튼.
2. **목표.** 분석이 특정한 빈칸만 채운다.
3. **구성.** 세 묶음이다.
   1. **사업 내용.** 부족한 항목만 묻는다.
   2. **원하는 방향.** 강조축 선택과 금지 표현 지정.
   3. **참고.** 답이 내 정보에 저장된다는 안내.
4. **흐름.**
   1. 질문마다 어느 심사 항목 몇 점에 쓰이는지 한 줄로 붙인다.
   2. 내 정보에 있는 값은 채워서 보여주고 고칠 수 있게 한다.
   3. 건너뛰기를 허용하고 그 결과를 알린다.
   4. 답변은 즉시 내 정보의 집필용 항목에 저장된다.
5. **설계 판단.**
   1. 질문에 배점을 붙이는 것이 이 단계의 전부다. 범용 도구는 사업에 대해 알려 달라고 뭉뚱그려 묻는다. 우리는 25점짜리 항목에 필요한 것을 지목해 묻는다.
   2. 금지 표현을 받는 이유는 인터뷰의 문체 마찰 때문이다. 생성 후 손질 분량을 줄인다.

### 4.5 S5 계획서 초안 작성

1. **진입.** S4 다음 버튼.
2. **레이아웃.** 메인 영역을 2분할한다. 좌측 항목 네비, 우측 에디터.
3. **흐름.**
   1. 좌측에 심사 항목, 배점, 작성 상태를 둔다. 순서는 배점 높은 순이다.
   2. 에디터 상단에 얇은 컨텍스트 바를 둔다. 항목명, 배점, 분량, 원본 공고 링크.
   3. 초안이 스트리밍으로 생성된다. 첫 출력까지 5초를 넘기지 않는다.
   4. 항목 단위로 다시 쓸 수 있다.
   5. 사용자가 직접 고친 문단은 재생성해도 덮지 않는다.
   6. 컨텍스트 바 옆에서 이 항목의 2단계 답변을 펼쳐 바로 고칠 수 있다. 고치면 그 항목만 다시 쓴다.
   7. 분량 카운터가 공고 제한 대비 현재 분량을 보여준다.
4. **설계 판단.** 우측 근거 패널을 두지 않는다. 사용자가 집필 중 계속 봐야 하는 것은 배점과 분량이고 그건 한 줄이면 된다.
5. **에러.** 실패는 항목 단위로 처리한다. 만든 항목은 유지한다.

### 4.6 S6 문서 산출

1. **진입.** S5 완료 버튼.
2. **흐름.**
   1. 심사 항목 순서로 합쳐 미리보기를 보여준다.
   2. 안 쓴 항목이 있으면 상단에 알린다.
   3. 하단에 책임 고지를 넣는다.
   4. PDF로 내려받는다. 완료 시 신청 현황 상태를 바꿀지 묻는다.

### 4.7 S7 신청 현황

1. **진입.** LNB 신청 현황.
2. **구성.**
   1. 최상단에 마감 임박 경고. D-7 이내 건이 있으면 띄운다.
   2. 상태별 그룹. 검토 중, 준비 중, 작성 중, 제출 준비 완료, 제출함.
   3. 각 행에 사업명, 마감 D-day, 계획서 진행률, 다음 할 일과 버튼.
3. **흐름.** 다음 할 일 버튼을 누르면 그 단계로 간다. 검토 중이면 S2로, 작성 중이면 S5의 해당 항목으로, 제출 준비 완료면 S6으로 간다.
4. **설계 판단.**
   1. 다음 할 일 열이 이 화면의 존재 이유다. 없으면 즐겨찾기와 다를 게 없다.
   2. 상태를 자동으로 바꾸지 않는다. 제출이 범위 밖이라 우리가 알 방법이 없고, 안다고 표시하면 거짓이 된다.

### 4.8 S8 내 정보

시연에서 열지 않는다. 기능은 갖춘다.

1. **진입.** 우상단 아바타.
2. **구성.** 두 탭이다.
   1. **개인정보.** 대표자 생년월일, 연락처.
   2. **사업 정보.** 두 묶음으로 나눈다. 판별에 쓰는 정형 항목과 계획서에 쓰는 서술 항목이다. 각 묶음 위에 무엇에 쓰이는지 한 줄로 적는다.
3. **흐름.** 인라인 편집. 판별용 항목을 고치면 전체 재판정이 돌고 바뀐 공고 수를 알린다.

### 9.1 색

**GitHub Primer 라이트 모드 값을 그대로 쓴다.** 명도 대비가 이미 검증된 값이라 따로 계산하지 않는다. 의미가 있는 곳에만 색을 쓰고 나머지는 무채색이다.

**색 사용 규칙 넷.**

4. 본문 영역에는 색을 쓰지 않는다. 링크만 `--accent`다.

### 11.2 미확인 사실

근거 문서가 사라져 **확인된 적 없는 상태가 된 사실 주장**이다. 화면은 이 값들 위에 그려져 있으므로, 틀리면 화면이 틀린다.

| ID | 주장 | 쓰이는 곳 | 왜 미확인인가 |
|----|------|-----------|---------------|
| U1 | 초기창업패키지 심사는 **서류평가 · 심층인터뷰 · 발표평가 3단계**다 | §4.2 S2 5번 블록, §5.3 와이어프레임 | "`research.md` 2.3에서 확인"이라 적혀 있었으나 그 문서가 없다 |
| U2 | 서류평가 배점은 **문제인식 30 · 실현가능성 30 · 성장전략 25 · 팀구성 15**다 | §5.3, §12.4, S3 전체 | 원래부터 미확인이라고 적혀 있었다. 웹 본문에 없고 **첨부 HWP 안에 있는 것으로 추정**된다 |
| U3 | 실제 탈락 사유는 **지정 양식 미준수와 제출 후 수정 불가**다 | §4.2 S2 4·6번 블록 | "`context.md` 6장 때문"이라 적혀 있었으나 그 문서가 없다 |

**셋은 같은 자료 하나로 한꺼번에 확인된다.** 초기창업패키지 실제 공고와 그 첨부 문서를 받아 열어보면 U1·U2·U3가 동시에 결판난다. 따로 조사할 일이 아니다.

**U2가 가장 무겁다.** 배점을 못 얻으면 S3 공고 분석이 성립하지 않고, 그러면 남는 것은 자격 필터링뿐이라 이미 있는 서비스와 같아진다. `function.md` F0-2에 같은 내용을 적어 두었다.

**근거는 사라졌지만 재확인이 필요 없는 것.** §1.4의 디자인 기준(서체 Pretendard, 색 Primer, 밀도 Carbon, 카피 Polaris, 목록 Atlassian)은 사실 주장이 아니라 선택이다. 근거 문서가 없어도 결정은 그대로 유효하다.

### 11.3 남은 일

1. **첨부 문서 파싱 가능성 확인.** U1·U2·U3를 확인하는 동시에, 첨부(HWP·HWPX·PDF)에서 배점표가 기계적으로 추출되는지, 표본 20~30건에서 배점 명시율이 몇 %인지 잰다. 결과는 `docs/dev_research.md`로 남긴다. **아직 만들지 않은 문서다.**
2. **이 문서의 데모 전제를 제품 전제로 교체.** §1.5 A2·A3와 §9.4가 아직 "목업 데이터 · 사전 색인 스냅샷 · 단일 HTML · 외부 요청 없음"을 전제한다. `function.md` F0이 실제로 돌면 A3는 사실이 아니게 된다. 화면 설계(S1~S8, 토큰, 카피 규칙)는 그대로 유효하므로 전제 몇 줄만 고치면 된다. 프론트 착수 시점에 한다.
